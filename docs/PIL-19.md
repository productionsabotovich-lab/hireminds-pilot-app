## Цель и основания

Клиенту HTTP-API нужна сводка по списку дел без изменения данных: сколько дел всего,
сколько ещё открыто, сколько выполнено. Чистая функция считает по переданному состоянию
списка, эндпоинт `GET /todos/stats` отдаёт те же счётчики в JSON.

- [API приложения](../README.md), [модель списка и чистые функции](../src/todos.ts),
  [HTTP-обработчик](../src/server.ts), [существующие тесты](../test/todos.test.ts),
  [команды и зависимости](../package.json);
- соседние постановки той же функциональности: спецификация

## Согласуемый объём

### 1. Чистая функция `todoStats` (`src/todos.ts`)

- Экспортируется из `src/todos.ts` рядом с остальными чистыми функциями, по именованию
  и стилю существующих функций (`addTodo`, `completeTodo`, `listTodos`).
- Сигнатура: `todoStats(list: TodoList): TodoStats`, где
  `export type TodoStats = { total: number; open: number; done: number }`.
  Тип `TodoList` — существующий (`{ nextId, items }`); новые типы для входа и принимаемые
  `Todo[]` не вводятся. **Решение аналитика:** вход — `TodoList`, потому что так устроены
  все чистые функции модуля, а эндпоинт тогда передаёт `state` напрямую.
- Результат — обычный объект **ровно с тремя собственными ключами**: `total`, `open`, `done`.
  Никаких дополнительных полей, вложенности, процентов и метаданных.
- Значения — неотрицательные целые числа:
  - `total` = количество элементов `list.items`;
  - `done` = количество элементов с `done === true`;
  - `open` = количество элементов с `done === false` (эквивалентно `total - done`).
- Инвариант: `total === open + done` для любого корректного входа.
- Счёт идёт по флагу `done` у элементов, а не по истории действий: повторное
  `completeTodo` уже выполненного дела не увеличивает `done` дважды.
- Функция **не мутирует** вход: не меняет `list`, `list.nextId`, массив `list.items`
  (ссылка, длина и порядок), поля и идентичность элементов; элементы не добавляются
  и не удаляются.
- Функция детерминирована: повторные вызовы с одним и тем же состоянием дают равные результаты.
- Валидация некорректного объекта вне контракта TypeScript не вводится: функция
  внутренняя, единственный вызывающий код передаёт состояние сервера.

### 2. Эндпоинт `GET /todos/stats` (`src/server.ts`)

- Обработчик добавляется в существующий `handle` в `src/server.ts`; состояние читается
  из текущей переменной `state`. Новое хранилище, новые модули и новая логика хранения
  не вводятся.
- Ответ: HTTP **200**, заголовок `Content-Type: application/json; charset=utf-8`
  (существующий хелпер `send`), тело — результат `todoStats` для текущего состояния
  **без обёртки и дополнительных полей**: `{"total":N,"open":N,"done":N}`.
- Запрос только читает: состояние процесса после запроса не меняется, поведение
  `GET /todos`, `POST /todos`, `POST /todos/:id/complete` не меняется.
- Параметры запроса, включая `filter`, игнорируются: статистика всегда по всему списку.
  Неизвестные query-параметры не приводят к ошибке.
- Путь сопоставляется точно: `/todos/stats` не совпадает с `/todos` и с шаблоном
  `/todos/(\d+)/complete` (совпадение требует цифровой `id`), поэтому коллизий с
  существующими маршрутами нет; логика ответа 404 для неизвестных путей сохраняется
  (включая `/todos/stats/` со слешем — так же, как сейчас ведут себя другие пути).
- Метод, отличный от `GET` (например `POST /todos/stats`), получает существующий
  ответ 404 `{"error":"not found"}` — новое поведение для него не вводится.
- Новая ветка маршрута ставится внутри существующей цепочки `if` до ветки 404;
  отдельный файл-роутер, middleware и рефакторинг `handle` не вводятся.

### 3. Тесты (`test/todos.test.ts`)

Добавляются в существующий файл `test/todos.test.ts`, рядом с текущими кейсами `todos`,
без новых тестовых зависимостей и без отдельных файлов. Обязательные кейсы:

- **Пустой список**: `todoStats(emptyList())` → ровно `{ total: 0, open: 0, done: 0 }`.
- **Смешанный список**: три дела, одно выполнено → ровно `{ total: 3, open: 2, done: 1 }`.
- **Все выполнены**: два выполненных дела → ровно `{ total: 2, open: 0, done: 2 }`.
- **Отсутствие мутаций**: снимок состояния (ссылка на `list`, значение `nextId`, ссылка и
  содержимое массива `items`, поля и идентичность каждого элемента) до и после вызова
  совпадает; повторный вызов даёт тот же результат.

Сравнение результата — точное, по всему объекту (`toEqual`): лишние определённые ключи
в результате проверку не проходят, поэтому отдельная проверка набора ключей не обязательна,
но допускается. Дополнительно (сверх обязательного, а не вместо него) допускаются проверки
инварианта `total === open + done` и попытка записи в замороженный вход (`Object.freeze`)
как способ обнаружения мутации.

Кейс HTTP-эндпоинта в `test/` допускается, но не обязателен: отдельного серверного
харнесса в проекте сейчас нет, а его добавление расширяет объём. Функциональная
проверка эндпоинта вынесена в план проверки.

## Исключения и границы

Вне объёма (не делается в этой задаче):

- UI, веб-интерфейс, дашборды и визуализация статистики;
- сохранение данных, базы данных, файловое или внешнее хранилище: статистика живёт
  в памяти процесса так же, как сам список, и сбрасывается при перезапуске;
- статистика по фильтрам, пользователям, категориям, приоритетам, процентам и долям;
- новые поля в модели `Todo`/`TodoList`, миграции модели, валидация некорректного `TodoList`;
- рефакторинг существующих маршрутов, изменение формата ответов `GET /todos`,
  `POST /todos`, `POST /todos/:id/complete`;
- новые зависимости, изменения `package.json`/`package-lock.json`, изменения `.github/**`,
  CI и инфраструктуры;
- серверные тест-харнессы и отдельные файлы тестов;
- пагинация, сортировка, версионирование API, кэш и `ETag`.

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые TypeScript,
  Node.js `>=20` и Vitest.
- `package.json` и `package-lock.json` не меняются; `npm ci` работает без обновления
  lock-файла.
- Требуются только команды из [package.json](../package.json): `npm run check` и `npm test`;
  обе доступны без сети.
- Особенность окружения: в текущем окружении установлен `NODE_ENV=production`, при котором
  `npm ci` пропускает dev-зависимости (`npm config get omit` → `dev`; `typescript`, `vitest`,
  `@types/node` в `node_modules` отсутствуют, `npm test` → `vitest: not found`). Поэтому
  для локальных проверок нужен `NODE_ENV=development npm ci --include=dev`. На это
  не влияют изменения в репозитории.
- Спецификация (`docs/PIL-19.md`) включается в PR реализации.

## План проверки

1. `npm run check` — проверка типов проходит без ошибок (включая новую сигнатуру `todoStats`).
2. `npm test` — все тесты vitest проходят; новые кейсы (пустой список, смешанный,
   все выполнены, отсутствие мутаций) присутствуют и зелёные; существующие кейсы `todos`
   не меняются по смыслу.
3. Ручная проверка эндпоинта: `npm run build && npm start`, затем
   `GET /todos/stats` (ожидается `{"total":0,"open":0,"done":0}`),
   `POST /todos {"title":"a"}`, повторный `GET /todos/stats` (`total` 1, `open` 1),
   `POST /todos/1/complete`, `GET /todos/stats` (`total` 1, `open` 0, `done` 1),
   `GET /todos/stats?filter=open` (тот же ответ), `POST /todos/stats` (404).
4. Проверка, что `GET /todos/stats` не изменил состояние: `GET /todos` до и после
   запроса статистики отдаёт тот же список.
5. Проверка границ объёма: `git diff --name-only main...HEAD` показывает только
   `src/todos.ts`, `src/server.ts`, `test/todos.test.ts`, `README.md`, `docs/PIL-19.md`;
   `package.json`, `package-lock.json`, `.github/**` без изменений.
6. CI на текущем HEAD PR выполняет `npm ci`, `npm run check`, `npm test` — все три шага зелёные.
