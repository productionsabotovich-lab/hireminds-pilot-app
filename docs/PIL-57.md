# PIL-57 — Проверка чтения TODO без фильтра

Редакция 1 от 2026-11-24. Статус: предложена к утверждению.

## Цель и основания

Подтвердить, что чтение списка TODO без фильтра возвращает все записи в существующем
порядке. Если подходящая проверка уже существует, использовать её, сохранив API.

## Фактическое состояние и восстановление

База анализа — `main`, коммит
[dd2526c](https://github.com/productionsabotovich-lab/hireminds-pilot-app/commit/dd2526c).
Перед подготовкой документа рабочее дерево чистое; документа PIL-57 нет.
Проверка удалённых веток по ключу PIL-57 и
[PR во всех состояниях](https://github.com/productionsabotovich-lab/hireminds-pilot-app/pulls?q=is%3Apr+PIL-57)
не выявила сохранённой ветки или PR этой задачи на момент подготовки редакции.
Контекст трекера прочитан из предоставленного снимка; прямого доступа к трекеру в этой
сессии нет. Ошибка предыдущего запуска отражена в журнале, отдельного результата
спецификации в доступных источниках не найдено.

В `test/server.test.ts` уже есть кейс `lists todos and filters them by state`:
через HTTP создаёт `a`, затем `b`, завершает первое дело и проверяет, что запрос
`GET /todos` без query-параметров возвращает HTTP 200 и точный массив
`[{ id: 1, title: 'a', done: true }, { id: 2, title: 'b', done: false }]`.
Сравнение массива через `toEqual` проверяет порядок, состав и поля записей.
Проверка длины в тесте чистой функции сама по себе порядок не подтверждает;
основанием приёмки служит существующий HTTP-кейс.

## Согласуемый объём

Использовать существующий HTTP-кейс для подтверждения требования; повторный тест
и изменение рабочего кода не требуются. Под существующим порядком понимается порядок
элементов текущего списка: добавление помещает запись в конец, завершение сохраняет
её позицию. Новое правило сортировки не вводится.

В этой фазе создаётся только `docs/PIL-57.md`. После утверждения выполняются
существующие проверки и фиксируется ссылка на использованный кейс и результат запуска.
Если существующий кейс не проходит, фиксируется расхождение с этой спецификацией;
изменение поведения API не входит в согласуемый объём.

## Пользовательские сценарии и критерии приёмки

| Сценарий | Критерий приёмки | Подтверждение |
| --- | --- | --- |
| Клиент создал `a`, затем `b` и читает список без фильтра | HTTP 200; JSON-массив содержит обе записи в порядке `a`, `b` | Существующий HTTP-кейс после завершения первой записи |
| Клиент завершил первое дело и читает список без фильтра | Выполненная запись остаётся первой; возвращаются и выполненная, и открытая запись, с прежними `id`, `title`, `done` | Точное сравнение массива в том же кейсе |
| Проверка порядка уже есть | Используется `lists todos and filters them by state`; новый дублирующий кейс не создаётся | Ссылка на кейс и успешный запуск |
| Прогон регрессии | `npm run check` и `npm test` проходят; API и существующие проверки сохранены | Результат запуска после утверждения |
| Проверка границ изменения | Изменена только спецификация PIL-57 | Diff относительно базы задачи |

## Исключения и ограничения

- Сообщения об авторизации раннера, подключения платформы и повторные запуски относятся
  к контексту тестового прогона; изменение авторизации не входит в задачу приложения.
- Новые маршруты, параметры, сортировка, пагинация, UI и постоянное хранилище исключены.
- Поведение фильтров `all`, `open`, `done`, неизвестных параметров и прочих маршрутов
  сохраняется. Расширение матрицы тестов для них не требуется.
- Пустой список сохраняет действующее поведение; отдельный новый тест для него
  не требуется для подтверждения порядка нескольких записей.
- Изменения `src/`, `test/`, зависимостей, конфигурации, CI и других спецификаций
  в согласуемый объём не входят. Работа ограничена тестовым репозиторием проекта.

## Зависимости

Нужны Node.js >=20 и зависимости из текущего lock-файла, включая Vitest и TypeScript.
Для HTTP-тестов необходим локальный сокет; существующий каркас использует свободный
порт, изоляцию состояния и закрытие сервера. Внешние API и новые пакеты не нужны.
Проверки выполняются после утверждения спецификации; реализация и декомпозиция
до утверждения не начинаются.

## План проверки после утверждения

1. При необходимости установить текущие зависимости через `npm ci --include=dev`,
   не меняя manifest и lock-файл.
2. Выполнить `npm test -- test/server.test.ts -t "lists todos and filters them by state"`.
   Подтвердить прохождение существующего HTTP-кейса с точным сравнением массива.
3. Выполнить обязательные проверки проекта `npm run check` и `npm test`.
4. Проверить diff: допустим только `docs/PIL-57.md`; новых тестов и изменений API нет.
5. В результате проверки сослаться на существующий кейс и приложить фактический
   результат команд. Ошибку окружения отличать от нарушения порядка в ответе.
