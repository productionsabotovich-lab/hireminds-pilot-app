# PIL-41 — GET /health в тестовом API

Редакция 1 от 2026-11-19. Статус: объём ожидает утверждения, реализация не начата.

## Цель и основания

Потребителю тестового API (например, E2E-проверке) нужен простой HTTP-запрос,
подтверждающий, что сервис принимает запросы и отвечает. Ответ не зависит от состояния
списка дел и от внешних сервисов: проверка работоспособности не создаёт, не изменяет и
не расходует идентификаторы задач.

Основания и ограничения:

- [Постановка PIL-41](/opt/hireminds/context/issue.md).
- [Правила проекта](../CLAUDE.md) и [правила документов](README.md).
- [Действующий контракт API](../README.md#api), [HTTP-обработчик](../src/server.ts),
  [существующие HTTP-тесты](../test/server.test.ts).
- [Действующая спецификация PIL-21](PIL-21.md): контракт сводки сохраняется, её
  исторические вопросы к PM в PIL-41 не входят.
- Смежные задачи семейства проверок: PIL-35 (`GET /readyz`), PIL-38 (`GET /healthz`),
  PIL-39 (`GET /livez`, только спецификация), PIL-40 (`GET /version`) — см. вопрос 1 к PM.
  Закрытая без слияния PIL-15 вводила `GET /health` с телом `{"status":"ok","uptime":N}`;
  в текущем `main` маршрута `/health` нет, поведение PIL-41 задаётся заново.

## Контракт и согласуемый объём

- `GET /health` возвращает HTTP **200** и тело ровно `{"status":"ok"}` — единственный
  ключ `status` со значением `ok`, без обёртки, дополнительных полей и завершающего
  перевода строки.
- Медиа-тип ответа — `application/json`. Используется существующий общий способ отправки
  JSON из [src/server.ts](../src/server.ts), поэтому фактический заголовок —
  `application/json; charset=utf-8`; указание кодировки не меняет требуемый медиа-тип
  и совпадает с поведением остальных маршрутов.
- Ответ одинаков при любом состоянии списка: при пустом списке, при наличии открытых
  и выполненных задач, при повторных запросах.
- Обработчик не читает и не изменяет состояние списка: задачи, их порядок, поля и счётчик
  следующего идентификатора сохраняются. Внешних запросов, обращений к файлам и базам
  данных нет; отдельное состояние готовности или счётчик uptime не вводится.
- Маршрут сопоставляется по методу `GET` и точному `url.pathname === '/health'` — так же,
  как существующие маршруты. Query-параметры игнорируются: `/health?probe=1` даёт тот же
  ответ, что и `/health`.
- Другие методы на `/health`, в том числе `POST`, а также пути `/health/` и
  `/health/extra` сохраняют существующий ответ 404 `{"error":"not found"}`; для `HEAD`
  тело ответа не требуется (стандартные правила HTTP).
- Существующие маршруты `GET /todos`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete` и обработка ошибок сохраняют поведение: статусы, тела
  ответов, фильтрация и сводка не меняются.
- Новое HTTP-поведение покрывается автоматическими кейсами в существующем
  [test/server.test.ts](../test/server.test.ts) — тем же каркасом, что и текущие
  HTTP-тесты: сервер поднимается на реальном сокете (`createServer(handle)`,
  `listen(0, '127.0.0.1')`, адрес берётся из `server.address()`), запросы выполняются
  глобальным `fetch`, состояние изолируется через `vi.resetModules()` и динамический
  импорт `../src/server.js`, сервер закрывается в `afterEach`.
- В таблицу раздела «API» [README.md](../README.md#api) добавляется одна строка про
  `GET /health` с ожидаемым ответом; остальные разделы документации не переписываются.
- Новых зависимостей нет. `package.json`, `package-lock.json`, `tsconfig.json`,
  `CLAUDE.md`, `docs/README.md`, `.github/**` не меняются; [src/todos.ts](../src/todos.ts)
  не меняется — отдельная бизнес-функция для health-ответа не нужна, ответ не зависит
  от модели задач.

Ожидаемые изменения после утверждения: `src/server.ts`, `test/server.test.ts`,
`README.md` и эта спецификация `docs/PIL-41.md`. В фазе спецификации создаётся только
`docs/PIL-41.md`.

## Исключения и границы

В объём входят только маршрут в [src/server.ts](../src/server.ts), HTTP-проверки в
существующем [test/server.test.ts](../test/server.test.ts), одна строка таблицы API в
[README.md](../README.md#api) и эта спецификация `docs/PIL-41.md`. Новая ветка обработки
использует существующий способ отправки JSON; отдельный файл-роутер, middleware и
рефакторинг `handle` не вводятся.

За пределами объёма:

- дополнительные поля health-ответа: `uptime`, версия, время старта, счётчики —
  в отличие от закрытой PIL-15 тело остаётся ровно `{"status":"ok"}`;
- readiness/liveness-семантика и маршруты `GET /readyz` (PIL-35), `GET /healthz` (PIL-38),
  `GET /livez` (PIL-39), `GET /version` (PIL-40) — это отдельные задачи; в PIL-41
  не вводятся;
- мониторинг, метрики, health-агенты, агрегаторы, трассировка, алерты;
- проверки готовности зависимостей: баз данных, файлов, внешних сервисов; исходящие
  сетевые запросы из health-ответа;
- авторизация, rate limit, кэширование (`ETag`, `Cache-Control`), версионирование API,
  CORS и настройки запуска и порта;
- изменения `src/todos.ts`, модели задач, существующих маршрутов и форматов их ответов;
- UI, веб-интерфейс, дашборды;
- новые зависимости, изменения `package.json`/`package-lock.json`, `tsconfig.json`,
  `CLAUDE.md`, `docs/README.md`, `.github/**`, CI и инфраструктуры;
- чужие задачи, ветки и PR (PIL-15, PIL-35, PIL-38, PIL-39, PIL-40) не трогаются.

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые Node.js `>=20`,
  TypeScript и Vitest, встроенные `node:http` и `fetch`.
- HTTP-тесту нужен локальный сокет на свободном порту (`listen(0, '127.0.0.1')`);
  внешний сервер и сеть за пределами loopback не требуются.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным.
- Требуются только команды из [package.json](../package.json): `npm run check` и `npm test`;
  обе доступны без сети после установки dev-зависимостей.
- Особенность окружения (проверено на текущем `main`): в окружении `NODE_ENV=production`
  и `npm config omit=dev`, поэтому обычный `npm ci` **не ставит** dev-зависимости — для
  `npm run check` и `npm test` нужен `npm ci --include=dev`. В CI выполняется обычный
  `npm ci` (см. [.github/workflows/ci.yml](../.github/workflows/ci.yml)), где dev-зависимости
  устанавливаются.
- Особенность конфигурации (проверено): `tsconfig.json` включает только `src`, поэтому
  файлы в `test/` не проверяются командой `npm run check` — типы тестов проверяются
  только в IDE, а сборка `npm run build` затрагивает только `src`.
- Спецификация (`docs/PIL-41.md`) включается в PR реализации.

## План проверки

1. `npm run check` — проверка типов проходит без ошибок.
2. `npm test` — все тесты vitest проходят; видна новая группа кейсов `GET /health`
   в `test/server.test.ts`; существующие кейсы (`todos`, `todoStats`, HTTP-маршруты)
   не меняются по смыслу и по числу (на текущем `main` — 21 успешный тест).
3. Ручная проверка на собранном сервере: `npm run build && npm start`, затем
   `curl -i http://127.0.0.1:3000/health` — ожидаются HTTP 200,
   `content-type: application/json; charset=utf-8` и тело ровно `{"status":"ok"}`;
   `curl http://127.0.0.1:3000/todos` до и после health-запроса отдаёт одинаковый список;
   `POST /todos {"title":"a"}` после health-запроса создаёт задачу с `id` 1.
4. Проверка неподдерживаемых вариантов: `POST /health` и `GET /health/` — 404
   `{"error":"not found"}`; `GET /health?probe=1` — тот же успешный ответ.
5. Проверка границ объёма: `git diff --name-only main...HEAD` показывает только
   `src/server.ts`, `test/server.test.ts`, `README.md`, `docs/PIL-41.md`;
   `package.json`, `package-lock.json`, `tsconfig.json`, `src/todos.ts`, `.github/**`
   без изменений.
6. CI на HEAD PR выполняет `npm ci`, `npm run check`, `npm test` — все три шага зелёные.

## Вопросы к PM

1. **Конвенция семейства проверок.** В трекере параллельно идут PIL-35 (`/readyz`),
   PIL-38 (`/healthz`, открытый PR #18), PIL-39 (`/livez`, только спецификация),
   PIL-40 (`/version`, открытый PR #19) и закрытая без слияния PIL-15 (`/health`
   с полем `uptime`). Нужно ли ввести единую конвенцию health-маршрутов и объединить
   эти задачи? Решение по умолчанию: PIL-41 реализует `GET /health` самостоятельно,
   чужие задачи, ветки и PR не трогаются; при слиянии нескольких задач в `README.md`
   появится несколько строк таблицы API.
2. **Формат тела.** Требуется ли строго ровно `{"status":"ok"}` (как в постановке) или
   допустимо расширение (например, `uptime`, как в PIL-15)? Решение по умолчанию: строго
   `{"status":"ok"}`, без дополнительных полей.
3. **Заголовок Content-Type.** Достаточно соответствия медиа-типу `application/json`
   (фактически `application/json; charset=utf-8` из общего способа отправки JSON) или
   требуется заголовок ровно `application/json` без параметра `charset`? Решение по
   умолчанию: использовать существующий общий способ отправки JSON, отдельный
   заголовок для одного маршрута не вводить.
4. **Уровень E2E.** Достаточно ли автоматического HTTP-теста в `test/server.test.ts`
   (по примеру существующих тестов), или нужен отдельный E2E-прогон против запущенного
   сервера — например, скрипт или шаг CI с `curl`? Решение по умолчанию: автоматический
   HTTP-тест в существующем файле тестов; ручной прогон собранного сервера остаётся
   частью плана проверки, отдельный E2E-скрипт и изменения CI не вводятся.
