# PIL-49 — E2E Stop · HEAD для статистики TODO

Редакция 1. Статус: спецификация подготовлена, объём не утверждён; реализация не начата.

## Цель и основания

Задача — контрольный (E2E) прогон Hireminds с остановкой активного этапа и продолжением
работы после «Повторить». Проверяется, что сессия возобновляется после остановки этапа
Spec и приводит к ожидаемому материальному результату в тестовом репозитории TODO API.

Материальный результат задачи — работающий маршрут `HEAD /todos/stats` в тестовом
приложении:

- HTTP **200**;
- те же заголовки представления, что у `GET /todos/stats`
  (`Content-Type: application/json; charset=utf-8`);
- **пустое тело** (0 байт на уровне сокета);
- состояние списка дел сохраняется;
- HTTP-тест в `test/` и строка про `HEAD /todos/stats` в `README.md`.

Постановка требует именно этого: после утверждения спецификации добавить
`HEAD /todos/stats`, покрыть HTTP-поведение тестом и описать маршрут в README. Других
функциональных изменений не требуется.

Родственные постановки: [PIL-48](https://github.com/productionsabotovich-lab/hireminds-pilot-app/blob/hm/PIL-48-head-todos/docs/PIL-48.md)
(`HEAD /todos`; спецификация подготовлена в ветке `hm/PIL-48-head-todos`, реализации нет)
и PIL-24 (та же функциональность, спецификация без реализации). Отличие PIL-49 от них:
маршрут должен быть **реализован** в рамках контрольного прогона, а сама спецификация
должна быть самодостаточной — её достаточно для продолжения работы после остановки
этапа, без контекста прерванной сессии (см. раздел 4).

**Конфликт с PIL-48.** Критерий 6 и обязательный кейс в спецификации PIL-48 фиксируют
`HEAD /todos/stats` → 404 `{"error":"not found"}`; постановка PIL-49 требует для этого же
маршрута 200 с теми же заголовками, что у `GET`. Постановка PIL-49 новее и прямо
относится к этому пути, поэтому **PIL-49 выигрывает для `HEAD /todos/stats`**: критерий
и тест PIL-48 приводятся в соответствие, остальной объём PIL-48 (сам маршрут
`HEAD /todos`) не меняется (вопрос 1 к PM).

### Текущее поведение (проверено в этом окружении, Node.js v22.23.4)

Проверено на собранном сервере из `main` (`npm run build && npm start`) и на прототипе
с тем же хелпером `send`:

- `GET /todos/stats` → **200**, `Content-Type: application/json; charset=utf-8`,
  `Transfer-Encoding: chunked`, тело — JSON-сводка (для пустого списка
  `{"total":0,"open":0,"done":0}`, 29 байт);
- `HEAD /todos/stats` → **404** `{"error":"not found"}`: ветка маршрута проверяет строго
  `req.method === 'GET'`, поэтому `HEAD` попадает в обработку неизвестного маршрута;
- `HEAD /todos` → **404** на текущем `main` (реализация PIL-48 не в `main`);
- `POST /todos/stats` → **404** `{"error":"not found"}`;
- `HEAD /todos/stats/` (со слешем) → **404** `{"error":"not found"}` — путь сопоставляется
  точно;
- Node.js не пишет payload ответа в сокет для запроса с методом `HEAD`: прототип с тем
  же хелпером `send` дал **200**, `content-type: application/json; charset=utf-8` и
  **0 байт** тела; у `HEAD` нет `Transfer-Encoding`, у `GET` он есть (кадрирующий
  заголовок);
- базовая проверка на `main` пройдена: `npm run check` — без ошибок, `npm test` —
  21 тест в двух файлах, все зелёные;
- особенность окружения (проверено): `NODE_ENV=production` и `npm config omit=dev`,
  поэтому обычный `npm ci` **не ставит** dev-зависимости («up to date, audited 1
  package»); для `npm run check` и `npm test` нужен `npm ci --include=dev`. На содержимое
  репозитория это не влияет;
- `curl` в окружении отсутствует, ручные проверки выполняются Node-однострочниками
  (см. план проверки).

## Согласуемый объём

### 1. Маршрут `HEAD /todos/stats` (`src/server.ts`)

- Обработчик добавляется в существующий `handle` в `src/server.ts`: условие маршрута
  `/todos/stats` расширяется с `GET` на `GET` и `HEAD`. Отдельный файл-роутер,
  middleware и рефакторинг `handle` не вводятся; порядок веток `if` и ветка 404
  остаются как есть.
- Ответ `HEAD /todos/stats`:
  - HTTP **200** — тот же статус, что у `GET /todos/stats`;
  - заголовок представления `Content-Type: application/json; charset=utf-8` — то же
    значение, что у `GET /todos/stats` (тот же хелпер `send`);
  - **тело пустое**: 0 байт, переданных в сокет.
- Определение терминов:
  - **заголовки представления** — заголовки, описывающие представление ресурса. В этом
    API их ровно один: `Content-Type`. Значение `HEAD` совпадает со значением `GET` для
    того же URI;
  - **заголовки кадрирования и hop-by-hop** — `Transfer-Encoding`, `Content-Length`,
    `Connection`, `Keep-Alive`, `Date`. Они **не** входят в контракт: `GET /todos/stats`
    отдаётся chunked-без `Content-Length`, а у `HEAD` тела нет, поэтому Node.js не
    выводит `Transfer-Encoding`. `Content-Length` не добавляется (вопрос 3 к PM).
- Сводка считается по тем же правилам, что и у `GET /todos/stats`, включая игнорирование
  query-параметров (`filter` и любые другие). Поэтому заголовки представления
  `HEAD /todos/stats?filter=open` совпадают с `GET /todos/stats?filter=open`.
- Запрос только читает: состояние процесса после `HEAD /todos/stats` не меняется —
  дела не добавляются, не меняются и не завершаются; следующий выданный идентификатор
  не расходуется.
- **Все остальные пары «метод + путь» сохраняют текущее поведение** 404
  `{"error":"not found"}`: `HEAD /todos/:id/complete`, `HEAD /неизвестный-путь`,
  `HEAD /todos/stats/` (со слешем), `POST /todos/stats` и прочие. Код
  `405 Method Not Allowed` не вводится, новые методы и новые пути не появляются.
- Существующее поведение `GET /todos`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete` не меняется: прежние статусы, прежние тела ответов.
- `HEAD /todos` в объём PIL-49 **не входит**: этот маршрут — предмет PIL-48, и его
  контракт (200) прямо противоречил бы зафиксированному здесь 404 для остальных
  маршрутов (вопрос 6 к PM).
- Допустимые способы реализации (на выбор разработчика), оба обязаны давать один и тот
  же наблюдаемый контракт:
  - **(а) переиспользовать существующий хелпер `send`** — рекомендуемый вариант: Node.js
    для `HEAD` не пишет payload в сокет, поэтому `send(res, 200, todoStats(state))` даёт
    нужные заголовки и пустое тело (проверено прототипом в этом окружении);
  - **(б) отдельная ветка `HEAD`**, которая пишет те же заголовки представления и
    завершает ответ без payload (`res.end()`).
- Проверяемое требование — поведение на уровне HTTP, а не способ реализации: 200,
  совпадающий `Content-Type`, 0 байт тела.
- `src/todos.ts` **не меняется**: новая доменная логика не нужна, `HEAD` переиспользует
  существующую `todoStats`.

### 2. Проверки (`test/server.test.ts`)

Кейсы добавляются в существующий файл `test/server.test.ts` отдельной группой
`describe('HEAD /todos/stats')`. Существующие кейсы по смыслу не меняются. Новых
тестовых зависимостей нет: используются глобальный `fetch` Node.js и встроенный
`node:http`.

Обязательные кейсы:

- **Статус и заголовки совпадают с `GET`**: `HEAD /todos/stats` → 200; значение
  `content-type` равно значению `content-type` из `GET /todos/stats` для того же URI и
  равно строке `application/json; charset=utf-8`.
- **Тело пустое**: на уровне сокета длина полученного тела равна 0 байт. Проверка
  выполняется сырым запросом из `node:http`
  (`request({ host, port, path: '/todos/stats', method: 'HEAD' })`): `fetch` для `HEAD`
  всегда отдаёт пустое тело и сам по себе не доказывает, что сервер ничего не
  отправил. Дополнительно проверяется, что `await res.text()` равно `''`.
- **Пустой список**: `HEAD /todos/stats` при пустом состоянии → 200, тот же
  `content-type`, 0 байт тела.
- **Query-параметры игнорируются**: `HEAD /todos/stats?filter=open` → 200, `content-type`
  совпадает с `GET /todos/stats?filter=open`.
- **Запрос не меняет задачи**: `GET /todos` до и после `HEAD /todos/stats` отдаёт
  одинаковый список; `GET /todos/stats` до и после — одинаковые счётчики; следующий
  `POST /todos` получает следующий последовательный идентификатор (повторный `HEAD`
  идентификатор не расходует).
- **Неизвестные маршруты и методы сохраняют 404**: `HEAD /todos/:id/complete` → 404,
  `HEAD /неизвестный-путь` → 404, `HEAD /todos/stats/` → 404; существующий кейс
  `POST /todos/stats` → 404 остаётся.
- **Регрессия существующих маршрутов**: `GET /todos`, `GET /todos?filter=open`,
  `GET /todos?filter=done`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete` отвечают как раньше (прежние статусы и прежние тела).

Ограничение на состав кейсов (прямое следствие конфликта с PIL-48, раздел «Цель и
основания»):

- **кейс `HEAD /todos` → 404 в PIL-49 не добавляется**: по контракту PIL-48 этот маршрут
  должен отдавать 200. Проверка `HEAD /todos` в тестах PIL-49 не фиксируется, чтобы
  тесты оставались зелёными и после объединения PIL-48;
- порядок слияния при этом не важен: реализация PIL-49 не ломает тест PIL-48 для
  `HEAD /todos`, а тест PIL-48 для `HEAD /todos/stats` должен быть заменён на 200
  (вопрос 1 к PM).

Рекомендуемый и проверенный каркас (прототип собран и прогнан при подготовке
спецификации: 21 существующий + 6 новых кейсов, `npm test` — зелёный):

- переиспользуются существующие `beforeEach`/`afterEach` каркаса файла: `vi.resetModules()`
  и динамический импорт `const { handle } = await import('../src/server.js')` дают новый
  экземпляр модуля с пустым `state`, поэтому кейс «пустой список» детерминирован;
- для HEAD добавляется рядом с существующими `get`/`post` хелперами два хелпера:
  - `head(path)` — `fetch` с `method: 'HEAD'` для проверки статуса и заголовков;
  - `headRaw(path)` — сырой запрос `request({ host: '127.0.0.1', port, path, method:
    'HEAD' })` из `node:http`, который возвращает статус, заголовки и число байт тела
    (порт берётся из `server.address()` — тот же, что у `baseUrl`);
- существующие хелперы `get`, `post` и `addTodo` не меняются.

Замечания по окружению (не влияют на объём):

- `tsconfig.json` включает только `src`, поэтому файлы в `test/` **не** проверяются
  командой `npm run check`; типы тестов проверяются только вручную/в IDE.
- Сборка `npm run build` тоже затрагивает только `src`.
- Vitest по умолчанию изолирует каждый тестовый файл (свой реестр модулей), поэтому
  `test/server.test.ts` не влияет на `test/todos.test.ts` и наоборот.

## Исключения и границы

Вне объёма (не делается в этой задаче):

- `HEAD` для остальных маршрутов, в том числе `HEAD /todos` (предмет PIL-48) и `HEAD`
  для POST-маршрутов (`HEAD /todos/:id/complete`);
- `405 Method Not Allowed` и любые другие коды вместо существующего 404;
- `Content-Length`, `ETag`, `Cache-Control`, кэширование и прочие заголовки кадрирования
  и валидации представления (вопросы 3, 5 и 7 к PM);
- обработка обрыва клиентского соединения как отдельная функциональность: специальные
  обработчики `aborted`/`close`, таймауты, ретраи, коды ошибок соединения — текущее
  поведение (сервер переживает обрыв и продолжает работать) сохраняется;
- поддержка `HEAD` через отдельный сервер или middleware, рефакторинг `handle`,
  выделение роутера в отдельный модуль;
- изменения `GET /todos` и `GET /todos/stats`: формат тел и заголовков прежний; сама
  сводка и её чистая функция `todoStats` не меняются;
- изменения модели `Todo`/`TodoList`, новые чистые функции в `src/todos.ts`;

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые Node.js `>=20`
  (`node:http`, глобальный `fetch`), TypeScript и Vitest. HTTP-клиент из зависимостей
  не нужен.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным,
  `npm ci` работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check` и
  `npm test`; обе доступны без сети.
- Особенность окружения (проверено): в текущем окружении `NODE_ENV=production` и
  `npm config omit=dev`, поэтому обычный `npm ci` **не ставит** dev-зависимости;
  для `npm run check` и `npm test` нужен `npm ci --include=dev`. На содержимое
  репозитория это не влияет.
- Особенность проекта: `tsconfig.json` включает только `src`, поэтому файлы в `test/`
  **не** проверяются командой `npm run check` — типы тестов проверяются только вручную
  или в IDE. Сборка `npm run build` тоже затрагивает только `src`.
- В окружении отсутствует `curl`, поэтому ручные проверки выполняются Node-однострочниками
  (см. план проверки); для пользователя эквивалент — `curl -I
  http://127.0.0.1:3000/todos/stats`.
- Спецификация (`docs/PIL-49.md`) включается в PR реализации.

## Вопросы к PM (не блокируют минимальный объём)

1. **Конфликт с PIL-48.** Спецификация PIL-48 (ветка `hm/PIL-48-head-todos`) фиксирует
   `HEAD /todos/stats` → 404 (критерий 6 и обязательный тест), а постановка PIL-49
   требует 200 с теми же заголовками, что у `GET /todos/stats`. Подтвердить, что PIL-49
   выигрывает для `/todos/stats`, и что соответствующий критерий и кейс PIL-48
   приводятся в соответствие (остальной объём PIL-48 не меняется)? Решение по
   умолчанию: **да** — PIL-49 реализует `HEAD /todos/stats` → 200, PIL-48 правится в
   одном пункте; ветки и PR не трогаются.
2. **Объединять ли PIL-48 и PIL-49.** Обе задачи — контрольные прогоны с `HEAD`-маршрутами.
   Нужно ли реализовать оба маршрута в одной ветке, или PIL-49 ограничивается только
   `/todos/stats`? Решение по умолчанию: **нет** — PIL-49 реализует только
   `HEAD /todos/stats`, `HEAD /todos` остаётся в PIL-48.
3. **`Content-Length` в ответе `HEAD`.** RFC 9110 рекомендует отдавать в ответе на
   `HEAD` те же поля, что и в ответе на `GET`, в том числе `Content-Length`. Сейчас
   `GET /todos/stats` идёт chunked-без `Content-Length`. Добавлять ли `Content-Length`
   со значением, равным длине JSON-тела `GET`? Решение по умолчанию: **не добавлять** —
   контракт задачи ограничен заголовками представления (`Content-Type`).
4. **Строгость «те же заголовки».** «Те же заголовки ответа, что у `GET /todos/stats`» —
   совпадать должен весь набор заголовков (включая `Transfer-Encoding`/`Content-Length`)
   или только `Content-Type`? Решение по умолчанию: **только `Content-Type`**
   (заголовки представления); разница в кадрирующих заголовках — нормальное поведение
   HTTP для `HEAD`.
5. **Кэширование.** Нужен ли `ETag` или `Cache-Control` для `HEAD /todos/stats`?
   Решение по умолчанию: **не добавлять**, отвечать как обычный JSON-эндпоинт.
6. **`HEAD` для других маршрутов.** Нужен ли `HEAD /todos/:id/complete` и `HEAD` для
   POST-маршрутов? Решение по умолчанию: **нет** — в объёме только `HEAD /todos/stats`,
   как в постановке.
7. **`405` вместо `404`.** Нужен ли для известных путей с неподдерживаемым методом ответ
   `405 Method Not Allowed` с заголовком `Allow`? Решение по умолчанию: **нет**,
   сохраняется существующий 404 — постановка требует сохранить обработку неизвестных
   маршрутов.
8. **Регресс-тест на обрыв соединения.** Стоит ли добавить кейс «сервер переживает
   обрыв клиентского соединения», чтобы зафиксировать E2E-аспект остановки этапа в
   репозитории? Решение по умолчанию: **нет** — поведение не меняется и уже устойчиво
   (проверено), контракт задачи — `HEAD /todos/stats`.
