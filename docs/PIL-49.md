## Контракт и границы объёма

- Только точный путь `/todos/stats` получает поддержку метода HEAD.
- Ответ — HTTP 200; прикладные заголовки совпадают с GET того же URI.
  В текущем API это `Content-Type: application/json; charset=utf-8`.
- Тело отсутствует: после блока заголовков сервер не передаёт байты тела.
  Динамический Date и транспортные поля Connection, Keep-Alive,
  Transfer-Encoding не требуют побайтного совпадения с GET.
  Новые заголовки не требуются. Если Content-Length присутствует, он соответствует
  длине GET-представления, а не нулевой длине HEAD-тела.
  Основание: [семантика HEAD](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2).
- Query-параметры, включая filter и неизвестные параметры, игнорируются,
  как у GET; статистика относится ко всему списку.
- HEAD не меняет элементы, порядок, признаки выполнения и следующий ID.
  Повторные HEAD также ничего не меняют. Состояние остаётся в памяти процесса;
  сохранение состояния означает отсутствие мутации запросом, а не хранение
  после перезапуска.
- GET статистики и операции списка сохраняют поведение. Путь `/todos/stats/`
  и неподдерживаемые методы, например POST для `/todos/stats`, сохраняют 404.
  Ответ HEAD с ошибкой также не содержит тела.
- В таблицу API README добавляется строка про `HEAD /todos/stats`:
  200, заголовки как у GET, без тела.
- После утверждения допускаются изменения только `src/server.ts`,
  `test/server.test.ts`, `README.md` и этой спецификации.
  Выбор способа обработки HEAD остаётся разработчику; проверяется HTTP-контракт.

PIL-49 уточняет прежнее общее правило PIL-21 «метод, отличный от GET, возвращает
404» только для HEAD статистики. Реализация HEAD для `/todos`, чужие ветки,
тесты и спецификации не входят в объём. При последующей интеграции PIL-48
его отрицательные ожидания для `/todos/stats` должны учитывать утверждённый
контракт PIL-49; чужие документы в рамках этой задачи не правятся.

## Пользовательские сценарии и критерии приёмки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Клиент запрашивает HEAD статистики пустого списка | 200, Content-Type как у GET, 0 байт тела |
| В списке есть открытые и выполненные дела | Тот же контракт HEAD без JSON-тела |
| Клиент повторяет HEAD | Список и GET-статистика до и после равны; следующий POST получает очередной ID |
| Передан `?filter=open` или неизвестный параметр | 200, заголовки как у GET того же URI, тело отсутствует |
| HEAD для `/todos/stats/` | 404 без тела |
| POST для `/todos/stats` | Прежний 404 с прежним JSON ошибки |
| GET статистики и существующие операции списка | Прежние статусы, тела, фильтрация и изменения состояния |
| Пользователь читает README | В таблице API есть строка с контрактом HEAD статистики |

## Исключения

Вне объёма: HEAD для других путей, новые поля статистики, изменение модели,
постоянное хранилище, UI, авторизация, кэширование, новые зависимости,
рефакторинг роутера, изменение CI, введение 405 и изменения платформы Hireminds.
Остановка этапа и «Повторить» — контекст контрольного прогона платформы;
обработка обрыва HTTP-соединения не является новой функцией приложения.

## Зависимости

Используются существующие Node.js >=20, TypeScript, Vitest и встроенные HTTP-средства.
Менять зависимости и lock-файл не требуется. Базовый GET уже присутствует в main.
Существующая изоляция тестов через `vi.resetModules()` и локальный сервер подходит
для новых проверок; после теста соединения и сервер должны закрываться.
Реализация начинается после утверждения спецификации платформенным решением.

## План проверки после утверждения и реализации

1. В `test/server.test.ts` проверить реальный HTTP-ответ HEAD на пустом и смешанном
   списке: 200, Content-Type совпадает с GET, тело пустое.
2. Для требования об отсутствии байтов использовать сырой TCP-запрос через
   `node:net` с `Connection: close`: после разделителя заголовков `\r\n\r\n`
   до закрытия соединения нет данных. Ограничить ожидание таймаутом и закрывать
   соединение при любом исходе. Один лишь `fetch().text()` или отсутствие событий
   data у HTTP-клиента не доказывает отсутствие байтов на проводе.
3. В HTTP-сценарии с открытым и выполненным делом сравнить список и статистику
   до и после повторных HEAD; последующим POST проверить сохранение следующего ID.
4. Проверить query-параметры и отрицательные случаи из таблицы;
   существующие тесты операций списка должны продолжать проходить.
5. Перед PR выполнить обязательные `npm run check` и `npm test`.
   При исключённых dev-зависимостях установить инструменты через
   `npm ci --include=dev`. Проверить строку README и границы diff.

В фазе спецификации проверяются документ и сохранённое состояние;
реализация, HTTP-прототипы и тесты приложения не выполняются.
