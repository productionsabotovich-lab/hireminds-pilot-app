# PIL-75 — Версия тестового API

Редакция 1 от 2026-11-28. Статус: подготовлена к утверждению объёма.

## Цель и основания

Клиент тестового API получает версию приложения по HTTP и сопоставляет её с
`version` в `package.json` обслуживающего приложения.

## Согласуемый объём

- Добавить в существующий HTTP-обработчик `GET /version`.
- Возвращать HTTP 200, `Content-Type: application/json; charset=utf-8` и JSON
  ровно с одним полем `version` строкового типа, равным `package.json.version`.
  Текущее значение — `0.1.0`; оно является примером, а не константой контракта.
- Источник истины — `package.json` приложения. Не дублировать номер версии
  в исходном коде, не получать его из окружения, Git или внешнего сервиса.
  Допускается однократное чтение при загрузке модуля; изменение файла во время
  работы процесса не требует обновления ответа без перезапуска.
- Маршрут должен работать при штатном запуске собранного приложения
  `npm run build && npm start`, независимо от рабочего каталога процесса.
  Способ чтения метаданных выбирается при реализации с учётом NodeNext и структуры `dist`.
- Запрос не читает и не изменяет список дел. Query-параметры игнорируются.
- Сопоставление пути точное: `/version/` и `/Version` остаются неизвестными путями.
  Методы, отличные от GET, сохраняют существующий ответ 404
  `{"error":"not found"}`; отдельные 405, OPTIONS и обработка HEAD не добавляются.
- Поведение существующих маршрутов, ошибок и хранения данных сохраняется.
- В существующем `test/server.test.ts` добавить автоматическую проверку HTTP-ответа.
  Ожидаемую версию брать из `package.json`, независимо от экспортов реализации.
- В README добавить строку API и короткий пример:
  `curl -s http://127.0.0.1:3000/version` с ответом `{"version":"0.1.0"}`,
  пояснив, что версия соответствует `package.json`.

## Пользовательские сценарии и критерии приёмки

| Сценарий | Критерий |
| --- | --- |
| Клиент запрашивает `GET /version` | HTTP 200, JSON content-type, тело точно равно `{ version: packageJson.version }`, без дополнительных полей |
| Версия в метаданных меняется и приложение перезапускается/пересобирается | Ответ соответствует новой версии без изменения константы в исходниках |
| Клиент запрашивает `/version?probe=1` | Тот же ответ, что для `/version` |
| Клиент отправляет `POST /version` или запрашивает `/version/`, `/Version` | HTTP 404 и существующее тело `{"error":"not found"}` |
| Клиент запрашивает версию между операциями с TODO | Список и сводка до и после запроса совпадают; добавление, фильтрация и завершение работают как прежде |
| Клиент обращается к собранному серверу | Контракт совпадает с тестовым запуском обработчика, версия доступна без зависимости от текущего каталога |
| Разработчик читает README | Есть путь, пример вызова и пример ответа с указанием источника версии |

## Исключения и границы объёма

В объём входят только `src/server.ts`, `test/server.test.ts`, `README.md` и эта
спецификация `docs/PIL-75.md`. Реализация выполняется после утверждения спецификации
в ветке задачи и представляется одним PR в `main` вместе со спецификацией.

Не входят: изменение самой версии, `package.json` и lock-файла, новые зависимости,
изменение `tsconfig.json` или CI, рефакторинг TODO, UI, авторизация, health/readiness,
Git SHA, сведения о сборке и окружении, версионирование путей API, специальные
заголовки кэширования, горячая перезагрузка метаданных и упаковка приложения без
его `package.json`. Отсутствующий или некорректный `package.json` — некорректная
установка приложения; новый публичный контракт ошибок для неё не вводится.

## Зависимости

Используются существующие Node.js >=20, TypeScript и Vitest из
[package.json](../package.json), встроенные API Node.js и существующий HTTP-каркас
тестов. Внешние сервисы не требуются. `package.json` остаётся доступным в штатной
структуре репозитория рядом с каталогами `src` и `dist`. Ограничения PIL-21
относятся к его изменению; эта задача расширяет API отдельным маршрутом,
сохраняя контракт сводки и остальных операций.

## План проверки после утверждения и реализации

1. HTTP-тест: проверить статус, content-type и точное равенство JSON версии из
   метаданных; проверить игнорирование query-параметров и указанные случаи 404.
2. Проверить неизменность списка и сводки до/после запроса версии на непустом
   состоянии. Запустить существующие регрессионные тесты маршрутов и TODO.
3. Выполнить обязательные `npm run check` и `npm test`; CI должен пройти на HEAD PR.
4. Выполнить `npm run build`, запустить `node /абсолютный/путь/к/dist/server.js`
   из другого рабочего каталога и вызвать `/version`. Сравнить ответ с версией
   корневого `package.json`. Убедиться, что штатный `npm start` также работает.
5. В отдельной временной копии изменить только `package.json.version`,
   пересобрать/перезапустить и повторить запрос. Ответ должен отражать новую
   версию; изменения метаданных не включать в PR.
6. Проверить пример README, границы diff и отсутствие новых зависимостей.

Эти проверки являются планом приёмки реализации; в фазе спецификации они не выполняются.
