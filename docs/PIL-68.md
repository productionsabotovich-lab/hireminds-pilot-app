# PIL-68 — Текстовая сводка списка дел

Редакция 1 от 2026-11-24. Статус: подготовлена к утверждению объёма.
Реализация и декомпозиция до утверждения не выполняются.

## Цель и основания

Терминал мониторинга получает количество всех, открытых и завершённых дел простым
текстовым HTTP-запросом, без разбора JSON и без изменения списка.

## Согласуемый объём и контракт

1. Добавляется только `GET /todos/stats.txt`: HTTP 200,
   `Content-Type: text/plain; charset=utf-8`, тело в UTF-8 без BOM.
2. Ответ содержит ровно три строки со счётчиками в порядке `total`, `open`, `done`.
   Числа — десятичные неотрицательные целые без группировки и ведущих нулей,
   кроме самого нуля. Они равны полям `GET /todos/stats` для того же состояния;
   выполняется `total = open + done`.
3. Для первой реализации принимается базовый формат `имя: число`, разделитель строк
   LF. Предлагаемое тело пустого списка: `total: 0\nopen: 0\ndone: 0\n`;
   смешанного списка: `total: 3\nopen: 2\ndone: 1\n`.
   Завершающий LF не означает дополнительную пустую строку содержимого.
   **Это исходная редакция формата, а не предсказание замечания QA:** окончательное
   требование к последней строке уточняется в предусмотренном первом возврате QA.
4. Сводка считается по всему текущему списку. Query-параметры, включая `filter`,
   игнорируются, как у JSON-сводки. Заголовок Accept не переключает формат маршрута.
5. Чтение не меняет элементы, их порядок, идентификаторы и состояние генерации id.
   Повторные запросы при неизменном списке возвращают одинаковое тело.
6. Сохраняются существующие статусы, заголовки и тела JSON API: список, фильтры,
   добавление, завершение и `GET /todos/stats`. Текст не проходит JSON-сериализацию.
7. Сопоставление пути точное. `/todos/stats.txt/` и методы, отличные от GET,
   остаются в существующей обработке неизвестных маршрутов:
   404 с JSON `{"error":"not found"}`. Отдельного контракта HEAD не добавляется.

## Пользовательские сценарии и критерии приёмки

| Сценарий | Критерий |
| --- | --- |
| Мониторинг запрашивает пустой список | 200, текстовый UTF-8, три счётчика равны нулю и совпадают с JSON |
| Созданы три дела, одно завершено | Строки в порядке total/open/done со значениями 3/2/1; совпадение с JSON |
| Все дела открыты либо все завершены | Отсутствующая категория имеет значение 0; общий счёт корректен |
| После добавления или завершения запрошена сводка | Отражено новое состояние; повторное завершение не увеличивает done второй раз |
| Два чтения текстовой сводки | Ответы равны, список до и после полностью совпадает; следующее добавление получает ожидаемый id |
| Запрос с `?filter=open` или неизвестным query-параметром | Те же счётчики всего списка |
| Использование прежнего JSON API | Существующие контрактные и регрессионные проверки проходят без ослабления |
| Проверка окончательного текста | Полное равенство ожидаемых байтов, включая пробелы, LF и последнюю строку по фактическому уточнению QA |
| Проверка Content-Length после уточнения | Отдельная проверка заданного QA диапазона в байтах и соответствия длине фактического тела |

Равенство текстовой и JSON-сводки проверяется последовательными запросами без
промежуточной записи. Согласованность двух запросов при параллельных изменениях
списка не обещается.

## Двухэтапное согласование формата

По [постановке](/opt/hireminds/context/issue.md) первая проверка QA возвращает
реализацию разработчику с фактическим уточнением последней строки и отдельной
проверкой диапазона Content-Length в байтах. Разработчик учитывает это замечание,
синхронизирует документированный пример с итоговым форматом и дополняет тесты.
Повторный QA оценивает исправленный результат.

Точное уточнение и численные границы в доступных материалах отсутствуют;
настоящая редакция их не выдумывает. Исходный пример не отменяет предусмотренный
возврат. До получения замечания окончательная приёмка этих двух пунктов невозможна.
В финальной проверке Content-Length должен быть корректным целым числом байтов тела
UTF-8, без HTTP-заголовков, и попадать в фактически заданный диапазон. Длину нужно
измерять по байтам, а не по количеству символов. Проверка только точного тела или
только равенства длине не заменяет отдельную проверку диапазона.

## Исключения и границы

В объём входят HTTP-маршрут, HTTP-тесты, описание маршрута и примера в README,
эта спецификация и исправление формата по первому замечанию QA.
Ожидаемые файлы: `src/server.ts`, `test/server.test.ts`, `README.md`, `docs/PIL-68.md`.
Подсчёт переиспользует существующую `todoStats`; повторная реализация счётчиков не нужна.
Логика остаётся чистой в `src/todos.ts`, I/O — в `src/server.ts`.

Вне объёма: UI терминала мониторинга, новые счётчики и фильтрация статистики,
постоянное хранилище, авторизация, кэширование, новый роутер, рефакторинг JSON API,
изменение модели, зависимостей, настроек сборки и GitHub Actions, чужие задачи и PR.

## Зависимости и ограничения выполнения

- Используются Node.js >=20, TypeScript и Vitest из [package.json](../package.json).
  Внешние сервисы и новые зависимости не требуются.
- [Правила проекта](../CLAUDE.md) требуют одну ветку и один PR на задачу;
  основная ветка не изменяется. Эта спецификация готовится в ветке задачи.
- Для PIL-68 каждый коммит ветки содержит буквальный маркер `[skip ci]` в сообщении.
  Это требование [постановки](/opt/hireminds/context/issue.md) заменяет для этой
  задачи прежнее требование PIL-21 о зелёном GitHub Actions.
- `npm run check` и `npm test` выполняются на VPS, результаты привязываются к
  проверенной редакции реализации. Пропуск CI не заменяет эти проверки.
- Итоговое уточнение QA — зависимость окончательной приёмки формата и длины.

## План проверки после утверждения

1. Расширить существующий HTTP-набор в `test/server.test.ts`: изоляция состояния,
   реальный локальный HTTP-сервер, запросы штатным клиентом Node.js.
2. Проверить пустой, смешанный, полностью открытый и полностью завершённый списки:
   статус, Content-Type, точное тело и равенство счётчиков JSON. Проверить изменение
   сводки после записи, повторное чтение, отсутствие изменения списка и расхода id.
3. Проверить игнорирование query, точность пути и сохранение 404 для не-GET;
   выполнить существующие проверки JSON API.
4. На первом QA зафиксировать фактическое замечание о последней строке и диапазоне
   Content-Length. После возврата проверить исправленные байты и отдельный тест
   диапазона, в том числе на значениях счётчиков с несколькими цифрами.
   Если требование QA не задаёт границ или условий диапазона, запросить конкретизацию.
5. На VPS выполнить `npm run check` и `npm test` для исправленной редакции;
   при повторном QA проверить код, тесты и актуальный пример README вместе.
6. Проверить состав diff, отсутствие новых зависимостей и изменений основной ветки,
   наличие `[skip ci]` во всех коммитах ветки задачи.
