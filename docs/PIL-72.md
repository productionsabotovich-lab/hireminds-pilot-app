## Согласуемый объём и контракт

1. `GET /todos` принимает необязательный query-параметр `q` — буквальную подстроку
   заголовка `title`. Совпадение возможно в начале, середине или конце заголовка.
   Регистр игнорируется посредством одинакового стандартного преобразования строк
   JavaScript `toLowerCase()`; поддерживаются латиница и кириллица. Регулярные
   выражения, маски, разбиение на слова и нечёткий поиск не применяются.
2. Поиск применяется совместно с `filter`: результат содержит только дела,
   одновременно подходящие по статусу и заголовку. `filter=open` выбирает открытые,
   `filter=done` — выполненные; `all`, отсутствие, пустое и неизвестное значение
   `filter` сохраняют существующее поведение выбора всех статусов.
3. При отсутствии `q`, а также для `?q` и `?q=` поискового ограничения нет.
   Пробелы в непустом `q` значимы: строка не обрезается. Акценты, `е`/`ё` и разные
   Unicode-нормализации не приравниваются дополнительно.
4. Значение читается через стандартный `URLSearchParams`: URL-кодирование
   декодируется один раз, `+` означает пробел, буквальный плюс передаётся как `%2B`.
   Для повторяющихся `q` используется первое значение, как для существующего
   `filter`. Например, `?q=&q=хлеб` не ограничивает заголовки.
5. Ответ — HTTP 200, `Content-Type: application/json; charset=utf-8`, JSON-массив
   существующих объектов `{ id, title, done }`, без обёртки и новых полей.
   При отсутствии совпадений, включая пустое хранилище, ответ — `[]`.
   Порядок дел сохраняется; заголовки и состояние не меняются.
6. Логика поиска находится в чистой функции в `src/todos.ts`; разбор HTTP-параметра —
   в `src/server.ts`. Допустимо расширить `listTodos` необязательным третьим
   аргументом `q`, сохранив поведение существующих вызовов с одним/двумя аргументами.
   Новые зависимости и хранилища не требуются.
7. В README описываются `q`, поиск без учёта регистра, пустое значение и сочетание
   с `filter`; приводится пример `GET /todos?filter=open&q=хлеб`
   с пояснением URL-кодирования значения при отправке запроса.

## Пользовательские сценарии и критерии приёмки

Для сценариев 1–6 через HTTP созданы дела в таком порядке:
`{id:1,title:"Купить ХЛЕБ",done:false}`,
`{id:2,title:"Хлеб для ужина",done:true}`,
`{id:3,title:"Позвонить врачу",done:false}`.
Здесь идентификаторы обозначают порядок в изолированном пустом хранилище.

| № | Запрос / сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | `/todos?q=хЛеБ` | Дела 1 и 2 в исходном порядке, полные объекты без изменения заголовков |
| 2 | `/todos?q=вра` | Только дело 3: совпадение внутри слова |
| 3 | `/todos?q=молоко` | 200 и `[]` |
| 4 | `/todos?filter=open&q=хлеб` | Только дело 1 |
| 5 | `/todos?filter=done&q=хлеб` | Только дело 2 |
| 6 | `/todos?filter=all&q=хлеб` или неизвестный `filter` с тем же `q` | Дела 1 и 2 |
| 7 | Нет `q`, `?q`, `?q=`; также с `filter=open` и `filter=done` | Тот же список, что без поискового параметра при соответствующем фильтре |
| 8 | Пустое хранилище, любой `q` | 200 и `[]` |
| 9 | Заголовок `Read TypeScript`, `q=typesCRIPT` | Совпадение без учёта регистра латиницы |
| 10 | Заголовки `a.b` и `axb`, `q=.` | Только `a.b`: поиск буквальный |
| 11 | Заголовки `a b` и `a+b` | `q=a+b` находит первый; `q=a%2Bb` — второй |
| 12 | `q=%20хлеб%20` на исходном наборе | `[]`: пробелы не удаляются |
| 13 | `q=молоко&q=хлеб` | `[]`: используется первое значение |
| 14 | Список и статистика до/после поисковых запросов | Данные и счётчики не изменились |

Все поисковые ответы сохраняют статус, Content-Type и формат из контракта.
Порядок query-параметров не влияет на результат сочетания `q` и `filter`.

## Исключения и границы объёма

В объём входят чистая логика поиска, передача `q` из HTTP, автоматические HTTP-проверки
и описание параметра в README. Разрешённые файлы реализации после утверждения:
`src/todos.ts`, `src/server.ts`, `test/todos.test.ts`, `test/server.test.ts`,
`README.md` и эта спецификация `docs/PIL-72.md`.

Вне объёма: UI, поиск по `id` или другим полям, сортировка по релевантности,
пагинация, индексы, постоянное хранение, новые маршруты, изменение модели,
новые зависимости, изменение CI и конфигурации проекта, рефакторинг иных операций.
Лимиты длины `q` и отдельные ошибки валидации для него не вводятся.
`GET /todos/stats` по-прежнему игнорирует query-параметры, включая `q` и `filter`,
и возвращает общую статистику. Создание и завершение дел сохраняют прежний контракт.

## Зависимости

Используются существующие Node.js >=20, TypeScript и Vitest; HTTP-клиент — встроенный
`fetch`. Внешних сервисов и зависимых продуктовых задач нет. Существующий HTTP-каркас
обеспечивает изоляцию состояния через сброс модулей и сервер на свободном порту.
Объём этой редакции утверждён платформой 2026-11-25.

## План проверки

1. В `test/server.test.ts` автоматически проверить сценарии таблицы реальными
   HTTP-запросами; данные создавать и завершать через API. Проверять полные тела
   ответов, порядок, статусы и Content-Type. Для кириллицы и значимых символов
   формировать URL через `URLSearchParams` либо корректное percent-encoding.
2. Сравнить `/todos` до и после поиска; проверить неизменность `/todos/stats`,
   в том числе с `?q=молоко&filter=open`. Сохранить существующие HTTP-тесты
   создания, завершения и фильтрации без `q`.
3. В `test/todos.test.ts` проверить чистую логику: совместное ограничение по статусу
   и заголовку, обратную совместимость вызовов без `q` и отсутствие изменения
   входного списка, порядка и полей элементов.
4. После реализации выполнить `npm run check` и `npm test`; обе команды должны
   завершиться успешно согласно правилам проекта. В фазе спецификации эти команды
   не подтверждают ещё не реализованное поведение и не запускаются.
5. Проверить описание `q` и пример совместного запроса в README, а также состав diff:
   только согласованные файлы, без изменений зависимостей и конфигурации.
