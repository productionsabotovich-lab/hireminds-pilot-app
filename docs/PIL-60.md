# PIL-60 — Пустой список TODO

Редакция 1. Статус: подготовлена к утверждению; объём не утверждён.

## Цель и основания

Клиент получает успешный ответ с пустым массивом при запросе списка к пустому
хранилищу. Контракт закрепляется автоматической HTTP-проверкой и примером запроса.

- [Текущий API](../README.md), [действующая спецификация PIL-21](PIL-21.md).
- [Маршрут и JSON-ответ](../src/server.ts), [пустое состояние и список](../src/todos.ts).
- [HTTP-тесты и изоляция состояния](../test/server.test.ts), [тесты логики](../test/todos.test.ts).
- [Команды и зависимости](../package.json), [CI](../.github/workflows/ci.yml).

Краткая редакция 0 была сохранена в рабочей копии до просмотра маршрута; после
просмотра уточнены контракт и критерии ниже. По исходному коду требуемое поведение
уже предусмотрено. В текущих HTTP-тестах нет отдельного случая пустого `GET /todos`.
Это вывод статического анализа, а не результат запуска сервера.

## Согласуемый объём

- Закрепить существующий контракт: `GET /todos` при пустом состоянии возвращает
  HTTP `200`, `Content-Type: application/json; charset=utf-8`, тело ровно `[]`.
  Пустота — нормальный результат, без обёртки, сообщения об ошибке или `null`.
- Добавить отдельную автоматическую проверку через реальный HTTP-сервер в
  `test/server.test.ts`, используя существующий каркас Vitest, Node HTTP и `fetch`.
  Перед сценарием состояние гарантированно пустое: существующие сброс модулей и
  динамический импорт обработчика; до запроса задачи не создаются. Сервер закрывается
  после сценария существующим механизмом очистки.
- В `README.md` рядом с описанием API добавить пример для только что запущенного
  процесса, до создания задач: `curl -i http://127.0.0.1:3000/todos`.
  Показать значимые части ответа: статус `200`, JSON Content-Type и тело `[]`.
  Указать предпосылку пустого хранилища; обычный запрос списка не очищает данные.
- Сохранить спецификацию в `docs/PIL-60.md` для продолжения работы после Stop/Retry.

Допустимые изменения после утверждения: `test/server.test.ts`, `README.md`,
`docs/PIL-60.md`. Правки `src/server.ts` и `src/todos.ts` не требуются по текущему
коду и в согласуемый объём не входят. Если проверка выявит несоответствие контракта,
причину следует отразить и пересогласовать границы, прежде чем расширять изменения.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий | Критерий |
| --- | --- | --- |
| 1 | Клиент запрашивает `GET /todos` до создания задач в свежем состоянии | HTTP 200; Content-Type `application/json; charset=utf-8`; тело ровно `[]` |
| 2 | Клиент повторяет запрос без записи данных | Тот же успешный пустой ответ; чтение не создаёт задач |
| 3 | Разработчик запускает автоматические проверки | Отдельный HTTP-тест проверяет сценарии 1–2, включая статус, заголовок и тело; не зависит от порядка тестов и не оставляет сервер работающим |
| 4 | Пользователь следует примеру README на свежем сервере | Пример содержит запрос, предпосылку пустого состояния и ожидаемый ответ из сценария 1 |
| 5 | Используются существующие операции и фильтры | Существующие тесты проходят без ослабления проверок; формат и поведение маршрутов сохранены |

## Исключения и границы

- Пустое хранилище означает отсутствие задач в состоянии процесса, а не отсутствие
  совпадений фильтра. Новые отдельные проверки фильтров в объём не входят.
- Существующие параметры запроса, неизвестные пути и методы, создание и завершение
  задач, статистика и обработка ошибок сохраняют действующее поведение.
- Не добавляются API очистки, тестовый публичный маршрут сброса, постоянное хранилище,
  UI, зависимости, изменения сборки, конфигурации и CI.
- Stop и штатный Retry — контекст платформенного пилотного прогона. Реализация и
  автоматизация Stop/Retry, управление платформой, доказательство сохранения после
  ещё не произошедшей остановки и создание отдельного E2E-набора платформы вне объёма.
  Сохранённый файл спецификации является рабочим артефактом этой фазы.

## Зависимости

Используются Node.js >=20, существующие TypeScript и Vitest из
[package.json](../package.json), текущий HTTP-каркас и хранение в памяти.
Новые пакеты и внешние сервисы не нужны. Фаза реализации начинается после
утверждения редакции спецификации. Правила одной ветки и одного PR определены в
[CLAUDE.md](../CLAUDE.md); создание PR не входит в фазу анализа.

## План проверки после утверждения

1. Запустить HTTP-тест на изолированном пустом состоянии: два последовательных
   `GET /todos`, каждый со статусом 200, указанным Content-Type и телом `[]`.
2. Выполнить `npm run check` и `npm test`; существующие проверки также должны пройти.
3. Собрать и запустить приложение штатными командами README; до любого POST выполнить
   документированный curl и сопоставить статус, Content-Type и тело с примером.
4. Проверить diff: только согласованные файлы, нет ослабления существующих тестов,
   изменений зависимостей или маршрутов. Пример не обещает пустой список для
   процесса с уже созданными задачами.

В фазе анализа тесты не добавлялись и не запускались; реализация не начиналась,
декомпозиция не выполнялась. Проверка сохранения через фактический Stop/Retry
остаётся за платформенным прогоном и не заявляется выполненной.
