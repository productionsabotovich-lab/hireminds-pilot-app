## Пользовательские сценарии и критерии приёмки

### Изоляция пустого состояния и проверка наличия тела

Новый сценарий размещается в существующей группе `server routes`, чтобы наследовать
её `beforeEach` и `afterEach`. Перед каждым тестом необходимо выполнить строго по
порядку: `vi.resetModules()`, динамический импорт `../src/server.js`, создание
`createServer(handle)` с только что импортированным обработчиком и запуск на
свободном порту `0`. Новый экземпляр модуля инициализирует собственный `state` через
`emptyList()`. Обработчик из статического импорта или предыдущего теста использовать
нельзя: сброс реестра не очищает состояние уже сохранённого обработчика.

Общая фикстура этого сценария только запускает сервер и не создаёт задачи.
Внутри сценария нет POST, вызовов `addTodo` или подготовки непустого списка.
Данные соседних кейсов остаются в прежних экземплярах модуля; новый сценарий не
должен зависеть от порядка выполнения. Если общая подготовка начнёт добавлять
задачи, пустой сценарий следует вынести в отдельную группу с таким же чистым
жизненным циклом, без наследования заполненной фикстуры. Параллельное выполнение
кейсов с общими переменными `server` и `baseUrl` не вводится.

Для каждого из двух последовательных ответов проверяются `status === 200`, точный
Content-Type и `expect(await res.text()).toBe('[]')`. Тело читается один раз.
Именно точное сравнение текста различает JSON-массив `[]` и отсутствие тела (`''`):
ответ 200 без тела не проходит, как и `null`, `{}` или обёртка `{"items":[]}`.
Ответ 204 также не проходит проверку статуса. Не допускаются подстановка пустого
массива при пустом теле, проверка только длины текста или один лишь `res.ok`.
Повторно читать тот же поток через `res.json()` не требуется.

Очистка после каждого кейса закрывает соединения и ожидает завершения `server.close()`;
это не механизм сброса хранилища: изоляцию обеспечивает новый экземпляр модуля.

| № | Сценарий | Критерий |
| --- | --- | --- |
| 1 | Клиент запрашивает `GET /todos` до создания задач в свежем состоянии | HTTP 200; Content-Type `application/json; charset=utf-8`; тело ровно `[]` |
| 2 | Клиент повторяет запрос без записи данных | Тот же успешный пустой ответ; чтение не создаёт задач |
| 3 | Разработчик запускает автоматические проверки | Отдельный HTTP-тест проверяет сценарии 1–2 на обработчике, динамически импортированном после `vi.resetModules()`, без заполнения фикстуры; каждый ответ проверяется через точное `res.text() === '[]'`, поэтому пустое тело не проходит; тест не зависит от порядка кейсов и закрывает сервер |
| 4 | Пользователь следует примеру README на свежем сервере | Пример содержит запрос, предпосылку пустого состояния и ожидаемый ответ из сценария 1 |
| 5 | Используются существующие операции и фильтры | Существующие тесты проходят без ослабления проверок; формат и поведение маршрутов сохранены |

### Сверка редакции 2 с существующими тестами

Уточнение выше сохранено до повторного чтения тестов. Затем выполнена статическая
сверка; на момент сверки новый тест ещё не был реализован.

| Критерий | Подтверждение и оставшийся объём |
| --- | --- |
| Пустое состояние каждого кейса | [beforeEach](../test/server.test.ts#L10) сбрасывает модули, динамически импортирует обработчик и запускает новый сервер; заполнения нет. [Инициализация state](../src/server.ts#L5) использует [emptyList](../src/todos.ts#L9). |
| Изоляция от данных соседних кейсов | [Наполнение списка](../test/server.test.ts#L52) и [подготовка теста списка](../test/server.test.ts#L127) находятся внутри отдельных `it`. Статического импорта обработчика нет. |
| Статус, заголовок, наличие и точное тело | [Тест пустой статистики](../test/server.test.ts#L45) уже отдельно проверяет статус, Content-Type и точный `res.text()`. Подход подходит для `[]`, но существующий тест относится к другому маршруту. |
| Два пустых ответа GET /todos | [Тест списка](../test/server.test.ts#L127) проверяет непустой массив; [проверка отсутствия мутаций](../test/server.test.ts#L78) относится к статистике заполненного списка. Два пустых ответа с точным телом `[]` остаются новым обязательным покрытием. |
| Освобождение сервера | [afterEach](../test/server.test.ts#L20) закрывает соединения и ожидает `server.close()`; новый кейс наследует очистку. |

Критерии совместимы с текущим каркасом без новых зависимостей и правок исходного
кода. Статическая сверка не заменяет запуск будущего теста.

## Реализация

Объём редакции 2 реализован в согласованных границах: `src/server.ts` и
`src/todos.ts` не менялись, контракт уже существовал.

- [Новый сценарий GET /todos](../test/server.test.ts#L112) добавлен в группу
  `server routes` и наследует её `beforeEach` и `afterEach`: сброс реестра модулей,
  динамический импорт обработчика, новый сервер на порту `0` и закрытие соединений
  после кейса. Внутри сценария нет POST и вызовов `addTodo`, поэтому хранилище
  гарантированно пустое и не зависит от порядка выполнения соседних кейсов.
- Тест выполняет два последовательных `GET /todos`; для каждого ответа проверяются
  `status === 200`, точный Content-Type `application/json; charset=utf-8` и
  `expect(await res.text()).toBe('[]')`. Тело каждого ответа читается один раз;
  точный текст отличает массив `[]` от пустого тела, `null`, объекта и обёртки.
- [Пример в README](../README.md#L38) показывает запрос `curl -i http://127.0.0.1:3000/todos`
  для только что запущенного процесса: статус `200`, JSON Content-Type и тело `[]`.
  Указана предпосылка пустого хранилища и то, что запрос списка не очищает данные.
- Этот файл сохранён как рабочий артефакт фазы Stop → Retry: реализация продолжена
  из сохранённой ветки без расширения объёма.

вне объёма и не заявляется выполненной.

## Исключения и границы

- Пустое хранилище означает отсутствие задач в состоянии процесса, а не отсутствие
  совпадений фильтра. Новые отдельные проверки фильтров в объём не входят.
- Существующие параметры запроса, неизвестные пути и методы, создание и завершение
  задач, статистика и обработка ошибок сохраняют действующее поведение.
- Не добавляются API очистки, тестовый публичный маршрут сброса, постоянное хранилище,
  UI, зависимости, изменения сборки, конфигурации и CI.
- Stop и штатный Retry — контекст платформенного пилотного прогона. Реализация и
  автоматизация Stop/Retry, управление платформой, доказательство сохранения после
  ещё не произошедшей остановки и создание отдельного E2E-набора платформы вне объёма.
  Сохранённый файл спецификации является рабочим артефактом этой фазы.
