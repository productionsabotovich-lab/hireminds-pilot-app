## Цель и границы объёма

Клиент получает количество всех, открытых и выполненных дел текущего списка.
После утверждения изменения ограничены `src/todos.ts`, `src/server.ts`,
`test/todos.test.ts` и `README.md`. Этот документ — артефакт фазы спецификации.
Новые зависимости, изменения `.github` и инфраструктуры исключены.

## Контракт

Экспортируемая чистая функция `todoStats(list: TodoList)` возвращает объект
ровно с тремя числовыми полями `{ total, open, done }`:

- `total` — число элементов `list.items`;
- `open` — число элементов с `done === false`;
- `done` — число элементов с `done === true`.

Все значения — неотрицательные целые числа, `total === open + done`.
Функция не изменяет `list`, `nextId`, массив `items`, его порядок и объекты дел.
Поддерживается существующая типизированная модель `TodoList`; валидация
произвольных некорректных входных данных не входит в объём.

`GET /todos/stats` возвращает HTTP 200, JSON с теми же тремя полями и
`Content-Type: application/json; charset=utf-8`. Подсчёт ведётся по всему
текущему состоянию в памяти процесса. Параметры запроса, включая `filter`,
не меняют статистику. Запрос не меняет состояние. Существующие маршруты
сохраняют поведение; неподдерживаемые методы используют существующий ответ 404.

## Пользовательские сценарии и критерии приёмки

| Сценарий | Ожидаемый результат функции и endpoint |
| --- | --- |
| В списке нет дел | `{ "total": 0, "open": 0, "done": 0 }` |
| Созданы три дела, одно завершено | `{ "total": 3, "open": 2, "done": 1 }` |
| Все три дела завершены | `{ "total": 3, "open": 0, "done": 3 }` |
| Добавлено новое открытое дело | `total` и `open` увеличиваются на 1; `done` прежний |
| Открытое дело завершено | `total` прежний; `open` уменьшается на 1, `done` увеличивается на 1 |
| Уже завершённое дело завершено повторно | Статистика не меняется |

Дополнительные критерии:

- Результат содержит только `total`, `open`, `done`, без дополнительных полей.
- Вызов функции сохраняет значения и ссылки входного списка, массива и элементов;
  чтение статистики по HTTP также не меняет список.
- В `test/todos.test.ts` добавлены проверки пустого, смешанного и полностью
  завершённого списка, а также отсутствия мутаций входных данных.
- В `README.md` указан новый endpoint, смысл полей и пример ответа.

## Исключения и зависимости

Не входят в объём: UI, проценты, группировки, история, сохранение данных,
новые фильтры статистики, изменение CRUD, рефакторинг архитектуры и зависимостей.
Статистика отражает только текущий процесс и обнуляется вместе с состоянием
после перезапуска. Зависимости: существующие `TodoList`, HTTP-обработчик,
Node.js >=20 и текущие TypeScript/Vitest. Новых внешних сервисов не требуется.

## План проверки после реализации

1. Автоматические тесты функции на трёх основных наборах из таблицы; точное
   сравнение объектов одновременно проверяет отсутствие лишних полей.
2. Проверка неизменности снимка входных данных и ссылок после вызова;
   замораживание списка, массива и каждого элемента позволяет обнаружить
   попытки записи, включая восстановленные впоследствии изменения.
3. HTTP-проверка на свежем процессе: пустая статистика; создание трёх дел;
   завершение одного; завершение остальных. Проверить статус, Content-Type,
   JSON, повторное чтение и независимость от `?filter=open`.
4. Проверить прежние маршруты списка, создания и завершения; убедиться,
   что чтение статистики не меняет результат `GET /todos`.
5. Выполнить `npm run check` и `npm test`; проверить diff на соблюдение
   списка разрешённых файлов и отсутствие новых зависимостей.

Это план будущей проверки, а не заявление о выполненных тестах.
