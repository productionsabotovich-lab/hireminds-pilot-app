# PIL-42 — Информация о сервисе TODO API

Редакция 1 от 2026-11-19. Статус: спецификация подготовлена к утверждению объёма;
реализация не начата, декомпозиция на задачи не выполнялась.

## Цель и основания

E2E-клиенту (внешней проверке, smoke-прогону, диагностике) нужен один HTTP-запрос,
который подтверждает, что перед ним именно сервис списка дел, и не создаёт побочных
эффектов: `GET /info` отвечает HTTP 200 и JSON с именем сервиса.

Ключевые свойства, которые следуют из постановки и фиксируются в объёме:

- маршрут **читает только**: список дел, его порядок, поля и счётчик следующего
  идентификатора не меняются, дела не создаются и не завершаются;
- ответ **не зависит от состояния данных**: одинаков при пустом списке и при
  заполненном, при повторных запросах;
- маршрут покрыт **автоматической HTTP-проверкой** (тест через реальный сокет),
  а не только ручной проверкой;
- поведение существующих маршрутов `/todos` **не меняется**;
- изменения ограничены репозиторием TODO API; новых зависимостей нет.

Основания:

  [команды и зависимости](../package.json), [CI](../.github/workflows/ci.yml);
- действующая спецификация [PIL-21](PIL-21.md) — контракт `GET /todos/stats` сохраняется,

## Контракт и согласуемый объём

Добавить маршрут в существующий HTTP-обработчик, автоматические проверки его поведения
в существующий набор HTTP-тестов и короткую документацию в README.

- `GET /info` возвращает HTTP **200** и JSON ровно `{"service":"todo-api"}`:
  единственный собственный ключ `service` со строковым значением `"todo-api"`.
  Никаких дополнительных полей (`version`, `uptime`, `environment`, счётчиков дел),
  обёртки и метаданных.
- Тело сериализуется общим способом отправки JSON приложения, поэтому фактический
  текст ответа — компактный: `{"service":"todo-api"}`. Пробелы в записи постановки
  (`{ "service": "todo-api" }`) — только форма записи JSON, семантика ответа та же.
- Заголовок `Content-Type: application/json; charset=utf-8` — тот же, что у остальных
  маршрутов; отдельный заголовок для одного маршрута не вводится.
- Ответ одинаков при любом состоянии списка: при пустом списке, при открытых и
  выполненных делах, при повторных запросах.
- Запрос не читает и не меняет состояние процесса: `state` в новой ветке обработки
  не используется и не присваивается, список, порядок, поля и счётчик следующего
  идентификатора сохраняются. Внешних обращений (файлы, базы, сеть) нет.
- Значение `todo-api` фиксировано в коде: оно не берётся из `package.json` (имя
  пакета — `hireminds-pilot-app`), из переменных окружения, из Git-метаданных и не
  настраивается; `package.json` и `package-lock.json` не меняются.
- Путь сопоставляется точно по `url.pathname`: совпадает только `/info`. Query-параметры
  игнорируются — `GET /info?probe=1` отдаёт тот же 200 и то же тело.
- Пути `/info/` (со слешем), `/Info`, `/api/info`, `/info/extra` сохраняют существующий
  ответ 404 `{"error":"not found"}`.
- Методы, отличные от `GET` (в том числе `POST`, `HEAD`, `OPTIONS`), сохраняют
  существующий ответ 404 `{"error":"not found"}`; ответ 405 и заголовок `Allow`
  не вводятся — это соответствует поведению остальных маршрутов приложения.
- Существующие маршруты `GET /todos` (с фильтрами `all|open|done`), `GET /todos/stats`,
  `POST /todos` (201), `POST /todos/:id/complete` (200 `{"ok":true}`), а также
  обработка ошибок (400 на некорректное тело и пустой `title`, 404 на неизвестные
  пути) сохраняют статусы, тела и семантику без изменений.
- Новая ветка обработки добавляется в существующую цепочку `if` внутри `handle`
  в [src/server.ts](../src/server.ts), до ветки 404; отдельный файл-роутер, middleware
  и рефакторинг `handle` не вводятся.
- [src/todos.ts](../src/todos.ts) не меняется: ответ не зависит от модели задач,
  отдельная чистая функция для константного ответа не нужна — так же сделано
  для `/version` (PIL-33, PIL-40) и `/health` (PIL-41). Константа с именем сервиса
  размещается в `src/server.ts` рядом с новой веткой обработки.
- Новое HTTP-поведение покрывается автоматическими кейсами в существующем
  [test/server.test.ts](../test/server.test.ts) — тем же каркасом, что и текущие
  HTTP-тесты: сервер поднимается на реальном сокете (`createServer(handle)`,
  `listen(0, '127.0.0.1')`, адрес берётся из `server.address()`), запросы выполняются
  глобальным `fetch`, состояние изолируется через `vi.resetModules()` и динамический
  импорт `../src/server.js`, сервер закрывается в `afterEach`.
- В таблицу раздела «API» [README.md](../README.md#api) добавляется одна строка про
  `GET /info` с ожидаемым ответом и рядом короткий пример запроса; остальные разделы
  документации не переписываются.
- Новых зависимостей нет. `package.json`, `package-lock.json`, `tsconfig.json`,
  `CLAUDE.md`, `docs/README.md`, `.github/**` не меняются.

Ожидаемые изменения после утверждения: `src/server.ts`, `test/server.test.ts`,
`README.md` и эта спецификация `docs/PIL-42.md`. На фазе спецификации создаётся только
`docs/PIL-42.md`.

## Исключения и границы

В объём входят только маршрут в [src/server.ts](../src/server.ts), HTTP-проверки
в существующем [test/server.test.ts](../test/server.test.ts), одна строка таблицы API
(и короткий пример запроса) в [README.md](../README.md#api) и эта спецификация
`docs/PIL-42.md`.

За пределами объёма:

- дополнительные поля в теле ответа (`version`, `uptime`, `environment`, `commit`,
  счётчики дел) — тело остаётся ровно `{"service":"todo-api"}`;
- вычисляемое имя сервиса: из `package.json`, переменных окружения, Git, DNS-имени
  хоста, конфигурационного файла; значение фиксировано в коде;
- перечисление сервисов, несколько сервисов в одном ответе, версионирование API
  (`/v1/info`), альтернативные пути (`/api/info`, `/service`, `/status`);
- readiness/liveness/health-семантика и остальные маршруты семейства:
  `GET /health` (PIL-41), `GET /healthz` (PIL-38), `GET /livez` (PIL-39),
  `GET /readyz` (PIL-35), `GET /version` (PIL-33, PIL-40), `GET /hello` (PIL-13) —
  это отдельные задачи, в PIL-42 не вводятся;
- поддержка `HEAD`, `OPTIONS`, ответ 405 с заголовком `Allow`, CORS, авторизация,
  rate limit, кэширование (`ETag`, `Cache-Control`);
- постоянное хранилище, базы данных, файлы, внешние сервисы, исходящие сетевые запросы;
- изменения [src/todos.ts](../src/todos.ts), модели задач, чистых функций дел,
  существующих маршрутов и форматов их ответов;
- UI, веб-интерфейс, дашборды, мониторинг, метрики, трассировка, алерты;
- новые зависимости, изменения `package.json`/`package-lock.json`, `tsconfig.json`,
  `CLAUDE.md`, `docs/README.md`, `.github/**`, CI и инфраструктуры;
- отдельный E2E-скрипт против запущенного сервера и новые шаги CI (см. вопрос 4 к PM);
- чужие задачи, ветки и PR (PIL-13, PIL-33, PIL-35, PIL-38, PIL-39, PIL-40, PIL-41) не
  трогаются.

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые Node.js `>=20`,
  TypeScript и Vitest, встроенные `node:http` и `fetch`.
- HTTP-тесту нужен локальный сокет на свободном порту (`listen(0, '127.0.0.1')`);
  внешний сервер и сеть за пределами loopback не требуются.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным,
  `npm ci` работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check` и
  `npm test`; обе доступны без сети после установки dev-зависимостей.
- Особенность окружения (проверено на текущем `main`): в окружении `NODE_ENV=production`
  и `npm config omit=dev`, поэтому обычный `npm ci` **не ставит** dev-зависимости —
  для `npm run check` и `npm test` нужен `npm ci --include=dev`. В CI выполняется
  обычный `npm ci` (см. [.github/workflows/ci.yml](../.github/workflows/ci.yml)), где
  dev-зависимости устанавливаются.
- Особенность конфигурации (проверено): `tsconfig.json` включает только `src`, поэтому
  файлы в `test/` не проверяются командой `npm run check` — типы тестов проверяются
  только в IDE, а сборка `npm run build` затрагивает только `src`.
- Спецификация (`docs/PIL-42.md`) включается в PR реализации.

## Вопросы к PM

1. **Конвенция семейства E2E-маршрутов.** В трекере параллельно идут PIL-13 (`/hello`),
   PIL-33 и PIL-40 (`/version`), PIL-35 (`/readyz`), PIL-38 (`/healthz`), PIL-39
   (`/livez`), PIL-41 (`/health`). Нужно ли ввести единую конвенцию для маршрутов
   самопроверки и объединить эти задачи в одну? Решение по умолчанию: PIL-42 реализует
   `GET /info` самостоятельно, чужие задачи, ветки и PR не трогаются; при слиянии
   нескольких задач в `README.md` появится несколько строк таблицы API.
2. **Значение `todo-api` и имя пакета.** В `package.json` пакет называется
   `hireminds-pilot-app`, а постановка требует `todo-api`. Нужно ли переименовать
   пакет, чтобы имена совпадали? Решение по умолчанию: не трогать `package.json`,
   значение `todo-api` зафиксировать в коде как требует постановка.
3. **Место константы и отдельная чистая функция.** Нужна ли функция в
   [src/todos.ts](../src/todos.ts) для константного ответа (как `healthStatus` в
   PIL-25) или достаточно константы в [src/server.ts](../src/server.ts)?
   Решение по умолчанию: константа в `src/server.ts`, `src/todos.ts` не меняется —
   ответ не зависит от модели задач, отдельная функция добавит код без проверяемого
   поведения.
4. **Уровень E2E.** Достаточно ли автоматического HTTP-теста в `test/server.test.ts`
   (по образцу существующих тестов) или нужен отдельный E2E-прогон против запущенного
   сервера — скрипт или шаг CI с `curl`? Решение по умолчанию: автоматический
   HTTP-тест в существующем файле тестов; ручной прогон собранного сервера остаётся
   частью плана проверки, отдельный E2E-скрипт и изменения CI не вводятся.
5. **Формат тела.** Требуется ли строго ровно `{"service":"todo-api"}` (один ключ) или
   допустимо расширение (например, `version` или `uptime`, как в закрытой без слияния
   PIL-15)? Решение по умолчанию: строго один ключ `service`, без дополнительных полей.
6. **Семантика метода.** Нужно ли отвечать 405 с заголовком `Allow` на не-`GET`
   методах `/info`? Решение по умолчанию: нет — остаётся существующий 404, как у всех
   маршрутов приложения.
