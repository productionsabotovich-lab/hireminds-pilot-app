# PIL-24 — Ответ на HEAD /todos

Редакция 1. Статус: спецификация подготовлена к утверждению объёма; реализация не начата.

## Цель и основания

Клиенту HTTP-API нужен дешёвый способ узнать, что ресурс списка дел доступен и какое у него
представление, без скачивания самого списка: `HEAD /todos` должен отвечать так же, как
`GET /todos`, но без тела. Конкретно — HTTP 200, те же заголовки представления, что у
`GET /todos`, и пустое тело.

Постановка требует: сохранить поведение существующего `GET` и обработки неизвестных
маршрутов, добавить HTTP-тест и описать `HEAD` в `README.md`.

Основания:

- [постановка PIL-24](/opt/hireminds/context/issue.md);
- [правила проекта](../CLAUDE.md) и [правила документов](README.md);
- [API приложения](../README.md), [HTTP-обработчик](../src/server.ts),
  [существующие HTTP-тесты](../test/server.test.ts), [чистые функции](../src/todos.ts),
  [команды и зависимости](../package.json), [CI](../.github/workflows/ci.yml);
- предыдущая спецификация [PIL-21](PIL-21.md) — формат документа, границы объёма и стиль
  проверок.

### Текущее поведение (проверено в этом окружении, Node.js v22.23.4)

- `GET /todos` → **200**, `Content-Type: application/json; charset=utf-8`,
  `Transfer-Encoding: chunked`, тело — JSON-массив дел.
- `HEAD /todos` → **404** `{"error":"not found"}`: ветка маршрута проверяет строго
  `req.method === 'GET'`, поэтому `HEAD` попадает в обработку неизвестного маршрута.
  Тело при этом не передаётся: Node.js для запроса с методом `HEAD` не пишет payload
  ответа в сокет.
- Node.js сам опускает тело ответа для `HEAD`: прототип с тем же хелпером `send` дал
  `200`, `content-type: application/json; charset=utf-8` и **0 байт** тела на уровне
  сокета, без заголовка `Transfer-Encoding` (у `GET` он есть, так как тело есть).

## Согласуемый объём

### 1. Маршрут `HEAD /todos` (`src/server.ts`)

- Обработчик добавляется в существующий `handle` в `src/server.ts`: условие маршрута
  `/todos` расширяется с `GET` на `GET` и `HEAD`. Отдельный файл-роутер, middleware и
  рефакторинг `handle` не вводятся; порядок веток `if` и ветка 404 остаются как есть.
- Ответ `HEAD /todos`:
  - HTTP **200** — тот же статус, что у `GET /todos`;
  - заголовок представления `Content-Type: application/json; charset=utf-8` — то же
    значение, что у `GET /todos` (тот же хелпер `send`);
  - **тело пустое**: 0 байт, переданных в сокет.
- Определение терминов:
  - **заголовки представления** — заголовки, описывающие представление ресурса. В этом
    API их ровно один: `Content-Type`. Значение `HEAD` совпадает со значением `GET` для
    того же URI;
  - **заголовки кадрирования и hop-by-hop** — `Transfer-Encoding`, `Content-Length`,
    `Connection`, `Keep-Alive`, `Date`. Они **не** входят в контракт: `GET /todos`
    отдаётся chunked-без `Content-Length`, а у `HEAD` тела нет, поэтому Node.js не
    выводит `Transfer-Encoding`. `Content-Length` не добавляется (вопрос 1 к PM).
- Представление считается по тем же правилам, что и у `GET /todos`, включая разбор
  `filter=open|done` (неизвестное значение → `all`). Поэтому заголовки представления
  `HEAD /todos?filter=open` совпадают с `GET /todos?filter=open`.
- Запрос только читает: состояние процесса после `HEAD /todos` не меняется — дела не
  добавляются, не меняются и не завершаются.
- **Все остальные пары «метод + путь» сохраняют текущее поведение** 404
  `{"error":"not found"}`: `HEAD /todos/stats`, `HEAD /todos/:id/complete`,
  `HEAD /неизвестный-путь`, `POST /todos/stats`, `OPTIONS /todos` и прочие. Код
  `405 Method Not Allowed` не вводится, новые методы и новые пути не появляются.
- Существующее поведение `GET /todos`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete` не меняется: прежние статусы, прежние тела ответов.
- Допустимые способы реализации (на выбор разработчика), оба обязаны давать один и тот
  же наблюдаемый контракт:
  - **(а) переиспользовать существующий хелпер `send`** — рекомендуемый вариант: Node.js
    для `HEAD` не пишет payload в сокет, поэтому `send(res, 200, listTodos(...))` даёт
    нужные заголовки и пустое тело (проверено прототипом в этом окружении);
  - **(б) отдельная ветка `HEAD`**, которая пишет те же заголовки представления и
    завершает ответ без payload (`res.end()`).
- Проверяемое требование — поведение на уровне HTTP, а не способ реализации: 200,
  совпадающий `Content-Type`, 0 байт тела.

### 2. Проверки (`test/server.test.ts`)

Кейсы добавляются в существующий файл `test/server.test.ts` отдельной группой
`describe('HEAD /todos')`. Существующие кейсы по смыслу не меняются. Новых тестовых
зависимостей нет: используются глобальный `fetch` Node.js и встроенный `node:http`.

Обязательные кейсы:

- **Статус и заголовки совпадают с `GET`**: `HEAD /todos` → 200; значение
  `content-type` равно значению `content-type` из `GET /todos` для того же URI и равно
  строке `application/json; charset=utf-8`.
- **Тело пустое**: на уровне сокета длина полученного тела равна 0 байт. Проверка
  выполняется сырым запросом из `node:http` (`request(..., { method: 'HEAD' })`):
  `fetch` для `HEAD` всегда отдаёт пустое тело и сам по себе не доказывает, что сервер
  ничего не отправил. Дополнительно проверяется, что `await res.text()` равно `''`.
- **Пустой список**: `HEAD /todos` при пустом состоянии → 200, те же заголовки
  представления, 0 байт тела.
- **Фильтр**: `HEAD /todos?filter=open` → 200, `content-type` совпадает с
  `GET /todos?filter=open`, тело пустое.
- **Запрос не меняет задачи**: `GET /todos` до и после `HEAD /todos` отдаёт одинаковый
  список; `GET /todos/stats` до и после `HEAD /todos` отдаёт одинаковые счётчики.
- **Неизвестные маршруты и методы сохраняют 404**: `HEAD /todos/stats` → 404,
  `HEAD /неизвестный-путь` → 404; существующий кейс `POST /todos/stats` → 404 остаётся.
- **Регрессия существующих маршрутов**: `GET /todos`, `GET /todos?filter=open`,
  `GET /todos?filter=done`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete` отвечают как раньше (прежние статусы и прежние тела).

## Исключения и границы

Вне объёма (не делается в этой задаче):

- `HEAD` для остальных маршрутов, в том числе `HEAD /todos/stats` и `HEAD` для
  POST-маршрутов (постановка требует только `HEAD /todos`);
- `405 Method Not Allowed` и любые другие коды вместо существующего 404;
- `Content-Length`, `ETag`, `Cache-Control`, кэширование и прочие заголовки кадрирования
  и валидации представления (вопрос 1 к PM);
- поддержка `HEAD` через отдельный сервер или middleware, рефакторинг `handle`,
  выделение роутера в отдельный модуль;
- изменения `GET /todos` и `GET /todos/stats`: формат тел и заголовков прежний;
- изменения модели `Todo`/`TodoList`, новые чистые функции в `src/todos.ts`;
- постоянное хранилище: базы данных, файлы, внешние сервисы (список, как и раньше,
  живёт в памяти процесса и сбрасывается при перезапуске);
- новые зависимости, изменения `package.json`/`package-lock.json`, `tsconfig.json`,
  `.github/**`, CI и инфраструктуры;
- обработка запросов с телом, `OPTIONS`/`TRACE` и прочих методов, WebSocket, SSE,
  сжатие ответов.

- Внешних зависимостей и сервисов нет: используются уже подключённые Node.js `>=20`
  (`node:http`, глобальный `fetch`), TypeScript и Vitest. HTTP-клиент из зависимостей не
  нужен.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным, `npm ci`
  работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check` и
  `npm test`; обе доступны без сети.
- Особенность окружения (проверено ранее в PIL-21 и подтверждено при подготовке этой
  спецификации): в окружении `NODE_ENV=production` и `npm config omit=dev`, поэтому

- В окружении отсутствует `curl`, поэтому ручные проверки выполняются Node-однострочниками
  (см. план проверки); для пользователя эквивалент — `curl -I http://127.0.0.1:3000/todos`.
- Спецификация (`docs/PIL-24.md`) включается в PR реализации.

## Вопросы к PM (не блокируют минимальный объём)

1. **`Content-Length` в ответе `HEAD`.** RFC 9110 рекомендует отдавать в ответе на
   `HEAD` те же поля, что и в ответе на `GET`, в том числе `Content-Length`. Сейчас
   `GET /todos` идёт chunked-без `Content-Length`. Нужно ли добавлять
   `Content-Length` со значением, равным длине JSON-тела `GET`? Решение по умолчанию:
   **не добавлять** — контракт задачи ограничен заголовками представления
   (`Content-Type`).
2. **`HEAD` для других маршрутов.** Нужен ли `HEAD /todos/stats` и `HEAD` для
   POST-маршрутов (например, `HEAD /todos/1/complete`)? Решение по умолчанию: **нет**,
   в объёме только `HEAD /todos`, как в постановке.
3. **`405` вместо `404`.** Нужно ли для известных путей с неподдерживаемым методом
   отвечать `405 Method Not Allowed` с заголовком `Allow`? Решение по умолчанию: **нет**,
   сохраняется существующий 404 — постановка прямо требует сохранить обработку
   неизвестных маршрутов.
4. **Кэширование.** Нужен ли `ETag` или `Cache-Control` для `HEAD /todos`?
   Решение по умолчанию: **не добавлять**, отвечать как обычный JSON-эндпоинт.
5. **Объём проверки тела.** Достаточно ли проверки через `fetch` (он для `HEAD` всегда
   показывает пустое тело) или обязательна байтовая проверка сырым запросом
   `node:http`? Решение по умолчанию: **обязательна байтовая проверка** — только она
   доказывает, что сервер не отправил байты тела.
