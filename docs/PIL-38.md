# PIL-38 — GET /healthz в тестовом API

Редакция 1 от 2026-11-19. Статус: объём утверждён (решение D-5, 2026-11-19), реализация выполнена.

## Цель и основания

Клиенту проверки доступности нужен простой HTTP-запрос, подтверждающий, что API
принимает запросы. Ответ не зависит от списка дел или внешних сервисов.

## Согласуемый контракт

- `GET /healthz` возвращает HTTP 200 и JSON ровно `{"status":"ok"}`,
  без обёртки и дополнительных полей.
- Медиа-тип — `application/json`. Допускается и используется существующий
  заголовок `application/json; charset=utf-8` из общего способа отправки JSON;
  указание кодировки не меняет требуемый медиа-тип.
- Ответ одинаков при пустом и заполненном списке, в том числе при повторных запросах.
- Обработчик не читает и не изменяет состояние списка: задачи, их порядок, поля
  и счётчик следующего идентификатора сохраняются. Внешних запросов, проверки
  базы данных, файлов или иных зависимостей нет.
- Маршрут сопоставляется по методу `GET` и точному `url.pathname === '/healthz'`.
  Query-параметры игнорируются, например `/healthz?probe=1` даёт тот же ответ.
- Другие методы на `/healthz`, в том числе `POST` и `HEAD`, а также `/healthz/`
  и `/healthz/extra` сохраняют существующий HTTP 404. Для запросов, допускающих
  тело ответа, JSON ошибки — `{"error":"not found"}`; тело для `HEAD` не требуется.
- Существующие маршруты списка, фильтров, добавления, завершения и сводки,
  а также обработка ошибок сохраняют поведение.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | Клиент проверяет доступность через `GET /healthz` | HTTP 200, JSON-медиа-тип, тело ровно `{"status":"ok"}` |
| 2 | Клиент повторяет проверку на пустом и смешанном списке | Каждый ответ соответствует сценарию 1 |
| 3 | Между операциями со списком вызывается `/healthz` | Список до и после совпадает; следующая созданная задача получает ожидаемый следующий ID |
| 4 | Клиент передаёт query-параметры | Ответ соответствует сценарию 1 |
| 5 | Клиент использует `POST /healthz` или путь `/healthz/` | HTTP 404 с существующей JSON-ошибкой |
| 6 | Клиент использует прежние маршруты | Сохраняются статусы, тела ответов, фильтрация и сводка |
| 7 | Разработчик запускает проверки | Новое поведение покрыто HTTP-тестами; существующие тесты и проверка типов проходят |
| 8 | Пользователь читает раздел API | В таблице README есть строка `GET /healthz` с HTTP 200 и `{"status":"ok"}` |
| 9 | Ревью изменений | Нет новых зависимостей и обращений к внешним сервисам |

## Границы объёма и исключения

В объём входят только маршрут в [src/server.ts](../src/server.ts), HTTP-проверки
в существующем [test/server.test.ts](../test/server.test.ts), одна строка таблицы
API в [README.md](../README.md#api) и эта спецификация `docs/PIL-38.md`.
Новая ветка обработчика использует существующий способ отправки JSON;
отдельная бизнес-функция и изменение `src/todos.ts` не нужны.

За пределами объёма: readiness-проверки зависимостей, мониторинг и метрики,
новые поля ответа (версия, uptime, время), авторизация, отдельные маршруты
для других методов, рефакторинг API, UI, настройки запуска и порта, CI,
инфраструктура, новые зависимости и изменения package/lock-файлов.
Спецификация PIL-21 и её реализация не пересматриваются.

## Зависимости

Используются текущие Node.js >=20, TypeScript, Vitest и встроенные `node:http`
и `fetch`. HTTP-тестам нужен локальный сокет на свободном порту, но внешний
сервер и доступ к сети за пределами loopback не требуются. Для запуска проверок
должны быть установлены существующие dev-зависимости.

## План проверки после реализации

1. В существующем HTTP-каркасе с изоляцией состояния и закрытием сервера
   проверить статус 200, JSON-медиа-тип и точное тело нового ответа.
2. Проверить тот же контракт на пустом и заполненном списке и при повторном
   запросе. Для заполненного списка создать два дела и завершить одно;
   сравнить `GET /todos` до и после проверки доступности. Затем создать ещё
   одно дело и проверить следующий ID — health-запрос не расходует идентификаторы.
3. Проверить игнорирование query-параметров, 404 для `POST /healthz`
   и `GET /healthz/`. Прочие неподдерживаемые методы и пути сверить с общим
   fallback обработчика при ревью; отдельная матрица тестов не нужна.
4. Выполнить `npm run check` и `npm test`, сохранив существующие регрессионные
   проверки CRUD, фильтров и `/todos/stats` без ослабления ожиданий.
5. Проверить diff: только согласованные четыре файла; строка README отражает
   контракт; новый маршрут не использует состояние, внешнее I/O или зависимости.

План выполнен в фазе Code: пункты 1–4 покрыты новыми HTTP-тестами
в `test/server.test.ts` и локальным прогоном `npm run check` и `npm test`;
пункт 5 проверен по diff и ревью.
