## Согласуемый объём и контракт

- Добавляется только `OPTIONS /todos` в существующий HTTP-обработчик.
- Ответ: HTTP **204**, заголовок **`Allow: GET, POST, OPTIONS`** с указанным
  значением и порядком методов, тело отсутствует (ноль байт, без JSON и `null`).
  Регистр имени заголовка несущественен по правилам HTTP.
- Маршрут определяется методом и точным `pathname === '/todos'` по существующему
  подходу. Query-параметры, в том числе `filter`, не влияют на ответ.
- Запрос не изменяет элементы, их порядок, `id`, `title`, `done` и следующий
  выдаваемый идентификатор. Повторный запрос даёт тот же ответ и не меняет состояние.
- Контракт одинаков для пустого и непустого списка. Состояние остаётся в памяти
  процесса с существующим жизненным циклом.
- В таблицу API README добавляется одна строка с методом, путём, кодом 204,
  отсутствием тела и значением `Allow`.
- Новое поведение проверяется HTTP-тестом в существующем `test/server.test.ts`.
  Допустимые файлы изменения после утверждения: `src/server.ts`,
  `test/server.test.ts`, `README.md` и эта спецификация.

## Пользовательские сценарии

1. Клиент отправляет `OPTIONS /todos` для пустого списка и получает 204,
   `Allow: GET, POST, OPTIONS` и пустое тело.
2. В списке есть открытые и выполненные дела. Клиент делает OPTIONS, затем
   читает список: содержимое и порядок совпадают с состоянием до запроса.
   Следующее добавленное дело получает очередной идентификатор без пропуска.
3. Клиент повторяет OPTIONS либо добавляет query-параметры: контракт ответа
   и состояние остаются прежними.

## Исключения и границы объёма

Глобальный обработчик OPTIONS, `OPTIONS *`, OPTIONS для отдельных дел и сводки,
поддержка новых методов, смена 404 на 405, CORS и заголовки `Access-Control-Allow-*`
не входят в объём. `Allow` описывает методы коллекции `/todos`, а не всего API.
Запрос с `Origin` не требует отдельного поведения или CORS-политики.

Не входят изменения бизнес-логики `src/todos.ts`, хранения, зависимостей,
конфигурации CI, контейнеров, прокси, механизма восстановления платформы,
автоматизация замены прокси и отдельная E2E-инфраструктура. Сохранность списка
означает отсутствие мутаций от OPTIONS в работающем процессе; сохранение после
перезапуска приложения не требуется. Обязательных требований к `Content-Type`
и `Content-Length` для пустого ответа не вводится.

## Зависимости и ограничения

Используются Node.js >=20, существующие TypeScript, Vitest и встроенный HTTP-клиент.
HTTP-проверка использует существующий каркас: `createServer(handle)`, свободный
локальный порт, сброс модулей для изоляции состояния, закрытие сервера после теста.
Новые библиотеки и сервисы не нужны. Правило одной ветки и одного PR в `main`
применяется к задаче целиком; чужие ветки и PR не изменяются.

## План проверки после утверждения

1. В существующем HTTP-каркасе проверить AC1 на пустом списке.
2. Создать два дела через HTTP, завершить одно, сохранить ответ `GET /todos`.
   Выполнить OPTIONS дважды, включая запрос с `filter=open`; проверить код,
   заголовок и пустое тело каждого ответа, затем сравнить список со снимком.
   Добавить третье дело и проверить следующий последовательный `id` (AC2–AC4).
3. Проверить точные границы пути из AC5 и прогнать существующие HTTP-тесты.
4. Выполнить `npm run check` и `npm test`; перед PR проверить строку README
   и отсутствие изменений за пределами согласованных файлов (AC6–AC7).
