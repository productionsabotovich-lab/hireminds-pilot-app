# PIL-74 — Показывать новые дела первыми в списке

Редакция 1. Статус: спецификация подготовлена к утверждению объёма.

## Цель и основания

Клиент HTTP-API может запросить дела от последнего созданного к первому через
`GET /todos?order=newest`, в том числе вместе с фильтром состояния.
Клиенты без нового параметра получают прежний порядок.

## Границы объёма и контракт

1. `GET /todos` принимает необязательный query-параметр `order=newest`.
   Только точное значение `newest` включает обратный порядок создания.
   При отсутствии, пустом или неизвестном значении (включая `oldest`, `NEWEST`)
   возвращается прежний порядок: от первого созданного к последнему.
   Новые ошибки валидации не вводятся. Для повторённого `order` используется
   первое значение, как при текущем чтении `filter` через `URLSearchParams.get`.
2. Режим работает с `filter=all`, `filter=open`, `filter=done` и без фильтра.
   Отсутствующий, пустой или неизвестный `filter` по-прежнему означает `all`.
   Порядок query-параметров в URL не влияет на результат.
3. «Новое» означает позже добавленное через `addTodo`, а не позже завершённое.
   Текущий массив хранит порядок создания: результат — отфильтрованные элементы
   в обратном порядке. Временные метки и новые поля модели не нужны.
   Завершение дела меняет только его принадлежность фильтру и не меняет
   его место относительно других дел по времени создания.
4. Ответ сохраняет HTTP 200, `Content-Type: application/json; charset=utf-8`
   и JSON-массив объектов `{ id, title, done }` без обёртки и дополнительных полей.
   Пустой результат — `[]`; единственный элемент возвращается без изменений.
5. Чтение не меняет состояние: порядок и содержимое `items`, `nextId` и поля дел
   сохраняются. Повторные запросы детерминированы; после `order=newest` запрос
   без `order` по-прежнему возвращает обычный порядок. Разворот массива состояния
   на месте недопустим.
6. Выбор порядка выполняется чистой логикой в `src/todos.ts`, разбор query —
   в `src/server.ts`. Существующие вызовы `listTodos` без выбора порядка сохраняют
   прежний результат; конкретную совместимую сигнатуру выбирает разработчик.
7. В разделе API `README.md` описываются параметр, порядок по умолчанию,
   совместимость с фильтрами и поведение неизвестных значений. Обязателен пример
   `curl 'http://127.0.0.1:3000/todos?filter=open&order=newest'`
   с примером JSON-ответа, где более позднее дело стоит первым.

## Пользовательские сценарии и критерии приёмки

Общая фикстура: последовательно создать A, B, C, D (id 1, 2, 3, 4),
затем завершить B и D. Ниже перечислены ожидаемые id; в реальном ответе
остаются полные объекты дел с правильными полями.

| Сценарий | Запрос | Ожидаемые id |
| --- | --- | --- |
| Последние дела сверху | `/todos?order=newest` | `[4,3,2,1]` |
| Явный полный список | `/todos?filter=all&order=newest` | `[4,3,2,1]` |
| Последние открытые | `/todos?filter=open&order=newest` | `[3,1]` |
| Последние выполненные | `/todos?filter=done&order=newest` | `[4,2]` |
| Прежний полный список | `/todos` | `[1,2,3,4]` |
| Прежние фильтры | `/todos?filter=open`, `/todos?filter=done` | `[1,3]`, `[2,4]` |
| Неизвестный фильтр | `/todos?filter=other&order=newest` | `[4,3,2,1]` |
| Неизвестный или пустой порядок | `/todos?order=other`, `/todos?order=` | `[1,2,3,4]` |

Дополнительные критерии:

- После завершения A последним запрос `filter=done&order=newest` возвращает
  `[4,2,1]`: дата завершения не влияет на порядок создания.
- После создания E запрос `order=newest` возвращает `[5,4,3,2,1]`.
- Для пустого списка, отсутствия совпадений фильтра и одного элемента режим
  возвращает корректный массив без ошибок.
- Последовательность обычный запрос → новый порядок → обычный запрос
  сохраняет первый и последний ответы одинаковыми, если между ними не было записи.
- `order=NEWEST` сохраняет обычный порядок; повторённый параметр учитывается
  по первому значению (`order=newest&order=other` включает новый режим,
  обратная последовательность — обычный).

## Исключения и зависимости

Вне объёма: UI, переключатель режима и сохранение пользовательских настроек,
другие виды сортировки, пагинация, даты создания, изменение хранения данных,
новые маршруты, рефакторинг инфраструктуры и новые зависимости.
Контракты добавления и завершения дел, ошибки маршрутов и статистика сохраняются.
`GET /todos/stats?order=newest` по-прежнему игнорирует query-параметры.
Состояние остаётся в памяти процесса; восстановление порядка после перезапуска
и сортировка произвольных внешних данных не входят в задачу.

Достаточно текущих Node.js >=20, TypeScript и Vitest. Внешних сервисов,
изменений схемы данных и дополнительных продуктовых решений не требуется.
Ожидаемые файлы реализации: `src/todos.ts`, `src/server.ts`,
`test/todos.test.ts`, `test/server.test.ts`, `README.md` и эта спецификация.

## План проверки после утверждения

- В `test/todos.test.ts` проверить новый и обычный порядок для всех фильтров,
  пустой результат, один элемент, независимость от завершения и отсутствие мутаций
  массива и элементов (в том числе при замороженном входном массиве).
- В существующем HTTP-каркасе `test/server.test.ts` создать дела запросами POST
  и проверить таблицу сценариев, новые добавления, повторные чтения, заголовок,
  статус и полные объекты ответа. Проверить неизвестные, пустые, повторённые
  параметры и регистр; проверить независимость от порядка query-параметров.
- Проверить, что запрос сортировки не меняет последующий обычный список и
  статистику; сохранить успешность существующих тестов маршрутов.
- Выполнить `npm run check` и `npm test` перед PR, как требуют правила проекта.
  Новое поведение покрывается автоматическими тестами обоих уровней.
- Сверить документацию API с контрактом и примером ответа; проверить,
  что diff ограничен согласованным объёмом и не добавляет зависимости.
