# PIL-48 — E2E обрыва связи · HEAD для TODO API

Редакция 1. Статус: спецификация подготовлена, объём не утверждён; реализация не начата.

## Цель и основания

Задача — контрольный (E2E) прогон Hireminds с перезапуском worker во время этапа Spec.
Проверяется, что сессия продолжается после обрыва связи и приводит к ожидаемому
материальному результату в тестовом репозитории TODO API.

Материальный результат задачи — рабочий маршрут `HEAD /todos` в тестовом приложении:

- HTTP **200**;
- те же заголовки представления, что у `GET /todos`
  (`Content-Type: application/json; charset=utf-8`);
- **пустое тело** (0 байт на уровне сокета);
- состояние списка дел не меняется;
- HTTP-тест в `test/` и краткая строка про `HEAD /todos` в `README.md`.

Постановка требует именно этого: после согласования спецификации добавить `HEAD /todos`,
покрыть HTTP-поведение тестом и описать маршрут в README. Никаких других функциональных
изменений не требуется.

Отличие PIL-48 от родственной постановки [PIL-24](https://github.com/productionsabotovich-lab/hireminds-pilot-app/blob/hm/PIL-24-head-todos/docs/PIL-24.md)
(та же функциональность, спецификация без реализации): в PIL-48 маршрут должен быть
**реализован** в рамках контрольного прогона, а сама спецификация должна быть
самодостаточной — её достаточно для продолжения работы после обрыва связи, без
зависимости от контекста сессии (см. раздел 4).

### Текущее поведение (проверено в этом окружении, Node.js v22.23.4)

Проверено на собранном сервере из `main` (`npm run build && npm start`) и на прототипе
с тем же хелпером `send`:

- `GET /todos` → **200**, `Content-Type: application/json; charset=utf-8`,
  `Transfer-Encoding: chunked`, тело — JSON-массив дел;
- `HEAD /todos` → **404** `{"error":"not found"}`: ветка маршрута проверяет строго
  `req.method === 'GET'`, поэтому `HEAD` попадает в обработку неизвестного маршрута;
- `HEAD /todos/stats` → **404** `{"error":"not found"}`;
- Node.js не пишет payload ответа в сокет для запроса с методом `HEAD`: прототип с тем
  же хелпером `send` дал **200**, `content-type: application/json; charset=utf-8` и
  **0 байт** тела (у `GET` в этом случае есть `Transfer-Encoding: chunked`);
- обрыв клиентского соединения (запрос `POST /todos` с оборванным телом) не роняет
  сервер: после обрыва сервер продолжает отвечать (`GET /todos` → 200, `POST /todos` →
  201), оборванный запрос не добавляет дело и не расходует идентификатор.

## Согласуемый объём

### 1. Маршрут `HEAD /todos` (`src/server.ts`)

- Обработчик добавляется в существующий `handle` в `src/server.ts`: условие маршрута
  `/todos` расширяется с `GET` на `GET` и `HEAD`. Отдельный файл-роутер, middleware и
  рефакторинг `handle` не вводятся; порядок веток `if` и ветка 404 остаются как есть.
- Ответ `HEAD /todos`:
  - HTTP **200** — тот же статус, что у `GET /todos`;
  - заголовок представления `Content-Type: application/json; charset=utf-8` — то же
    значение, что у `GET /todos` (тот же хелпер `send`);
  - **тело пустое**: 0 байт, переданных в сокет.
- Определение терминов:
  - **заголовки представления** — заголовки, описывающие представление ресурса. В этом
    API их ровно один: `Content-Type`. Значение `HEAD` совпадает со значением `GET` для
    того же URI;
  - **заголовки кадрирования и hop-by-hop** — `Transfer-Encoding`, `Content-Length`,
    `Connection`, `Keep-Alive`, `Date`. Они **не** входят в контракт: `GET /todos`
    отдаётся chunked-без `Content-Length`, а у `HEAD` тела нет, поэтому Node.js не
    выводит `Transfer-Encoding`. `Content-Length` не добавляется (вопрос 2 к PM).
- Представление считается по тем же правилам, что и у `GET /todos`, включая разбор
  `filter=open|done` (неизвестное значение → `all`). Поэтому заголовки представления
  `HEAD /todos?filter=open` совпадают с `GET /todos?filter=open`.
- Запрос только читает: состояние процесса после `HEAD /todos` не меняется — дела не
  добавляются, не меняются и не завершаются; следующий выданный идентификатор не
  расходуется.
- **Все остальные пары «метод + путь» сохраняют текущее поведение** 404
  `{"error":"not found"}`: `HEAD /todos/stats`, `HEAD /todos/:id/complete`,
  `HEAD /неизвестный-путь`, `POST /todos/stats`, `OPTIONS /todos` и прочие. Код
  `405 Method Not Allowed` не вводится, новые методы и новые пути не появляются.
- Существующее поведение `GET /todos`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete` не меняется: прежние статусы, прежние тела ответов.
- Допустимые способы реализации (на выбор разработчика), оба обязаны давать один и тот
  же наблюдаемый контракт:
  - **(а) переиспользовать существующий хелпер `send`** — рекомендуемый вариант: Node.js
    для `HEAD` не пишет payload в сокет, поэтому `send(res, 200, listTodos(...))` даёт
    нужные заголовки и пустое тело (проверено прототипом в этом окружении);
  - **(б) отдельная ветка `HEAD`**, которая пишет те же заголовки представления и
    завершает ответ без payload (`res.end()`).
- Проверяемое требование — поведение на уровне HTTP, а не способ реализации: 200,
  совпадающий `Content-Type`, 0 байт тела.
- `src/todos.ts` **не меняется**: новая доменная логика не нужна, `HEAD` переиспользует
  существующий `listTodos`.

### 2. Проверки (`test/server.test.ts`)

Кейсы добавляются в существующий файл `test/server.test.ts` отдельной группой
`describe('HEAD /todos')`. Существующие кейсы по смыслу не меняются. Новых тестовых
зависимостей нет: используются глобальный `fetch` Node.js и встроенный `node:http`.

Обязательные кейсы:

- **Статус и заголовки совпадают с `GET`**: `HEAD /todos` → 200; значение `content-type`
  равно значению `content-type` из `GET /todos` для того же URI и равно строке
  `application/json; charset=utf-8`.
- **Тело пустое**: на уровне сокета длина полученного тела равна 0 байт. Проверка
  выполняется сырым запросом из `node:http` (`request(..., { method: 'HEAD' })`):
  `fetch` для `HEAD` всегда отдаёт пустое тело и сам по себе не доказывает, что сервер
  ничего не отправил. Дополнительно проверяется, что `await res.text()` равно `''`.
- **Пустой список**: `HEAD /todos` при пустом состоянии → 200, те же заголовки
  представления, 0 байт тела.
- **Фильтр**: `HEAD /todos?filter=open` → 200, `content-type` совпадает с
  `GET /todos?filter=open`, тело пустое.
- **Запрос не меняет задачи**: `GET /todos` до и после `HEAD /todos` отдаёт одинаковый
  список; `GET /todos/stats` до и после — одинаковые счётчики; следующий `POST /todos`
  получает следующий последовательный идентификатор (оборванный/повторный `HEAD`
  идентификатор не расходует).
- **Неизвестные маршруты и методы сохраняют 404**: `HEAD /todos/stats` → 404,
  `HEAD /неизвестный-путь` → 404; существующий кейс `POST /todos/stats` → 404 остаётся.
- **Регрессия существующих маршрутов**: `GET /todos`, `GET /todos?filter=open`,
  `GET /todos?filter=done`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete` отвечают как раньше (прежние статусы и прежние тела).

Проверка «сервер переживает обрыв клиентского соединения» (E2E-аспект «обрыва связи»)
в обязательный объём **не входит**: поведение уже устойчиво и контракт задачи его не
меняет. Решение по умолчанию — не добавлять (вопрос 4 к PM).

## Исключения и границы

Вне объёма (не делается в этой задаче):

- `HEAD` для остальных маршрутов, в том числе `HEAD /todos/stats` и `HEAD` для
  POST-маршрутов (постановка требует только `HEAD /todos`);
- `405 Method Not Allowed` и любые другие коды вместо существующего 404;
- `Content-Length`, `ETag`, `Cache-Control`, кэширование и прочие заголовки кадрирования
  и валидации представления (вопросы 2 и 6 к PM);
- обработка обрыва клиентского соединения как отдельная функциональность: специальные
  обработчики `aborted`/`close`, таймауты, ретраи, коды ошибок соединения — текущее
  поведение (сервер переживает обрыв и продолжает работать) сохраняется;
- поддержка `HEAD` через отдельный сервер или middleware, рефакторинг `handle`,
  выделение роутера в отдельный модуль;
- изменения `GET /todos` и `GET /todos/stats`: формат тел и заголовков прежний;
- изменения модели `Todo`/`TodoList`, новые чистые функции в `src/todos.ts`;
- постоянное хранилище: базы данных, файлы, внешние сервисы (список, как и раньше,
  живёт в памяти процесса и сбрасывается при перезапуске);
- новые зависимости, изменения `package.json`/`package-lock.json`, `tsconfig.json`,
  `.github/**`, CI и инфраструктуры;
- обработка запросов с телом, `OPTIONS`/`TRACE` и прочих методов, WebSocket, SSE,
  сжатие ответов;
- сама платформенная часть контрольного прогона (перезапуск worker, оркестрация
  сессии Hireminds) — она не относится к приложению; материальный результат задачи —
  маршрут, тест и строка README;
- чужие задачи, ветки и PR (PIL-24, PIL-21, PIL-33, PIL-40, PIL-43, PIL-44 и серия
  PIL-24xxx) не трогаются.

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые Node.js `>=20`
  (`node:http`, глобальный `fetch`), TypeScript и Vitest. HTTP-клиент из зависимостей
  не нужен.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным,
  `npm ci` работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check` и
  `npm test`; обе доступны без сети.
- Особенность окружения (проверено): в текущем окружении `NODE_ENV=production` и
  `npm config omit=dev`, поэтому обычный `npm ci` **не ставит** dev-зависимости;
  для `npm run check` и `npm test` нужен `npm ci --include=dev`. На содержимое
  репозитория это не влияет.
- Особенность проекта: `tsconfig.json` включает только `src`, поэтому файлы в `test/`
  **не** проверяются командой `npm run check` — типы тестов проверяются только вручную
  или в IDE. Сборка `npm run build` тоже затрагивает только `src`.
- В окружении отсутствует `curl`, поэтому ручные проверки выполняются Node-однострочниками
  (см. план проверки); для пользователя эквивалент — `curl -I http://127.0.0.1:3000/todos`.
- Базовая проверка на текущем `main` пройдена: `npm run check` — без ошибок,
  `npm test` — 21 тест в двух файлах, все зелёные.
- Спецификация (`docs/PIL-48.md`) включается в PR реализации.

## План проверки

1. `npm ci --include=dev` (в окружении с `omit=dev`) — зависимости установлены.
2. `npm run check` — проверка типов проходит без ошибок (изменения касаются
   `src/server.ts`).
3. `npm test` — все тесты vitest проходят; видна новая группа кейсов `HEAD /todos`,
   существующие 21 кейс по смыслу не меняются.
4. Ручная проверка на собранном сервере: `npm run build && npm start`, затем:
   - заголовки, статус и тело:
     `node --input-type=module -e "const r = await fetch('http://127.0.0.1:3000/todos', { method: 'HEAD' }); console.log(r.status, r.headers.get('content-type'), JSON.stringify(await r.text()))"`
     → ожидается `200 application/json; charset=utf-8 ""`;
   - размер тела на уровне сокета:
     `node --input-type=module -e "import { request } from 'node:http'; request({ host: '127.0.0.1', port: 3000, path: '/todos', method: 'HEAD' }, (res) => { const c = []; res.on('data', (d) => c.push(d)); res.on('end', () => console.log(res.statusCode, res.headers['content-type'], Buffer.concat(c).length)); }).end();"`
     → ожидается `200 application/json; charset=utf-8 0`;
   - `HEAD /todos?filter=open` → 200 и те же заголовки; `HEAD /todos/stats` → 404;
     `GET /todos` → 200 и список дел; `POST /todos {"title":"a"}` → 201.
5. Проверка, что состояние не меняется: `GET /todos` и `GET /todos/stats` до и после
   `HEAD /todos` отдают то же самое; следующий `POST /todos` получает следующий
   последовательный `id`; существующие маршруты `GET /todos?filter=open|done`,

## Вопросы к PM (не блокируют минимальный объём)

1. **Дубликат PIL-24.** Спецификация `HEAD /todos` уже подготовлена в ветке
   `hm/PIL-24-head-todos` (реализации нет). Считать ли PIL-48 самостоятельной задачей и
   реализовать маршрут в рамках неё? Решение по умолчанию: **да** — PIL-48 реализует
   `HEAD /todos` самостоятельно, ветка и задача PIL-24 не трогаются.
2. **`Content-Length` в ответе `HEAD`.** RFC 9110 рекомендует отдавать в ответе на
   `HEAD` те же поля, что и в ответе на `GET`, в том числе `Content-Length`. Сейчас
   `GET /todos` идёт chunked-без `Content-Length`. Добавлять ли `Content-Length` со
   значением, равным длине JSON-тела `GET`? Решение по умолчанию: **не добавлять** —
   контракт задачи ограничен заголовками представления (`Content-Type`).
3. **`HEAD` для других маршрутов.** Нужен ли `HEAD /todos/stats` и `HEAD` для
   POST-маршрутов (например, `HEAD /todos/1/complete`)? Решение по умолчанию: **нет**,
   в объёме только `HEAD /todos`, как в постановке.
4. **Регресс-тест на обрыв соединения.** Стоит ли добавить в `test/server.test.ts`
   отдельный кейс «сервер переживает обрыв клиентского соединения», чтобы зафиксировать
   E2E-аспект «обрыва связи» в репозитории? Решение по умолчанию: **нет** — поведение
   не меняется и уже устойчиво (проверено), контракт задачи — `HEAD /todos`.
5. **`405` вместо `404`.** Нужен ли для известных путей с неподдерживаемым методом ответ
   `405 Method Not Allowed` с заголовком `Allow`? Решение по умолчанию: **нет**,
   сохраняется существующий 404 — постановка прямо требует сохранить обработку
   неизвестных маршрутов.
6. **Строгость «тех же заголовков».** «Те же заголовки ответа, что у `GET /todos`» —
   совпадать должен весь набор заголовков (включая `Transfer-Encoding`/`Content-Length`)
   или только `Content-Type`? Решение по умолчанию: **только `Content-Type`**
   (заголовки представления); разница в кадрирующих заголовках — нормальное поведение
   HTTP для `HEAD`.
7. **Кэширование.** Нужен ли `ETag` или `Cache-Control` для `HEAD /todos`?
   Решение по умолчанию: **не добавлять**, отвечать как обычный JSON-эндпоинт.
