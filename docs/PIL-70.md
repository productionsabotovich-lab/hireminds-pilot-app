# PIL-70 — Экспорт статистики задач в TSV

Редакция 1 от 2026-11-25. Статус: объём утверждён, оба круга выпуска выполнены.
Итоговый формат — тело с ровно одним завершающим LF после строки счётчиков.

## Цель и основания

Потребитель HTTP API импортирует три счётчика текущего списка дел в таблицу
или построчный загрузчик, не преобразуя JSON самостоятельно.

## Согласуемый объём

Добавить только экспорт `GET /todos/stats.tsv`, его HTTP-проверки и описание в
`README.md`. Использовать существующий `todoStats(state)` как источник счётчиков;
повторная независимая логика подсчёта не нужна. HTTP I/O остаётся в `src/server.ts`.

### Контракт HTTP и данных

- Успех: статус 200, `Content-Type: text/tab-separated-values; charset=utf-8`.
- Тело — UTF-8 без BOM, две логические строки и ровно три колонки в каждой.
- Первая строка строго `total\topen\tdone`, вторая — значения этих счётчиков
  в том же порядке. Здесь и далее `\t` обозначает байт табуляции, `\n` — LF.
- Значения — неотрицательные десятичные целые без пробелов, кавычек,
  разделителей разрядов и локализованного форматирования; `total = open + done`.
- Разделитель строк — один LF, не CRLF. Строка счётчиков завершается ровно
  одним финальным LF; пустой логической строки после данных нет. Нет
  дополнительных колонок, строк, метаданных или JSON-обёртки.
- Счётчики совпадают с `GET /todos/stats` при одном и том же состоянии списка.
  Между отдельными запросами состояние может измениться: согласованный снимок
  для нескольких HTTP-запросов не вводится.
- Как у JSON-статистики, все query-параметры, включая `filter`, игнорируются:
  экспорт всегда относится ко всему списку.
- Запрос только читает состояние. Повторный запрос при неизменном списке
  возвращает то же тело. Существующий JSON API сохраняет форматы и статусы.
- Путь сопоставляется точно. Для `/todos/stats.tsv/`, неизвестных путей и
  методов кроме GET сохраняется существующий 404 с JSON `{"error":"not found"}`.
  Специальная поддержка HEAD и согласование формата через Accept не добавляются.

### Два круга выпуска — обязательная часть объёма

Это порядок реализации и QA внутри одного PR, а не отдельные задачи.

1. Первая реализация отдаёт тело **без завершающего перевода строки**:
   пустой список — `total\topen\tdone\n0\t0\t0`, смешанный —
   `total\topen\tdone\n3\t2\t1`. Первый QA проверяет этот промежуточный контракт
   и возвращает разработчику замечание: добавить один финальный LF для
   построчного загрузчика и закрепить это отдельной проверкой точного тела.
2. Во втором круге разработчик в том же PR добавляет ровно один финальный LF.
   Итоговые тела: `total\topen\tdone\n0\t0\t0\n` и
   `total\topen\tdone\n3\t2\t1\n`. QA проверяет исправление, отдельную
   регрессионную проверку точного тела и зелёный CI на последнем SHA.

Первая реализация без LF является намеренно промежуточной и не удовлетворяет
итоговой приёмке. Финальный LF завершает строку чисел, не добавляя третью
логическую строку. Проверки первого круга, если они фиксировали отсутствие LF,
во втором круге приводятся к итоговому контракту; противоречащие тесты не оставляются.

## Сценарии и критерии приёмки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Импорт пустого списка | 200, TSV Content-Type с UTF-8; точное тело по соответствующему кругу с числами `0\t0\t0` |
| Импорт трёх дел, одно выполнено | Счётчики `3\t2\t1`, совпадающие с JSON-статистикой; порядок заголовков и колонок фиксирован |
| Добавление или завершение дела перед экспортом | Следующий экспорт отражает текущее состояние, без кэша старых счётчиков |
| Повторное чтение экспорта | Тело не меняется без изменения списка; `GET /todos` до и после даёт одинаковый список |
| Экспорт с `?filter=open` или неизвестным параметром | Тот же общий результат, что без параметров |
| POST на маршрут или GET с завершающим слешем | Прежний JSON 404 |
| Чтение JSON-статистики и работа со списком | Существующие ответы и операции сохраняются |
| Итоговый построчный импорт | Строка чисел завершается ровно одним LF; точное тело проверено отдельно, без trim или нормализации переводов строк |
| Завершение выпуска | Пройдены оба круга в одном PR; обязательные локальные проверки и CI последнего SHA зелёные |

## Исключения и ограничения

Вне объёма: выгрузка самих задач, CSV/XLSX, UI, загрузка файла в сторонние
таблицы, выбор разделителя, локализация, фильтрация статистики, новые счётчики,
авторизация, постоянное хранилище, кэширование и рефакторинг существующих маршрутов.
Специальные заголовки скачивания и интеграция с конкретным табличным продуктом
не требуются. Заголовки и числа не содержат пользовательских строк, поэтому
экранирование названий задач в TSV не требуется.

Ожидаемые изменения после утверждения: `src/server.ts`, `test/server.test.ts`,
`README.md` и эта спецификация. Изменение `src/todos.ts` не требуется: чистая
логика уже существует. Новые зависимости, изменения модели, конфигурации,
lock-файла и CI не входят в объём. Основная ветка не меняется; реализация ведётся
в отдельной ветке и одном PR в `main` согласно правилам проекта.

## План проверки после утверждения

1. Расширить существующие HTTP-проверки с изоляцией состояния. Для пустого и
   смешанного списков проверить 200, Content-Type, точное тело соответствующего
   круга и равенство значений JSON-статистике при неизменном состоянии.
2. Проверить обновление счётчиков после добавления и завершения задачи,
   отсутствие мутаций при экспорте, повторяемость ответа, игнорирование query,
   точность пути и прежний 404 для POST. Существующие регрессионные тесты API
   остаются обязательными.
3. Первый QA подтверждает промежуточный формат и оформляет указанное выше
   замечание о финальном LF. Этот круг не заменяет итоговую приёмку.
4. Во втором круге добавить отдельный HTTP-тест точного тела с единственным
   финальным LF. Сравнение полной строки (без trim/split-нормализации) должно
   отклонять отсутствие LF, двойной LF, CRLF, BOM, лишние пробелы и колонки.
5. Перед отправкой изменений каждого круга выполнить `npm run check` и `npm test`.
   После каждого нового SHA дождаться GitHub Actions; итоговый QA проверяет
   зелёные проверки именно последнего SHA того же PR.
6. Проверить diff на соблюдение границ объёма и описание нового маршрута в
   README: кодировка, колонки и окончательный LF должны соответствовать контракту.

## Граница текущей фазы

Реализованы оба круга выпуска в ветке задачи: маршрут `GET /todos/stats.tsv`
(`src/server.ts`), HTTP-проверки (`test/server.test.ts`) и описание маршрута
(`README.md`). Итоговое тело — `total\topen\tdone\n<total>\t<open>\t<done>\n`:
строка счётчиков завершается ровно одним LF, третья логическая строка не
добавляется. Отдельная проверка точного тела для табличного импорта сравнивает
полную строку без trim и нормализации переводов строк. Второй круг выполнен
тем же pull request после замечания QA; итоговая приёмка — за ролью QA.
