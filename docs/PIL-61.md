## Согласуемый объём и контракт

Автоматические проверки добавляются в `test/server.test.ts`, пример — в раздел API
корневого `README.md`. Код приложения уже реализует требуемое поведение;
его изменение для этой задачи не требуется. Спецификация хранится в `docs/PIL-61.md`.

Пустой заголовок — строка, для которой результат JavaScript `trim()` имеет длину ноль.
Обязательные HTTP-варианты: `""`, `"   "`, `" \t\n "` (в JSON управляющие символы
экранируются). Для каждого варианта:

- запрос: `POST /todos`, `Content-Type: application/json`, тело `{ "title": ... }`;
- ответ: статус `400`, `Content-Type: application/json; charset=utf-8`;
- JSON ответа ровно `{ "error": "title is empty" }`;
- дело не создаётся, существующие дела не изменяются, идентификатор не расходуется.

Корректный заголовок продолжает обрезаться по краям; ответ `201` содержит ровно
`{ "id": N, "title": "...", "done": false }`. Нумерация последовательная.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий клиента | Проверяемый результат |
| --- | --- | --- |
| 1 | Отправить заголовок `""` | 400, указанные JSON и Content-Type |
| 2 | Отправить заголовок из пробелов | Тот же ответ 400 |
| 3 | Отправить смесь пробелов, табуляции и перевода строки | Тот же ответ 400 |
| 4 | В пустом списке отправить невалидный запрос, затем корректный | Список после отказа пуст; корректный запрос создаёт дело с id 1 |
| 5 | Создать дело, отправить невалидный запрос, прочитать список и создать ещё одно дело | Список после отказа точно совпадает с исходным; следующее дело получает следующий id без пропуска |
| 6 | Отправить `{ "title": " Купить хлеб " }` | 201, `{ "id": N, "title": "Купить хлеб", "done": false }`; дело доступно через GET /todos |
| 7 | Открыть README и выполнить пример | Указаны метод, путь, JSON, заголовок запроса, ожидаемые 400 и тело ошибки |

HTTP-проверки выполняются через реальный локальный HTTP-сервер с экспортируемым `handle`,
а не прямым вызовом `addTodo` или подменой HTTP-ответа. Используется существующий
каркас тестов: свободный порт, Node.js fetch, изоляция состояния между кейсами,
закрытие соединений и сервера после каждого кейса.

В README приводится воспроизводимый запрос к запущенному локальному серверу:

```sh
curl -i -X POST http://127.0.0.1:3000/todos \
  -H 'Content-Type: application/json' \
  -d '{"title":""}'
```

Рядом указываются ожидаемый статус `400 Bad Request` и JSON
`{"error":"title is empty"}`, а также то, что строка из одних пробельных символов
считается пустой. Динамические заголовки вроде Date фиксировать не нужно.

## Исключения и границы

- Отсутствующий `title`, `null`, нестроковые значения, неверный JSON и пустое тело
  запроса не получают нового контракта и не входят в обязательную матрицу этой задачи.
- Не вводятся обязательность строкового типа, ограничения длины, новая схема ошибок,
  новые маршруты, авторизация, хранение данных или дополнительные зависимости.
- Существующие маршруты, фильтры и статистика сохраняют поведение.
- Ожидаемые изменения после утверждения: `test/server.test.ts`, `README.md`,
  `docs/PIL-61.md`. Переписывание HTTP-каркаса, production-кода, CI и зависимостей
  в согласуемый объём не входит.

## Зависимости и ограничения

Нужны Node.js >=20 и существующие dev-зависимости из lock-файла. Внешние сервисы,
браузер, учётные записи и новые пакеты не требуются. Состояние хранится в памяти;
каждый независимый HTTP-кейс начинает с нового экземпляра модуля сервера.
Сохраняется разделение чистой логики и I/O из правил проекта.

## План проверки после утверждения

1. Запустить обязательные `npm run check` и `npm test`; весь существующий набор
   и новые HTTP-сценарии должны проходить.
2. Проверить, что новые тесты проверяют статус, Content-Type и полное JSON-тело,
   отсутствие изменений списка и пропуска id, успешный запрос после отказа.
3. Собрать и запустить сервер штатными командами из README; выполнить приведённый
   curl-пример и сопоставить статус и тело с документацией.
4. Проверить diff: только согласованные файлы, без изменения существующих контрактов,
   зависимостей и конфигурации.

В фазе спецификации проверки реализации не выполняются и не заявляются пройденными.
