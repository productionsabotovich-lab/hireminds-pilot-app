## Согласуемый объём и контракт

Автоматические проверки добавляются в `test/server.test.ts`, пример — в раздел API
корневого `README.md`. Код приложения уже реализует требуемое поведение;
его изменение для этой задачи не требуется. Спецификация хранится в `docs/PIL-61.md`.

Пустой заголовок — строка, для которой результат JavaScript `trim()` имеет длину ноль.
Обязательные HTTP-варианты: `""`, `"   "`, `" \t\n "` (в JSON управляющие символы
экранируются). Для каждого варианта:

- запрос: `POST /todos`, `Content-Type: application/json`, тело `{ "title": ... }`;
- ответ: статус `400`, `Content-Type: application/json; charset=utf-8`;
- JSON ответа ровно `{ "error": "title is empty" }`;
- дело не создаётся, существующие дела не изменяются, идентификатор не расходуется.

Корректный заголовок продолжает обрезаться по краям; ответ `201` содержит ровно
`{ "id": N, "title": "...", "done": false }`. Нумерация последовательная.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий клиента | Проверяемый результат |
| --- | --- | --- |
| 1 | Отправить заголовок `""` | 400, указанные JSON и Content-Type |
| 2 | Отправить заголовок из пробелов | Тот же ответ 400 |
| 3 | Отправить смесь пробелов, табуляции и перевода строки | Тот же ответ 400 |
| 4 | В пустом списке отправить невалидный запрос, затем корректный | Список после отказа пуст; корректный запрос создаёт дело с id 1 |
| 5 | Создать дело, отправить невалидный запрос, прочитать список и создать ещё одно дело | Список после отказа точно совпадает с исходным; следующее дело получает следующий id без пропуска |
| 6 | Отправить `{ "title": " Купить хлеб " }` | 201, `{ "id": N, "title": "Купить хлеб", "done": false }`; дело доступно через GET /todos |
| 7 | Открыть README и выполнить пример | Указаны метод, путь, JSON, заголовок запроса, ожидаемые 400 и тело ошибки |

HTTP-проверки выполняются через реальный локальный HTTP-сервер с экспортируемым `handle`,
а не прямым вызовом `addTodo` или подменой HTTP-ответа. Используется существующий
каркас тестов: свободный порт, Node.js fetch, изоляция состояния между кейсами,
закрытие соединений и сервера после каждого кейса.

В README приводится воспроизводимый запрос к запущенному локальному серверу:

```sh
curl -i -X POST http://127.0.0.1:3000/todos \
  -H 'Content-Type: application/json' \
  -d '{"title":""}'
```

Рядом указываются ожидаемый статус `400 Bad Request` и JSON
`{"error":"title is empty"}`, а также то, что строка из одних пробельных символов
считается пустой. Динамические заголовки вроде Date фиксировать не нужно.

## Исключения и границы

- Отсутствующий `title`, `null`, нестроковые значения, неверный JSON и пустое тело
  запроса не получают нового контракта и не входят в обязательную матрицу этой задачи.
- Не вводятся обязательность строкового типа, ограничения длины, новая схема ошибок,
  новые маршруты, авторизация, хранение данных или дополнительные зависимости.
- Существующие маршруты, фильтры и статистика сохраняют поведение.
- Фактические изменения: `test/server.test.ts`, `README.md`, `docs/PIL-61.md`.
  Переписывание HTTP-каркаса, production-кода, CI и зависимостей в согласуемый объём
  не входит.

## Зависимости и ограничения

Нужны Node.js >=20 и существующие dev-зависимости из lock-файла. Внешние сервисы,
браузер, учётные записи и новые пакеты не требуются. Состояние хранится в памяти;
каждый независимый HTTP-кейс начинает с нового экземпляра модуля сервера.
Сохраняется разделение чистой логики и I/O из правил проекта.

## Реализация

Объём редакции 2 реализован в согласованных границах: `src/server.ts` и
`src/todos.ts` не менялись, контракт уже существовал.

- [Группа HTTP-проверок](../test/server.test.ts#L149) `POST /todos with an empty title`
  добавлена в существующую группу `server routes` и наследует её `beforeEach` и
  `afterEach`: сброс реестра модулей, динамический импорт `../src/server.js`, новый
  сервер на свободном порту `0`, закрытие соединений и сервера после кейса. Каждый
  кейс стартует с нового экземпляра модуля, поэтому состояние между кейсами не
  протекает.
- [Матрица пустых заголовков](../test/server.test.ts#L156) — `it.each` по трём
  обязательным вариантам: пустая строка, только пробелы, смесь пробелов, табуляции и
  перевода строки. Для каждого ответа проверяются статус `400`, точный Content-Type
  `application/json; charset=utf-8` и полное тело `{"error":"title is empty"}`; тело
  читается один раз, точное сравнение текста отличает нужный JSON от пустого тела и
  от другой схемы ошибок.
- [Пустой список после отказа](../test/server.test.ts#L164) — отказ на пустом
  хранилище не создаёт дело, `GET /todos` отвечает пустым массивом, а следующий
  корректный запрос получает id 1: идентификатор не расходуется.
- [Список и нумерация после отказа](../test/server.test.ts#L177) — сначала создаётся
  дело, затем отказ; тело списка до и после отказа совпадает посимвольно, а следующее
  дело получает id 2 без пропуска.
- [Корректный заголовок](../test/server.test.ts#L193) — `201`, обрезка пробелов по
  краям, тело `{ "id": 1, "title": "Купить хлеб", "done": false }` и наличие дела в
  `GET /todos`.
- [Пример в README](../README.md#L38) — запрос `curl -i -X POST .../todos` с
  заголовком `Content-Type: application/json` и телом `{"title":""}`, ожидаемый ответ
  `400 Bad Request`, точный Content-Type и тело `{"error":"title is empty"}`; указано,
  что пробельная строка считается пустой, дело не создаётся и идентификатор не
  расходуется. Рядом добавлен пример корректного запроса с обрезкой пробелов и
  ответом `201 Created`.

## Проверка после реализации

1. Выполнены `npm run check` и `npm test`: ошибок типов нет, все 27 тестов проходят
   (22 существующих и 5 новых). Существующие проверки не ослаблены.
2. Проверка на мутации выполнена дважды, изменения отменены, `src/` не тронут:
   - при замене текста ошибки `title is empty` на `title required` новые HTTP-кейсы
     падают с `expected '{"error":"title required"}' to be '{"error":"title is empty"}'`;
   - при отключении обрезки пробелов (`const trimmed = title;`) падают кейсы с пробельными
     заголовками и кейс обрезки ` Купить хлеб `.
3. Приложение собрано (`npm run build`) и запущено штатными командами README; на
   запущенном процессе выполнены запросы `POST /todos` с пустым заголовком, с
   пробелами и со смесью пробельных символов: каждый раз `HTTP/1.1 400 Bad Request`,
   `Content-Type: application/json; charset=utf-8`, тело `{"error":"title is empty"}`.
   Корректный запрос `{"title":" Купить хлеб "}` дал `HTTP/1.1 201 Created` и тело
   `{"id":1,"title":"Купить хлеб","done":false}`; `GET /todos` содержал одно дело —
   отказы не изменили список и не израсходовали идентификатор. Ответ совпадает с
   примером в README.
4. Проверен diff: изменены только согласованные файлы (`test/server.test.ts`,
   `README.md`, `docs/PIL-61.md`), без изменения production-кода, существующих
   контрактов, зависимостей и конфигурации.
