# PIL-37 — Получить одну задачу по идентификатору

Редакция 1. Статус: спецификация подготовлена к утверждению объёма; реализация не начата.

## Цель и основания

Клиенту HTTP-API нужно прочитать одно дело по его идентификатору: `GET /todos/:id`.
Постановка требует:

- для существующего положительного целого ID — HTTP **200** и JSON соответствующего TODO
  **в том же формате, что `GET /todos`**;
- для неизвестного ID и для некорректного пути — существующий JSON-ответ **404**;
- чтение ничего не меняет;
- остальные маршруты работают как раньше;
- добавлены HTTP-тесты успешного ответа и 404;
- обновлено короткое описание API (`README.md`);
- новых зависимостей нет.

Название «E2E» не расширяет задачу за пределы HTTP-маршрута приложения и его
автоматических проверок: полный цикл платформы Hireminds, отдельный E2E-фреймворк
и стенд в объём не входят.

## Текущее поведение (проверено в этом окружении, Node.js v22.23.4)

Проверено на собранном сервере (`npm run build && node dist/server.js`, порт 3311):

| Запрос | Ответ сейчас |
| --- | --- |
| `GET /todos/1` | **404** `{"error":"not found"}` |
| `GET /todos/007` | **404** `{"error":"not found"}` |
| `GET /todos/abc` | **404** `{"error":"not found"}` |
| `GET /todos/1/complete` | **404** `{"error":"not found"}` |
| `GET /todos/1/` | **404** `{"error":"not found"}` |
| `GET /todos/1?filter=open` | **404** `{"error":"not found"}` |
| `POST /todos/1` | **404** `{"error":"not found"}` |
| `GET /todos` | **200** `[]` (JSON-массив дел) |
| `GET /todos/stats` | **200** `{"total":0,"open":0,"done":0}` |

Причина: в `handle` (`src/server.ts`) для чтения есть только две ветки —
`GET /todos` и `GET /todos/stats`, а шаблон пути существует только один —
`/^\/todos\/(\d+)\/complete$/` для `POST`. Запрос `GET /todos/:id` попадает в общую
ветку неизвестного маршрута и даёт 404.

Дополнительно зафиксировано для согласованности с существующим поведением:

- ведущие нули в идентификаторе уже трактуются как числовой id:
  `POST /todos/007/complete` завершает дело с `id` 7 (`Number('007') === 7`);
- идентификаторы выдаются последовательно с 1 (`nextId` в модели `TodoList`),
  идентификаторы не переиспользуются;
- `POST /todos/999/complete` для неизвестного дела даёт **400**
  `{"error":"todo 999 not found"}` — ошибка из чистой функции попадает в общий
  `catch` обработчика. Это существующее поведение, в объём задачи не входит
  (вопрос 5 к PM);
- состояние живёт в памяти процесса и сбрасывается при перезапуске.

## Согласуемый объём

### 1. Чистая функция поиска дела (`src/todos.ts`)

По [правилу проекта](../CLAUDE.md) логика живёт в `src/todos.ts` чистыми функциями,
I/O — только в `src/server.ts`. Поиск дела по идентификатору — это логика, поэтому
предпочтительный вариант:

- Экспортируется из `src/todos.ts` рядом с остальными чистыми функциями
  (`addTodo`, `completeTodo`, `listTodos`, `todoStats`), по именованию и стилю модуля.
- Сигнатура: `findTodo(list: TodoList, id: number): Todo | undefined`.
  Вход — существующий тип `TodoList` (`{ nextId, items }`); новые типы для входа
  не вводятся.
- Результат:
  - если в `list.items` есть дело с `id`, возвращается **само это дело** — тот же
    объект элемента списка, с теми же тремя полями `id`, `title`, `done`
    (в том числе с текущим значением `done`);
  - если такого дела нет — `undefined`. «Нет дела» — это не ошибка, поэтому
    функция **не бросает исключений** (в отличие от `completeTodo` и `deleteTodo`).
- Функция **не мутирует** вход: не меняет `list`, `list.nextId`, массив `list.items`
  (ссылка, длина, порядок), поля и идентичность элементов. Вызов на замороженном
  входе (`Object.freeze`) не бросает исключений.
- Функция детерминирована: два вызова подряд на неизменённом состоянии дают равные
  результаты.
- Допустимая альтернатива (тот же наблюдаемый контракт): поиск выполняется прямо
  в обработчике через существующую `listTodos(state).find((t) => t.id === id)`,
  без новой функции в `src/todos.ts`. В этом случае обязательна HTTP-часть проверок
  (§3.2), а кейсы §3.1 не требуются. Согласование приоритета — вопрос 3 к PM.

### 2. Маршрут `GET /todos/:id` (`src/server.ts`)

- Обработчик добавляется в существующий `handle` в `src/server.ts`; состояние читается
  из текущей переменной `state`. Новое хранилище, новые модули, отдельный файл-роутер,
  middleware и рефакторинг `handle` не вводятся; существующие ветки `if` и их порядок
  не меняются.
- Путь сопоставляется шаблоном `/^\/todos\/(\d+)$/` — по образцу существующего
  шаблона `/^\/todos\/(\d+)\/complete$/`:
  - идентификатор — десятичное целое число (только цифры), ведущие нули допустимы:
    `GET /todos/007` соответствует делу с `id` 7 — согласованно с существующим
    `POST /todos/:id/complete`;
  - нечисловой (`/todos/abc`), отрицательный (`/todos/-1`), дробный (`/todos/1.5`),
    пустой (`/todos/`), с дополнительным сегментом (`/todos/1/complete`,
    `/todos/1/x`), с завершающим слешем (`/todos/1/`) и с другим регистром
    (`/Todos/1`) под шаблон **не подходят** → общий ответ 404
    `{"error":"not found"}` (текущее поведение).
- Метод — **только `GET`**. Другие методы на `/todos/:id`
  (`POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`) сохраняют текущий общий
  ответ **404** `{"error":"not found"}`. Ответ 405 с заголовком `Allow` не вводится.
  Маршруты изменения дела принадлежат другим частям серии E2E (например, PIL-32 —
  `DELETE /todos/:id`) и в эту задачу не входят.
- Ответ для существующего дела:
  - HTTP **200**;
  - заголовок `Content-Type: application/json; charset=utf-8` — существующий хелпер
    `send` в `src/server.ts`;
  - тело — **объект дела в том же формате, что элемент в `GET /todos`**: ровно три
    поля `id`, `title`, `done`, в том же порядке, без обёртки, без дополнительных
    полей и без завершающего перевода строки. Например:
    `{"id":1,"title":"Купить хлеб","done":false}`;
  - для завершённого дела `done` равен `true` — ответ отражает текущее состояние.
- Ответ для неизвестного числового идентификатора (в том числе `0`, идентификатора
  ещё не выданного, дела, которого нет в списке, и дела, удалённого другим маршрутом):
  HTTP **404**, тело — существующий общий JSON-ответ неизвестного маршрута
  `{"error":"not found"}`. Новый формат ошибок не вводится (вопрос 1 к PM).
- **Порядок проверок**: наличие дела проверяется до формирования успешного ответа;
  обработчик не должен отдавать 400 из общего `catch` вместо 404 (как это делает
  `completeTodo`). То есть обработчик сначала ищет дело и, если его нет, отвечает 404;
  и только затем формирует 200.
- Запрос **только читает**: состояние процесса, список дел, их порядок, флаги `done`
  и `nextId` после запроса не меняются; идентификатор не расходуется — следующее
  добавленное дело получает следующий последовательный `id`.
- Query-параметры игнорируются: `GET /todos/1?filter=open` и `GET /todos/1?x=1`
  дают тот же успешный ответ, что `GET /todos/1`. Тело запроса игнорируется.
- Существующие маршруты не меняются: `GET /todos`, `GET /todos?filter=open|done`,
  `GET /todos/stats`, `POST /todos`, `POST /todos/:id/complete` отвечают прежними
  статусами и прежними телами. В частности, `POST /todos/999/complete` по-прежнему
  даёт 400 `{"error":"todo 999 not found"}`.
- Новый шаблон `/^\/todos\/(\d+)$/` не конфликтует с точными сравнениями
  `/todos` и `/todos/stats`: `stats` не является числом, поэтому под шаблон не
  подходит и `GET /todos/stats` остаётся прежним. Порядок веток в `if` на это
  не влияет; отдельный порядок «новый маршрут перед `GET /todos`» не требуется.
- При пустом списке `GET /todos/1` даёт 404 — дела с `id` 1 ещё нет.

### 3. Проверки

Новых тестовых зависимостей нет: используются уже подключённые Vitest, встроенный
`node:http` и глобальный `fetch` Node.js.

#### 3.1. Чистая функция (`test/todos.test.ts`)

Кейсы добавляются в существующий файл `test/todos.test.ts`, рядом с текущими группами
`todos` и `todoStats`. Существующие кейсы по смыслу не меняются. Обязательные кейсы
(нужны при варианте с новой функцией `findTodo`, см. §1):

- **Дело найдено**: `findTodo(list, 1)` возвращает дело с `id` 1 — те же `id`, `title`
  и `done`, что в списке (сравнение точное, `toEqual`).
- **Открытое и завершённое дело**: для дела с `done: true` возвращается `done: true`;
  значение отражает текущее состояние, а не значение по умолчанию.
- **Неизвестный идентификатор**: `findTodo(list, 9)` → `undefined`; для пустого списка
  `findTodo(emptyList(), 1)` → `undefined`.
- **Отсутствие мутаций**: снимок состояния (ссылка на `list`, значение `nextId`, ссылка
  и содержимое массива `items`, порядок элементов, поля и идентичность каждого
  элемента) до и после вызова совпадает; вызов на замороженном входе (`Object.freeze`)
  не бросает исключений.
- **Детерминированность**: два вызова подряд на неизменённом состоянии дают равные
  результаты.

#### 3.2. HTTP-маршрут (`test/server.test.ts`)

Кейсы добавляются в существующий файл `test/server.test.ts` отдельной группой
`describe('GET /todos/:id')`. Изоляция состояния в файле уже настроена: перед каждым
кейсом выполняется `vi.resetModules()`, модуль `src/server.ts` импортируется заново
(новый экземпляр с пустым `state`), сервер поднимается на свободном порту
(`listen(0, '127.0.0.1')`), после кейса соединения закрываются. HTTP-запросы выполняются
глобальным `fetch` Node.js; существующие хелперы `get`/`post` и `addTodo` используются
как есть, дополнительный HTTP-клиент в зависимости не добавляется.

Обязательные кейсы:

- **Успешный ответ**: создать дело `POST /todos {"title":"a"}` → `GET /todos/1` →
  **200**, `content-type: application/json; charset=utf-8`, тело ровно
  `{"id":1,"title":"a","done":false}`; тело **совпадает** с элементом того же дела
  в `GET /todos` (одинаковый формат объекта).
- **Завершённое дело**: после `POST /todos/1/complete` → `GET /todos/1` → 200,
  тело с `"done":true`.
- **Неизвестный идентификатор**: `GET /todos/999` → **404**
  `{"error":"not found"}`; отдельным кейсом — `GET /todos/1` на пустом списке → 404.
- **Некорректные пути**: `GET /todos/abc`, `GET /todos/-1`, `GET /todos/1.5`,
  `GET /todos/1/complete`, `GET /todos/1/`, `GET /todos/` → 404
  `{"error":"not found"}`.
- **Не-GET**: `POST /todos/1` → 404 `{"error":"not found"}` (текущее поведение).
- **Query-параметры игнорируются**: `GET /todos/1?filter=open` → тот же успешный ответ,
  что `GET /todos/1`.
- **Чтение ничего не меняет**: `GET /todos` и `GET /todos/stats` до и после
  `GET /todos/:id` отдают одинаковые тела; повторный `GET /todos/1` даёт тот же ответ;
  после чтения следующее добавленное дело получает следующий последовательный `id`.
- **Регрессия существующих маршрутов**: `GET /todos`, `GET /todos?filter=open`,
  `GET /todos?filter=done`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete` и прежний 404 для неизвестных путей отвечают как раньше.

Кейсы допускается объединять в содержательные сценарии без дублирования проверок.

## Исключения и границы

Вне объёма (не делается в этой задаче):

- изменение дела: `PUT /todos/:id`, `PATCH /todos/:id` — текущий ответ 404 сохраняется;
  эти маршруты входят в другие части серии E2E;
- удаление дела: `DELETE /todos/:id` — текущий ответ 404 сохраняется; маршрут
  относится к задаче PIL-32 (вопрос 4 к PM);
- чтение нескольких дел: `GET /todos/1,2`, диапазоны `GET /todos/1-3`, подресурсы
  `GET /todos/1/items` — только один идентификатор;
- изменение формата `GET /todos` (например, добавление поля или конверта), фильтры
  и сортировка в списке, пагинация;
- новые поля в модели `Todo`/`TodoList` (`createdAt`, `updatedAt`, теги, категории),
  валидация и миграции модели;
- новый формат ошибок (например, `{"error":"todo 999 not found"}` для 404) — 404
  остаётся существующим общим ответом;
- код 405 и заголовок `Allow`, поддержка `HEAD`/`OPTIONS` как отдельных контрактов;
- кэширование (`ETag`, `Cache-Control`), версионирование API, авторизация, CORS;
- постоянное хранилище: базы данных, файлы, внешние сервисы — состояние, как и раньше,
  живёт в памяти процесса и сбрасывается при перезапуске;
- UI, дашборды, веб-интерфейс, отдельный E2E-стенд и E2E-фреймворк;
- рефакторинг маршрутизации `handle`, выделение роутера в отдельный модуль, middleware;
- новые зависимости, изменения `package.json`/`package-lock.json`, `tsconfig.json`,
  `CLAUDE.md`, `docs/README.md`, `docs/PIL-21.md`, `.github/**`, CI и инфраструктуры;
- чужие задачи и PR (PIL-18, PIL-19, PIL-21, PIL-24, PIL-25, PIL-32, PIL-33, PIL-35,

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые TypeScript,
  Node.js `>=20` (`node:http`, глобальный `fetch`) и Vitest; HTTP-клиент в
  зависимостях не нужен.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным,
  `npm ci` работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check` и
  `npm test`; обе доступны без сети.
- Особенность окружения (проверено): в текущем окружении `NODE_ENV=production` и
  `npm config omit=dev`, поэтому обычный `npm ci` **не ставит** dev-зависимости;
  для `npm run check` и `npm test` нужен `npm ci --include=dev`. На содержимое
  репозитория это не влияет.
- Особенность проекта: `tsconfig.json` включает только `src`, поэтому файлы в `test/`
  **не** проверяются командой `npm run check` — типы тестов проверяются вручную или
  в IDE. Сборка `npm run build` тоже затрагивает только `src`.
- В окружении отсутствует `curl` (проверено), поэтому ручные проверки выполняются
  Node-однострочниками (см. план проверки); для пользователя эквивалент — `curl -i
  http://127.0.0.1:3000/todos/1`.
- Спецификация (`docs/PIL-37.md`) включается в PR реализации.

## Вопросы к PM (не блокируют минимальный объём)

1. **Тело ответа 404.** Для неизвестного идентификатора предлагается существующий
   общий ответ `{"error":"not found"}` — так требует постановка. Нужен ли более
   конкретный текст, например `{"error":"todo 999 not found"}`, как у
   `POST /todos/:id/complete`? Решение по умолчанию: **общий
   `{"error":"not found"}`** — новый формат ошибок не вводится.
2. **Формат успешного ответа.** Предлагается отдавать объект дела напрямую
   (`{"id":1,"title":"...","done":false}`) — «в том же формате, что `GET /todos`».
   Нужен ли конверт вида `{"todo": {...}}`? Решение по умолчанию: **объект напрямую**.
3. **Чистая функция против поиска в обработчике.** Предпочтителен вариант с новой
   функцией `findTodo` в `src/todos.ts` (правило проекта о чистых функциях) и её
   кейсами в `test/todos.test.ts`. Допустим и проще вариант с поиском прямо в
   `src/server.ts` через `listTodos`. Что считать обязательным? Решение по умолчанию:
   **чистая функция обязательна**, HTTP-контракт одинаков в обоих вариантах.
4. **Согласование с соседними частями серии E2E.** PIL-32 добавляет
   `DELETE /todos/:id` в тот же обработчик и меняет те же файлы (`src/server.ts`,
   `test/server.test.ts`, `README.md`). Нужно ли объединять задачи в одну ветку или
   держать их раздельно с ожидаемым конфликтом при слиянии? Решение по умолчанию:
   **задачи раздельные**, каждая — своя ветка и PR; при слиянии конфликт в
   `src/server.ts` разрешается вручную, чужие ветки не трогаются.
5. **Несогласованность 404 и 400.** Чтение неизвестного дела даёт 404 (требование
   постановки), а завершение неизвестного дела — 400 `{"error":"todo N not found"}`
   (текущее поведение). Приводить ли `POST /todos/:id/complete` к 404 в этой же
   задаче? Решение по умолчанию: **нет**, `POST` не трогаем — правка существующего
   маршрута вне объёма.
6. **Ведущие нули в идентификаторе.** `GET /todos/007` по умолчанию соответствует
   делу с `id` 7 — согласованно с существующим `POST /todos/007/complete`. Нужно ли
   считать такой путь некорректным (404)? Решение по умолчанию: **трактовать как 7**.
7. **HEAD и другие методы.** По умолчанию `HEAD /todos/1` и прочие не-GET методы дают
   общий 404. Нужен ли отдельный контракт для `HEAD` (ответ без тела, как у
   `GET`)? Решение по умолчанию: **нет**, `HEAD` не вводится.
8. **Метаданные и кэш-заголовки.** Нужны ли `createdAt`/`updatedAt` в ответе, а также
   `ETag`/`Cache-Control`? Решение по умолчанию: **нет** — модель `Todo` не меняется,
   кэш-заголовки не добавляются.
