# PIL-35 — GET /readyz в тестовом API

Редакция 1 от 2026-11-19. Статус: подготовлена к утверждению объёма.
Реализация и декомпозиция до утверждения не выполняются.

## Цель и основания

Потребитель тестового API (например, E2E-проверка) может проверить готовность
HTTP-сервиса отдельным запросом, не создавая и не изменяя задачи.

## Контракт и согласуемый объём

- Добавляется `GET /readyz`: HTTP 200, тело ровно `{"ready":true}` без обёртки,
  дополнительных полей и завершающего перевода строки.
- Тип содержимого — `application/json`. Допускается и принимается существующий
  формат `application/json; charset=utf-8`: используется общий JSON-ответ сервера,
  поведение заголовков остальных маршрутов не меняется.
- Готовность означает способность запущенного HTTP-обработчика ответить на запрос.
  Ответ всегда `ready: true`, независимо от пустоты и содержимого списка задач.
- Обработка не меняет состояние списка, включая идентификатор следующей задачи;
  не обращается к внешним сервисам, файлам или базам данных и не делает исходящих
  сетевых запросов. Отдельное состояние готовности не вводится.
- Путь сопоставляется точно по `pathname`, как у существующих маршрутов.
  Query-параметры игнорируются: `/readyz?probe=1` имеет тот же результат.
- Другие методы на `/readyz` и неизвестные пути, включая `/readyz/`, сохраняют
  существующее поведение 404. Для ответов с телом — `{"error":"not found"}`;
  для `HEAD` действуют стандартные правила HTTP без тела ответа.
- Новое HTTP-поведение покрывается автоматическими тестами в существующем
  `test/server.test.ts`. Существующие тесты и контракты маршрутов сохраняются.
- В таблицу API `README.md` добавляется краткое описание `GET /readyz` с ответом
  `{"ready":true}`. Остальная документация API не переписывается.

Ожидаемые изменения после утверждения: `src/server.ts`, `test/server.test.ts`,
`README.md` и эта спецификация `docs/PIL-35.md`. Используются существующий
обработчик и хелпер JSON-ответа, без рефакторинга маршрутизации и модели задач.
В фазе спецификации создаётся только `docs/PIL-35.md`.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | Проверка после запуска при пустом списке | `GET /readyz` → 200, JSON Content-Type, тело ровно `{"ready":true}` |
| 2 | Проверка при наличии открытой и выполненной задачи | Тот же успешный ответ; готовность не зависит от задач |
| 3 | Несколько последовательных проверок | Каждый ответ удовлетворяет контракту; список до и после полностью совпадает по id, заголовкам, статусам и порядку |
| 4 | Создание задачи после проверок | Её id равен ожидаемому следующему id; проверки готовности не расходуют идентификаторы |
| 5 | `GET /readyz?probe=1` | Тот же ответ, что для `/readyz` |
| 6 | `POST /readyz`, `GET /readyz/` | 404 и прежний JSON ошибки; задачи не меняются |
| 7 | Существующие операции с задачами | Создание, чтение, фильтрация, завершение и статистика сохраняют статусы и форматы ответов |
| 8 | Изолированный от внешних сервисов запуск | Готовность работает без внешних подключений; в ветке обработки отсутствует внешнее I/O |
| 9 | Покрытие и отчёт реализации | Автоматические HTTP-проверки нового маршрута и регрессии проходят; в результате реализации перечислены фактически выполненные проверки и их исходы |

## Исключения и границы

В объём не входят динамическая диагностика зависимостей, ответ 503 или
`ready: false`, проверка БД/сети, управление запуском и завершением процесса,
отдельные liveness/startup-маршруты, таймауты и SLA, авторизация, метрики,
настройка инфраструктурных probes, CI или отдельный E2E-фреймворк.

Модель и хранение задач, существующие маршруты, зависимости, lock-файл,
TypeScript-конфигурация и спецификация PIL-21 не изменяются. Название E2E
не расширяет задачу за пределы HTTP API и его проверок.

## Зависимости

Используются Node.js >=20, TypeScript и Vitest из текущего проекта.
HTTP-тесты опираются на существующий локальный сервер на свободном порту,
встроенный `fetch`, сброс модулей между кейсами и закрытие соединений после них.
Локальные HTTP-запросы тестового клиента допустимы; запрет внешних запросов
относится к обработке готовности. Новые пакеты и внешние сервисы не требуются.

## План проверки после утверждения и реализации

1. Расширить существующие HTTP-проверки кейсами 1–6: проверить код, JSON-тип,
   точное тело, повторяемость, неизменность списка и следующий id.
   Кейсы можно объединять в содержательные сценарии без дублирования проверок.
2. Выполнить `npm run check` и `npm test` согласно правилам проекта.
   Полный прогон включает тесты модели и HTTP-регрессию: `GET /todos`, фильтры
   `all|open|done`, `POST /todos`, `POST /todos/:id/complete`, `GET /todos/stats`,
   а также существующие проверки ошибок и неизвестных путей.
3. Просмотреть ветку нового маршрута: фиксированный ответ через существующий
   хелпер, отсутствие записи в состояние и внешнего I/O. Отдельный сетевой
   стенд для этой проверки не требуется.
4. Проверить diff на соответствие границам файлов и актуальность строки API
   в README. В отчёте реализации указать команды, результаты и ограничения;
   невыполненные проверки явно обозначить, не считать успешными.
