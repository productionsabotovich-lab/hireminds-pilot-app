## Текущее состояние и согласуемый контракт

`addTodo(list, title)` уже применяет JavaScript `String.prototype.trim()` и при пустом результате бросает `Error('title is empty')`. Создание объекта и нового списка происходит после проверки. Существующий unit-тест проверяет отказ для `'   '`, но не сохранность входного состояния.

`POST /todos` читает JSON, передаёт `String(body.title ?? '')` в `addTodo` и присваивает новое состояние только после успешного возврата функции. Ошибка преобразуется в HTTP 400 с JSON. Существующие HTTP-тесты покрывают успешное создание, но не отказ при пустом названии. Остальные маршруты: `GET /todos`, `GET /todos/stats`, `POST /todos/:id/complete`.

Это закрепление существующего поведения и устранение пробела в проверках. Обязательной смены алгоритма в production-коде не требуется, если он удовлетворяет критериям ниже.

### Название и ответы

- Граница пустоты — результат существующего `trim()`: `''`, `'   '`, строка из табуляции и переводов строк, а также неразрывный пробел `\u00a0` отклоняются. Не вводится собственный список пробельных символов или нормализация Unicode.
- HTTP-отказ: статус **400**, `Content-Type: application/json; charset=utf-8`, тело ровно `{"error":"title is empty"}` без дополнительных полей.
- Название только из табуляции (`'\t'`, `'\t\t'`) и название только из перевода строки (`'\n'`, `'\n\n'`, `'\r'`, `'\r\n'`) обрабатываются так же, как название только из пробелов: после `trim()` строка пуста, ответ — 400 с указанной ошибкой, список и `nextId` не меняются. Каждый вариант проверяется независимо, смешанная строка не заменяет эти случаи.
- Корректная строка, например `'  Купить хлеб  '`, создаёт ровно одно дело со значением `title: 'Купить хлеб'`; внутренние пробелы сохраняются. Ответ **201**, тот же Content-Type, объект ровно `{ id, title, done: false }`. Идентификаторы последовательны.
- Отказ не меняет `items`, порядок, поля существующих дел, их статус выполнения и `nextId`. Следующее успешное создание получает тот же ID, который получило бы без невалидного запроса.
- Существующее преобразование `String(body.title ?? '')` сохраняется: отсутствующее поле и `null` приводят к пустому названию и тому же отказу; числа, boolean и другие значения не получают новой строгой проверки типа. Например, `42` по-прежнему создаёт название `'42'`. Дополнительные поля запроса по-прежнему игнорируются.

## Сценарии и критерии приёмки

| Сценарий | Критерий |
| --- | --- |
| Клиент создаёт дело с содержательным названием | 201, прежняя структура объекта, края обрезаны, внутренние пробелы сохранены; дело доступно через `GET /todos` |
| Клиент передаёт пустую строку или только пробельные символы | 400 и точный JSON ошибки, без создания дела |
| POST с `title: '   '` (только пробелы) | Отдельная HTTP-проверка: 400 и точный JSON ошибки; полный список и статистика до и после совпадают, следующий ID не расходуется |
| POST с `title: '\t'` или `'\t\t'` (только табуляция) | Для каждого значения отдельная HTTP-проверка: 400 и точный JSON ошибки; полный список и статистика до и после совпадают, следующий ID не расходуется |
| POST с `title: '\n'`, `'\n\n'`, `'\r'` или `'\r\n'` (только перевод строки) | Для каждого значения отдельная HTTP-проверка: 400 и точный JSON ошибки; полный список и статистика до и после совпадают, следующий ID не расходуется |
| Клиент ошибается в непустом списке | Полный список и статистика до и после отказа совпадают, включая выполненные дела |
| Клиент отправляет корректный запрос после отказа | Создаётся одно дело, ID следующий после последнего успешного создания, без пропуска |
| Клиент пропускает `title` или передаёт `null` | Существующий отказ 400 `title is empty` сохраняется |
| Клиент использует ранее допустимое приведение типа | `title: 42` сохраняет поведение 201 с названием `'42'` |
| Вызывающий код передаёт пустое название в `addTodo` | Ошибка `title is empty`, входной список полностью неизменён |
| Клиент использует другие маршруты | Существующие тесты списка, фильтров, завершения, статистики и 404 проходят без изменения ожидаемого поведения |

## План проверки после согласования

Это перечень проверок результата, а не декомпозиция реализации.

Обязательная матрица значений для unit- и HTTP-проверок: `''`, `'   '`, `'\t'`, `'\t\t'`, `'\n'`, `'\n\n'`, `'\r'`, `'\r\n'`, `'\t\r\n'`, `'\u00a0'`. Для **каждого** значения независимо выполняются проверки пустого и непустого хранилища из пунктов 3–4. Каждая строка параметризованного HTTP-теста включает полный цикл «снимок списка и статистики → отказ → сравнение списка и статистики → успешное создание с ожидаемым ID». Одна общая проверка после серии отказов не заменяет отдельную проверку для пробелов, табуляции и перевода строки. Между строками теста состояние изолируется существующим каркасом.

1. В `test/todos.test.ts` проверить отказ параметризованно для `''`, `'   '`, `'\t\r\n'`, `'\u00a0'`. Для непустого списка с открытым и выполненным делами сохранить независимую копию значений до вызова; после исключения сравнить всё состояние, `nextId`, ссылки массива и элементов. Снимок значений должен быть независимым, чтобы мутация не изменила одновременно ожидаемый результат. Проверить успешное создание после отказа с ожидаемым ID и сохранение внутренних пробелов в корректном названии.
2. В `test/server.test.ts` использовать существующий реальный HTTP-сервер, `fetch`, изоляцию через `vi.resetModules()` и закрытие сервера после теста. Параметризованно отправить JSON `{ title }` с перечисленными пустыми строками; проверить 400, Content-Type и точное тело ошибки. Табуляцию и переводы строк передавать через `JSON.stringify`, чтобы тело оставалось валидным JSON и проверялось название, а не синтаксис JSON.
3. Проверить отсутствие добавления в пустом хранилище: после отказа `GET /todos` возвращает `[]`, статистика — `{ total: 0, open: 0, done: 0 }`, следующее успешное создание получает ID 1.
4. Проверить отказ в непустом хранилище: создать дела с ID 1 и 2, завершить одно; получить и сохранить полный список и статистику; отправить невалидный запрос; повторные GET возвращают точные прежние данные. Затем корректный POST возвращает ID 3 и добавляет ровно одно открытое дело. Проверять статусы всех подготовительных запросов, чтобы ошибка подготовки не давала ложный успех.
5. Проверить совместимость: корректное название с краевыми и внутренними пробелами, отсутствующий `title`, `null`, числовой `title: 42`; существующие регрессионные тесты маршрутов остаются обязательными.
6. Выполнить `npm run check` и `npm test` согласно правилам проекта. На фазе спецификации эти проверки не заявляются как выполненные; новые тесты и код не пишутся. Проверить diff на соблюдение границ файлов.

## Границы объёма и исключения

После утверждения допускаются изменения `test/todos.test.ts`, `test/server.test.ts`, `docs/PIL-53.md`, краткое описание контракта в `README.md`. В `src/todos.ts` и `src/server.ts` допустима только минимальная корректировка, если проверки выявят несоответствие указанному контракту; рефакторинг не входит в объём.

Вне объёма: строгая схема входного JSON, запрет нестроковых значений, новая обработка JSON верхнего уровня и синтаксических ошибок, ограничения длины названия или размера тела, новые коды/форматы ошибок, изменение HTTP-маршрутов, UI, постоянное хранилище, новые зависимости, изменения CI и конфигурации. Символы, которые JavaScript `trim()` не удаляет, например `\u200b`, не объявляются пустотой в этой задаче. Не требуется одинаковый текст ошибок парсинга JSON между версиями Node.js.

## Зависимости и ограничения

- Node.js >=20, существующие TypeScript и Vitest; HTTP-клиент — встроенный `fetch`. Внешние сервисы и новые пакеты не нужны.
- Состояние остаётся в памяти процесса. Для наблюдения за `nextId` HTTP-тест использует следующее успешное создание, без тестового эндпоинта или экспорта состояния.
- Логика остаётся в чистых функциях `src/todos.ts`, I/O — в `src/server.ts` согласно правилам проекта.
- Спецификация PIL-21 сохраняет силу для статистики; данная редакция не меняет её контракт и не наследует вопросы о чужих задачах.
- До согласования создаётся только этот документ; реализация, PR реализации и разбиение на задачи не выполняются.
