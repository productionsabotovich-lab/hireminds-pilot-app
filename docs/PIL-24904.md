# PIL-24904 — Add todo statistics

Редакция 1. Статус: подготовлена к утверждению объёма; реализация не начата.

## Цель и основания

Пользователь получает количество всех, открытых и выполненных дел текущего
списка одним запросом.

Основания: [описание задачи](/opt/hireminds/context/issue.md),
[правила проекта](../CLAUDE.md), [API и хранение состояния](../README.md),
[модель списка](../src/todos.ts), [HTTP-обработчик](../src/server.ts),
[существующие тесты](../test/todos.test.ts).

## Контракт и сценарии

- `src/todos.ts` экспортирует чистую функцию `todoStats(list: TodoList)`,
  возвращающую объект ровно с полями `{ total, open, done }` типа `number`.
- `total` равен `list.items.length`; `done` — количеству элементов с
  `done === true`; `open` — количеству элементов с `done === false`.
  Для корректного `TodoList` всегда `total === open + done`.
- Подсчёт не меняет `list`, `nextId`, массив `items`, его порядок, ссылки
  на элементы и любые поля элементов.
- `GET /todos/stats` возвращает HTTP 200 и JSON ровно указанной формы
  для текущего состояния сервера, с существующим JSON content-type.
  Query-параметры не ограничивают подсчёт: статистика относится ко всему списку.
- До добавления дел ответ равен `{ "total": 0, "open": 0, "done": 0 }`.
  После добавления дела растут `total` и `open`; после завершения дела
  `open` уменьшается, `done` увеличивается, `total` сохраняется.
  Повторное завершение уже выполненного дела не меняет статистику.
- Чтение статистики не меняет состояние. После перезапуска статистика
  снова нулевая согласно существующему хранению в памяти процесса.

## Критерии приёмки

1. Пустой список даёт ровно `{ total: 0, open: 0, done: 0 }`.
2. Список из трёх дел, одно из которых завершено, даёт ровно
   `{ total: 3, open: 2, done: 1 }`.
3. Два завершённых дела дают ровно `{ total: 2, open: 0, done: 2 }`.
4. Тест немутируемости проверяет сохранность всего входного списка,
   включая `nextId`, порядок и поля элементов; замороженные входные объекты
   допустимы для усиления этой проверки. Повторный вызов даёт тот же результат.
5. HTTP-запрос возвращает актуальные счётчики после добавления и завершения
   дел, HTTP 200 и JSON без дополнительных полей.
6. README описывает метод, путь и поля ответа нового endpoint.
7. Существующее поведение API и тесты сохраняются; `npm run check`
   и `npm test` проходят без новых зависимостей.

## Границы объёма и исключения

Единственный новый файл — эта спецификация `docs/PIL-24904.md`.
После утверждения изменения реализации ограничены четырьмя существующими
файлами: `src/todos.ts`, `src/server.ts`, `test/todos.test.ts`, `README.md`.
Автоматизированные тесты добавляются в существующий тестовый файл.

В объём не входят UI, фильтруемая статистика, проценты, история, персистентность,
новые зависимости, изменения `.github` и инфраструктуры, рефакторинг
архитектуры сервера и валидация некорректных объектов вне типа `TodoList`.
Другие методы и пути используют существующую маршрутизацию и ошибки.

## Зависимости и план проверки

Используются существующие `TodoList`, HTTP-обработчик и Vitest;
[команды и требование Node.js](../package.json) остаются прежними.

После утверждения спецификации проверить:

- Автоматически: пустой, смешанный и полностью завершённый списки;
  немутируемость и точный набор полей результата в `test/todos.test.ts`.
- Через HTTP: начальный нулевой ответ, добавление двух дел, завершение одного,
  повторное завершение и повторное чтение; проверить значения, статус и
  JSON content-type. Проверить, что query-параметр не фильтрует статистику.
- Выполнить `npm run check` и `npm test`; сверить документацию с ответом API
  и убедиться, что diff ограничен перечисленными пятью файлами.
