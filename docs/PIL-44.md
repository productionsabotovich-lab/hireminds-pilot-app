# PIL-44 — E2E N1 · Список возможностей TODO API

Редакция 1 от 2026-11-21. Статус: объём утверждён 2026-11-21 (решение D-13), реализация выполнена
в фазе Code; объём реализации соответствует этой редакции.

## Цель и основания

Клиенту сквозной (E2E) проверки нужен способ узнать, какие функциональные части поддерживает
тестовый TODO API, не изучая исходный код и не вызывая по очереди все маршруты. Один
HTTP-запрос `GET /capabilities` возвращает фиксированный перечень поддерживаемых возможностей.

Отличие PIL-44 от соседних E2E-задач пилота ([PIL-35](https://github.com/productionsabotovich-lab/hireminds-pilot-app/pull/17),
[PIL-38](https://github.com/productionsabotovich-lab/hireminds-pilot-app/pull/18),
[PIL-40](https://github.com/productionsabotovich-lab/hireminds-pilot-app/pull/19),
[PIL-41](https://github.com/productionsabotovich-lab/hireminds-pilot-app/pull/20),
[PIL-42](https://github.com/productionsabotovich-lab/hireminds-pilot-app/pull/21)): те добавляют по
одному «служебному» маршруту (`/readyz`, `/healthz`, `/version`, `/health`, `/info`) с одиночным
фиксированным ответом. PIL-44 добавляет точку самоописания API — список названий функциональных
областей, а не конкретный статус, версию или имя сервиса.

## Согласуемый объём

1. Маршрут `GET /capabilities` в существующем HTTP-обработчике `src/server.ts`.

### 1. Маршрут `GET /capabilities` (`src/server.ts`)

- Ответ: HTTP **200**, заголовок `Content-Type: application/json; charset=utf-8`
  (существующий хелпер `send` в [src/server.ts](../src/server.ts)), тело — ровно
  `{"capabilities":["todos"]}`.
- Структура ответа: **единственный собственный ключ** `capabilities`; значение — массив строк;
  в этой редакции в массиве ровно один элемент — строка `"todos"`.
- Список **фиксирован**: он задаётся константой в `src/server.ts` (например
  `const CAPABILITIES = ['todos'];`) и не вычисляется рефлексией по зарегистрированным
  маршрутам, не читается из `package.json`, переменных окружения, файлов, базы данных и
  внешних сервисов.
- Запрос только читает: состояние списка дел не меняется, `nextId` не расходуется, тело
  запроса не читается, файловых, сетевых и иных внешних обращений нет.
- Ответ одинаков при пустом и заполненном списке и при повторных запросах; ответ не зависит
  от числа дел и их состояния.
- Сопоставление маршрута — по методу `GET` и точному `url.pathname === '/capabilities'`,
  как у существующих маршрутов. Query-параметры игнорируются: `/capabilities?probe=1`
  даёт тот же ответ.
- Другие методы на `/capabilities` (в том числе `POST`), а также пути `/capabilities/`
  и `/capabilities/extra` сохраняют существующий ответ 404 `{"error":"not found"}`.
  Поддержка `HEAD` и `OPTIONS` не добавляется.
- Новая ветка маршрута добавляется в существующую цепочку `if` внутри `handle`, до ветки 404;
  отдельный файл-роутер, middleware и рефакторинг `handle` не вводятся.
- Верхний комментарий в `src/server.ts`, перечисляющий маршруты, дополняется строкой
  `GET /capabilities`.
- `src/todos.ts` **не меняется**: отдельная бизнес-функция для списка возможностей не нужна,
  состояние списка дел в ответе не участвует.

### 2. Автоматические проверки (`test/server.test.ts`)

Кейсы добавляются в существующий файл [test/server.test.ts](../test/server.test.ts) отдельной
группой `describe('GET /capabilities')`, рядом с группой `GET /todos/stats` и до группы
`existing routes`. Используется существующий каркас файла: `vi.resetModules()` и динамический
импорт `handle`, сервер на свободном порту (`server.listen(0, '127.0.0.1')`), глобальный
`fetch` Node.js, закрытие сервера в `afterEach`. Новых тестовых файлов, фреймворков и
зависимостей не требуется.

Обязательные кейсы:

- **Пустой список**: `GET /capabilities` → 200,
  `content-type: application/json; charset=utf-8`, тело ровно `{"capabilities":["todos"]}`.
- **Заполненный список и повторные запросы**: создать два дела через `POST /todos`, завершить
  одно через `POST /todos/:id/complete`; два запроса `GET /capabilities` подряд → одинаковое
  тело `{"capabilities":["todos"]}`.
- **Отсутствие побочных эффектов**: `GET /todos` до и после запроса отдаёт одинаковый список;
  следующее созданное дело получает следующий последовательный `id` (проверка, что `nextId`
  не расходуется).
- **Query-параметры игнорируются**: `GET /capabilities?probe=1` → 200 и то же тело.
- **Не-GET и похожие пути**: `POST /capabilities` → 404 `{"error":"not found"}`;
  `GET /capabilities/` → 404 `{"error":"not found"}`.
- **Регрессия существующих маршрутов**: существующие кейсы `GET /todos`,
  `GET /todos?filter=open|done`, `POST /todos`, `POST /todos/:id/complete`, `GET /todos/stats`
  остаются в силе и не ослабляются.

Замечание к окружению (не влияет на объём): `tsconfig.json` включает только `src`, поэтому
файлы в `test/` не проверяются командой `npm run check` — типы тестов проверяются вручную
или в IDE (та же особенность, что зафиксирована в [PIL-21](PIL-21.md)).

## Исключения и границы

Вне объёма (не делается в этой задаче):

- автоматическое обнаружение маршрутов (рефлексия по `handle`), саморегистрация capability,
  динамический перечень возможностей;
- дополнительные поля ответа (`version`, `count`, `generatedAt`, `description`), объекты вместо
  строк, вложенные структуры, группировка возможностей;
- новые возможности сверх `todos` (`stats`, `health`, `healthz`, `livez`, `readyz`, `version`,
  `info`, `delete`, `update`) — в том числе добавление их в перечень при слиянии соседних PR;
- новые маршруты, кроме `GET /capabilities`; изменение форматов, кодов, заголовков и обработки
  ошибок существующих маршрутов (`GET /todos`, `GET /todos/stats`, `POST /todos`,
  `POST /todos/:id/complete`);
- изменения модели `Todo`/`TodoList`, `src/todos.ts`, постоянное хранилище, база данных;
- авторизация, CORS, кэш-заголовки (`ETag`, `Cache-Control`), версионирование API, rate limit;
- UI, дашборды, OpenAPI/Swagger, отдельный E2E-фреймворк и E2E-инфраструктура;
- новые зависимости, изменения `package.json`/`package-lock.json`, `tsconfig.json`, `CLAUDE.md`,
  `docs/README.md`, `.github/**`, CI и инфраструктуры;
- правки чужих задач, веток и PR (#17–#22) — не трогаются.

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые Node.js `>=20`
  (встроенные `node:http` и `fetch`), TypeScript и Vitest из [package.json](../package.json).
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным, `npm ci`
  работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check` и `npm test`;
  обе доступны без сети.
- Особенность окружения (проверено 2026-11-21): в текущем окружении `NODE_ENV=production`
  и `npm config omit=dev`, поэтому обычный `npm ci` **не ставит** dev-зависимости; для
  `npm run check` и `npm test` нужен `npm ci --include=dev`. На содержимое репозитория это
  не влияет.
- Базовая проверка на текущем `main` (`dd2526c`) пройдена 2026-11-21: `npm run check` — без
  ошибок, `npm test` — 21 тест в двух файлах, все зелёные.
- Координация с соседними E2E-PR: открытые PR #17–#21 меняют те же файлы `src/server.ts`,
  `test/server.test.ts`, `README.md`, поэтому при слиянии возможны конфликты. PIL-44 чужие
  ветки и PR не изменяет; конфликты разрешаются при слиянии с сохранением всех маршрутов
  (см. вопрос 5 к PM).

## Вопросы к PM (не блокируют минимальный объём)

1. **Состав перечня.** Ограничиться ли элементом `"todos"`, или он должен перечислять
   под-возможности (`stats`, `health`, `version`)? Решение по умолчанию: только `"todos"`,
   ровно как в постановке.
2. **Формат элементов.** Строки (`"todos"`) или объекты вида `{ "name": "todos", ... }`?
   Решение по умолчанию: строки — формат зафиксирован постановкой.
3. **Источник перечня.** Фиксированная константа или автообнаружение зарегистрированных
   маршрутов? Решение по умолчанию: фиксированная константа — автообнаружение усложняет
   маршрут без выгоды для клиента.
4. **Дополнительные поля ответа.** Нужны ли `version`, `count`, `generatedAt`?
   Решение по умолчанию: нет — тело ровно `{"capabilities":["todos"]}`.
5. **Слияние с соседними E2E-PR.** Должны ли `readyz`, `healthz`, `version`, `health`, `info`
   появиться в перечне после слияния своих PR? Решение по умолчанию: нет в этой задаче —
   каждая соседняя задача расширяет перечень в своём PR, иначе возникнут конфликты
   и взаимные зависимости.
6. **Порядок слияния и конфликты файлов.** Кто и в каком порядке сливает PR #17–#22, все
   они меняют `src/server.ts`, `test/server.test.ts` и `README.md`? Решение по умолчанию:
   PIL-44 не трогает чужие ветки; конфликты разрешаются вручную при слиянии, все маршруты
   и тесты сохраняются.
7. **Метод `HEAD`.** Нужна ли поддержка `HEAD /capabilities`? Решение по умолчанию: нет —
   поведение существующих маршрутов (404 для не-GET) сохраняется.
