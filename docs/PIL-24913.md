# PIL-24913 — Add todo statistics

Редакция 1. Статус: спецификация подготовлена к утверждению объёма.

## Цель и основания

Предоставить клиенту количество всех, открытых и выполненных дел без изменения списка.

Источники: [постановка PIL-24913](/opt/hireminds/context/issue.md),
[правила проекта](../CLAUDE.md), [описание API](../README.md),
[модель и чистые функции](../src/todos.ts), [HTTP-обработчик](../src/server.ts),
[существующие тесты](../test/todos.test.ts), [команды и зависимости](../package.json).

## Согласуемый объём

Экспортировать `todoStats(list: TodoList)` из `src/todos.ts`. Результат — объект
ровно с ключами `{ total, open, done }`, значения — неотрицательные целые числа:
`total = list.items.length`, `done` — количество элементов с `done: true`,
`open` — количество элементов с `done: false`; `total = open + done`.
Функция не изменяет объект списка, `nextId`, массив, порядок или поля элементов.
Вход соответствует существующему типу `TodoList`; новая валидация не требуется.

Добавить `GET /todos/stats` в существующий HTTP-обработчик. Ответ: HTTP 200,
`Content-Type: application/json; charset=utf-8`, тело — результат `todoStats`
для текущего состояния процесса без обёртки и дополнительных полей.
Статистика относится ко всему списку; параметры запроса, включая `filter`,
не изменяют результат. Запрос не меняет состояние.

Добавить проверки в `test/todos.test.ts` и строку об эндпоинте с форматом ответа
в разделе API `README.md`. После утверждения допускаются изменения только
`src/todos.ts`, `src/server.ts`, `test/todos.test.ts`, `README.md` и этой спецификации.

## Пользовательские сценарии и критерии приёмки

1. Клиент запрашивает статистику пустого списка: функция и эндпоинт возвращают
   ровно `{ total: 0, open: 0, done: 0 }`.
2. В списке три дела, одно выполнено: результат — ровно
   `{ total: 3, open: 2, done: 1 }`.
3. Все два дела выполнены: результат — ровно `{ total: 2, open: 0, done: 2 }`.
4. После создания дела увеличиваются `total` и `open`; после завершения дела
   уменьшается `open` и увеличивается `done`, а `total` сохраняется.
   Повторное завершение того же дела не меняет счётчики.
5. После вызова функции исходный список, `nextId`, массив и элементы сохраняют
   значения и ссылки. Повторные вызовы дают тот же результат.
6. HTTP-ответ отражает текущее состояние, содержит ровно три указанных ключа,
   имеет статус 200 и существующий JSON content type. Чтение статистики
   не меняет последующие ответы списка.
7. Существующие операции создания, завершения и фильтрации сохраняют поведение;
   неподдерживаемый метод для `/todos/stats` получает существующий ответ 404.

## Исключения и зависимости

Вне объёма: UI, сохранение данных, статистика по фильтрам или пользователям,
проценты, новые поля модели, валидация некорректного `TodoList`, рефакторинг API,
новые зависимости, изменения `.github` и инфраструктуры. Сохраняется хранение
в памяти процесса и сброс при перезапуске.

Используются существующие TypeScript, Node.js >=20 и Vitest. Внешние сервисы
не нужны. Реализация начинается после утверждения этой редакции; аналитик
не создаёт PR и не выполняет реализацию.

## План проверки после утверждения

- В `test/todos.test.ts` проверить пустой, смешанный и полностью выполненный
  списки точным сравнением результата, включая отсутствие лишних ключей.
- Проверить отсутствие мутаций сравнением снимка до/после и сохранением ссылок
  списка, массива и элементов; замороженный вход может дополнительно выявлять
  попытки записи.
- Проверить HTTP через временный локальный сервер: пустой список, создание трёх
  дел, завершение одного, чтение статистики, завершение остальных. Проверить
  статус, content type, точное тело, независимость от `filter`, неизменность
  списка после чтения и существующий 404 для POST на путь статистики.
  Автоматизированные HTTP-проверки, если добавляются, разместить в том же файле
  тестов и закрывать сервер после проверки.
- Выполнить `npm run check` и `npm test`; проверить строку API в README и
  соответствие diff разрешённым пяти файлам.
