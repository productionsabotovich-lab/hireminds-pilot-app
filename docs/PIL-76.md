# PIL-76 — GET /health в тестовом API

Редакция 1. Статус: подготовлена к утверждению объёма.

## Цель и основания

Пользователь или автоматическая проверка может убедиться, что запущенный HTTP-процесс API отвечает, запросив `GET /health` и получив HTTP 200 с JSON `{"status":"ok"}`.

Источники требований и ограничений:

- [Постановка PIL-76](/opt/hireminds/context/issue.md).
- [Правила проекта](../CLAUDE.md) и [правила документов](README.md).
- [Действующая спецификация API статистики](PIL-21.md).
- [HTTP-обработчик](../src/server.ts), [HTTP-тесты](../test/server.test.ts), [API и запуск](../README.md).
- [Команды и зависимости](../package.json), [штатный CI](../.github/workflows/ci.yml).

## Согласуемый объём

1. Добавить маршрут в существующий HTTP-обработчик `src/server.ts`, используя текущий способ отправки JSON. Проверяется доступность процесса; состояние TODO и внешние сервисы не проверяются.
2. Добавить автоматический HTTP-тест в `test/server.test.ts` через существующий каркас: реальный сервер на свободном локальном порту, запрос через `fetch`, закрытие сервера после проверки. Прямой вызов функции вместо HTTP-запроса не заменяет этот тест.
3. Добавить строку `GET /health` с форматом ответа в таблицу API `README.md`.
4. При реализации оформить один PR в `main`, указав изменения, результаты штатных проверок и ссылку на PIL-76 в трекере. Использовать реальный URL задачи; не подменять его ссылкой на локальную спецификацию.

Допустимые изменения: `src/server.ts`, `test/server.test.ts`, `README.md`, `docs/PIL-76.md`. Новые зависимости, изменения модели TODO и конфигурации не требуются.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | Проверяющий отправляет `GET /health` запущенному API без авторизации | HTTP 200; `Content-Type: application/json; charset=utf-8`; разобранное JSON-тело строго равно `{"status":"ok"}`, без дополнительных полей. Пробелы в сериализации значения не имеют. |
| 2 | Запрос повторяется при пустом или заполненном списке TODO | Тот же успешный ответ; список TODO не изменяется. Маршрут не читает и не изменяет состояние задач. |
| 3 | `GET /health?probe=1` | Тот же ответ, query-параметры игнорируются в соответствии с маршрутизацией по `pathname`. |
| 4 | `GET /health/` или `POST /health` | Существующий HTTP 404 с JSON `{"error":"not found"}`; отдельная обработка методов и нормализация пути не вводятся. |
| 5 | Выполняются существующие операции TODO и статистики | Их статусы, тела ответов и поведение сохраняются; существующие тесты проходят. |
| 6 | Запускаются штатные проверки | `npm run check` и `npm test` проходят; новый HTTP-тест проверяет статус, JSON Content-Type и точное содержимое ответа `/health`. |
| 7 | Просматривается документация и PR реализации | README описывает маршрут и ответ; описание PR содержит ссылку на задачу PIL-76. |

## Исключения

- Readiness, диагностика БД и внешних сервисов, агрегированное состояние зависимостей.
- Метрики, uptime, версия сборки, диагностические данные и дополнительные поля ответа.
- Новые UI, авторизация, отдельный сервер или порт, мониторинг, деплой и инфраструктура.
- Рефакторинг HTTP-обработчика, изменение других маршрутов, новые зависимости.
- Особые ответы для HEAD/OPTIONS, код 405, перенаправления и нормализация завершающего слеша.
- Требования к SLA, нагрузке и времени ответа: численные пороги постановкой не заданы.

## Зависимости

- Существующие Node.js >=20, TypeScript и Vitest из [package.json](../package.json); внешние сервисы не нужны.
- Существующий экспорт `handle` и HTTP-каркас тестов; новые тестовые библиотеки не нужны.
- Для ссылки в PR нужен фактический URL PIL-76 из трекера на фазе оформления PR.
- Реализация начинается после утверждения этой редакции платформой.

## План проверки после утверждения

1. HTTP-тест обязательного контракта: реальный `GET /health`, статус 200, заголовок JSON с UTF-8, точное равенство разобранного тела `{ status: 'ok' }`.
2. Проверить повторный вызов и отсутствие изменений списка: создать TODO через API, сравнить `GET /todos` до и после запросов здоровья. Проверить query-параметр и граничные запросы из сценариев 3–4 в том же HTTP-каркасе.
3. Выполнить `npm run check` и полный `npm test`, включая существующую регрессию TODO и статистики. Сверить результат CI с текущим HEAD PR.
4. Просмотреть diff: изменения ограничены указанными файлами; README содержит маршрут; описание PR содержит рабочую ссылку на PIL-76.
