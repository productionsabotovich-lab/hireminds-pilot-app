# PIL-25 — Проверка доступности TODO API

Редакция 1. Статус: спецификация подготовлена, объём на утверждении; реализация не начата,
декомпозиция на задачи не выполнялась.

## Цель и основания

У TODO API нужен маршрут, по которому внешний наблюдатель (мониторинг, деплой, ручная проверка)
определяет, что процесс жив и отвечает по HTTP. Маршрут `GET /health` отвечает HTTP 200
с JSON `{"status":"ok"}` и ничего не говорит о содержимом списка дел.

Ключевые свойства, которые следуют из постановки и должны быть зафиксированы в объёме:

- проверка **не читает и не меняет** список TODO — это делает её независимой от состояния
  данных и безопасной для вызова в любой момент;
- маршрут покрыт **автоматической HTTP-проверкой** (тест через реальный сокет), а не только
  проверкой чистой функции;
- поведение существующих методов `/todos` **не меняется**;
- изменения ограничены репозиторием TODO API.

## Согласуемый объём

### 1. Чистая функция `healthStatus` (`src/todos.ts`)

- Экспортируется из `src/todos.ts` рядом с остальными чистыми функциями
  (`addTodo`, `completeTodo`, `listTodos`, `todoStats`), по именованию и стилю модуля.
- Сигнатура: `healthStatus(): HealthStatus`, где
  `export type HealthStatus = { status: 'ok' }` — литеральный тип `'ok'`, а не `string`,
  чтобы неправильное значение нельзя было выдать за штатное.
- **Аргументов нет.** Это и есть техническое выражение требования «проверка не читает список
  дел»: у функции нет доступа к `TodoList`, поэтому она физически не может его прочитать
  или изменить.
- Результат — объект **ровно с одним собственным ключом** `status` и значением `"ok"`.
  Никаких дополнительных полей (`uptime`, `version`, `timestamp`, счётчиков дел).
- Функция детерминирована: повторные вызовы дают равные результаты; состояние сервера
  не затрагивается.

### 2. Маршрут `GET /health` (`src/server.ts`)

- Обработчик добавляется в существующую цепочку `if` внутри `handle` в `src/server.ts`,
  до ветки 404; отдельный роутер, middleware и рефакторинг `handle` не вводятся.
- Ответ: HTTP **200**, заголовок `Content-Type: application/json; charset=utf-8`
  (существующий хелпер `send`), тело — результат `healthStatus()`, то есть ровно
  `{"status":"ok"}`. Ни обёртки, ни лишних ключей.
- Проверка **не читает и не меняет** список дел: состояние `state` в маршруте не
  используется и не присваивается; поведение `GET /todos`, `GET /todos/stats`,
  `POST /todos`, `POST /todos/:id/complete` не меняется.
- Параметры запроса игнорируются: `GET /health?verbose=1` (и любые другие query-параметры)
  отвечают тем же 200 и тем же телом; неизвестные параметры не приводят к ошибке.
- Путь сопоставляется точно: `/health` — единственный совпадающий путь. `/health/`,
  `/healthz`, `/api/health` получают существующий ответ 404 `{"error":"not found"}`.
- Метод, отличный от `GET` (в том числе `POST`, `PUT`, `DELETE`, `HEAD`), получает
  существующий ответ 404 `{"error":"not found"}` — новое поведение 405 и заголовок `Allow`
  не вводятся (это соответствует поведению остальных маршрутов приложения).
- «Нештатный случай» в границах приложения отсутствует: у процесса нет внешних
  зависимостей, которые проверка могла бы признать недоступными. Если процесс не
  запущен, клиент получает отказ соединения — это поведение уровня сети, а не ответа
  приложения, и в контракт маршрута не входит.

### 3. Проверки

Новых тестовых зависимостей нет. Проверки закрывают обе части критерия приёмки:
HTTP-поведение маршрута покрыто автоматически, чистая функция — отдельным кейсом.

#### 3.1. Чистая функция (`test/todos.test.ts`)

Кейсы добавляются в существующий файл `test/todos.test.ts`, отдельной группой
`healthStatus` рядом с группой `todoStats`. Существующие кейсы по смыслу не меняются.

- **Штатный статус**: `healthStatus()` → ровно `{ status: 'ok' }` (сравнение точное,
  по всему объекту: лишние ключи проверку не проходят).
- **Детерминированность**: два вызова подряд дают равные результаты.

#### 3.2. HTTP-маршрут (`test/server.test.ts`)

Кейсы добавляются в существующий файл `test/server.test.ts`, отдельной группой
`GET /health` рядом с группой `GET /todos/stats`. Используется уже настроенный в файле
каркас: сервер поднимается на реальном сокете (`createServer(handle)`,
`server.listen(0, '127.0.0.1')`), запросы выполняются глобальным `fetch` Node.js,
состояние изолируется через `vi.resetModules()` и динамический импорт
`const { handle } = await import('../src/server.js')`. Новый файл теста и новый
HTTP-клиент не нужны.

Обязательные HTTP-кейсы:

- **Штатный ответ**: `GET /health` → 200, `content-type: application/json; charset=utf-8`,
  тело ровно `{"status":"ok"}`.
- **Список дел не влияет на ответ**: добавить дела через `POST /todos`, одно завершить
  через `POST /todos/:id/complete` → `GET /health` всё равно отвечает ровно
  `{"status":"ok"}`; счётчики и содержимое списка в ответ не подмешиваются.
- **Проверка ничего не меняет**: `GET /todos` до и после `GET /health` отдаёт одинаковый
  список; повторный `GET /health` даёт тот же ответ.
- **Query-параметры игнорируются**: `GET /health?verbose=1` → 200 и то же тело.
- **Не-`GET`**: `POST /health` → 404 `{"error":"not found"}` (существующее поведение).
- **Близкие пути**: `GET /health/` и `GET /healthz` → 404 `{"error":"not found"}`.
- **Регрессия существующих маршрутов**: `GET /todos`, `GET /todos?filter=open`,
  `GET /todos?filter=done`, `GET /todos/stats`, `POST /todos`, `POST /todos/:id/complete`
  отвечают как раньше (прежние статусы и прежние тела ответов).

Замечания по окружению (не влияют на объём):

- `tsconfig.json` включает только `src` (`"include": ["src"]`), поэтому файлы в `test/`
  командой `npm run check` не проверяются; типы тестов проверяются вручную или в IDE.
- Vitest по умолчанию изолирует каждый тестовый файл, поэтому существующие файлы
  `test/todos.test.ts` и `test/server.test.ts` не влияют друг на друга.

3. **Метод `HEAD`.** Нужен ли `HEAD /health` (часто используется пробами)? Решение по
   умолчанию: нет, `HEAD` получает существующий 404, как и остальные не-`GET` маршруты.
4. **Ответ на не-`GET`.** Оставить 404 (текущее поведение приложения) или ввести 405
   с заголовком `Allow`? Решение по умолчанию: 404, новое поведение не вводится.
5. **Смысл проверки.** Подтвердить, что `/health` — это liveness-проверка «процесс отвечает
   по HTTP», без проверки данных и зависимостей. Решение по умолчанию: да, liveness;
   проверка списка дел в ответ не попадает.
6. **Путь маршрута.** Подтвердить, что путь — ровно `/health` (без версий и алиасов
   `/healthz`, `/livez`, `/readyz`, `/status`). Решение по умолчанию: да, ровно `/health`.
7. **Формат маршрута в API-документации.** Нужно ли обновлять `README.md` в этой же задаче
