# PIL-40 — Версия тестового API

Редакция 1. Статус: объём утверждён 2026-11-19; реализация выполнена в этой же ветке
(`src/server.ts`, `test/server.test.ts`, `README.md`).

## Цель и основания

Клиент E2E-проверки получает фиксированную версию тестового API через отдельный
HTTP-запрос, без изменения данных и обращения к внешним системам.

## Согласуемый объём и контракт

Добавить маршрут в существующий HTTP-обработчик, автоматические проверки его
поведения в существующий набор HTTP-тестов и короткую документацию в README.

- `GET /version` возвращает HTTP `200` и JSON ровно `{"version":"1"}`:
  единственное поле `version`, значение — строка `"1"`.
- Заголовок `Content-Type: application/json; charset=utf-8` соответствует
  принятому в приложении формату JSON-ответов.
- Значение фиксировано; оно не берётся из `package.json`, переменных окружения,
  Git, файлов, базы данных или внешних сервисов. Версия пакета не меняется.
- Ответ одинаков при пустом и заполненном списке TODO и повторных запросах.
- Запрос не меняет состояние процесса, в том числе список TODO и следующий ID;
  не выполняет внешних обращений и операций с хранилищем.
- Путь сопоставляется точно по pathname: query-параметры игнорируются;
  `/version/` и другие пути сохраняют ответ `404 {"error":"not found"}`.
- Для методов кроме `GET` на `/version` сохраняется существующий ответ 404.
  Отдельная поддержка `HEAD` и `OPTIONS` не добавляется; особенности тела HEAD
  определяются текущим HTTP-сервером Node.js.
- Сохраняются статусы, тела, фильтрация и ошибки существующих маршрутов:
  `GET /todos`, `GET /todos/stats`, `POST /todos`, `POST /todos/:id/complete`.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | E2E-клиент запрашивает `GET /version` | 200, указанный JSON Content-Type, тело ровно `{"version":"1"}`; число `1` и дополнительные поля недопустимы |
| 2 | Клиент повторяет запрос до и после создания и завершения TODO | Каждый ответ содержит ту же версию; список и сводка до и после запросов версии совпадают |
| 3 | После запроса версии клиент создаёт следующее TODO | Выдача ID продолжает обычную последовательность, запрос версии её не сдвигает |
| 4 | Клиент передаёт query, например `/version?probe=1` | Тот же ответ, что у `/version` |
| 5 | Клиент вызывает `POST /version` или `GET /version/` | Существующий ответ 404 с JSON `{"error":"not found"}` |
| 6 | Клиент использует прежние операции TODO | Существующее поведение API сохранено |
| 7 | Разработчик читает README | В таблице API есть `GET /version`, рядом короткий пример запроса и точного ответа |
| 8 | Выполняются автоматические проверки проекта | HTTP-тест проверяет статус и полное тело нового ответа; прежние тесты проходят |

Пример для README:

```sh
$ curl -s http://127.0.0.1:3000/version
{"version":"1"}
```

## Исключения и границы объёма

В объём реализации входят изменения `src/server.ts`, `test/server.test.ts`,
`README.md`; документ задачи — `docs/PIL-40.md`.

Вне объёма: новые зависимости, изменения модели TODO и `src/todos.ts`, новые
хранилища, UI, авторизация, динамическая версия сборки, версионирование URL API,
проверка готовности внешних сервисов, настройка E2E-инфраструктуры, изменения CI,
рефакторинг маршрутизации и обновление версии пакета. Название E2E не требует
нового тестового фреймворка: достаточно существующих HTTP-тестов Vitest.

## Зависимости

Используются существующие Node.js >=20, TypeScript, Vitest, HTTP-обработчик и
каркас HTTP-тестов с локальным сервером на свободном порту. Новые пакеты и внешние
сервисы не требуются. Реализация выполнена после утверждения этой редакции;
других продуктовых зависимостей нет.

## План проверки после реализации

1. В `test/server.test.ts` проверить реальным HTTP-запросом статус 200,
   Content-Type и полное JSON-тело с полем-строкой `version: "1"`.
2. В HTTP-сценарии с созданием и завершением TODO проверить повторяемость ответа,
   неизменность списка и сводки, а затем обычную выдачу следующего ID.
3. Проверить игнорирование query и сохранение 404 для `POST /version`
   и `GET /version/`.
4. Выполнить `npm run check` и `npm test`, включая существующие регрессионные
   проверки TODO и сводки. Использовать изоляцию и закрытие сервера из текущего
   каркаса тестов. Отсутствие внешних обращений дополнительно проверить просмотром
   изменения обработчика: ответ не должен зависеть от I/O или окружения.
5. Проверить пример README на собранном приложении (`npm run build`, `npm start`)
   запросом из примера; сопоставить ответ со спецификацией.
6. Перед PR проверить diff на соблюдение границ файлов и обязательные проверки CI.
