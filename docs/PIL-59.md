# PIL-59 — Чтение отсутствующей TODO

Редакция 1. Статус: подготовлена к утверждению объёма.

## Цель и основания

Закрепить HTTP 404 при чтении TODO с несуществующим идентификатором, добавить ровно
одну автоматическую проверку и пример запроса в документацию.

Основания: [постановка PIL-59](/opt/hireminds/context/issue.md),
[правила проекта](../CLAUDE.md), [правила документов](README.md),
[действующая спецификация PIL-21](PIL-21.md), [API](../README.md),
[HTTP-обработчик](../src/server.ts), [модель TODO](../src/todos.ts),
[HTTP-тесты](../test/server.test.ts), [команды проекта](../package.json).

В текущем HTTP-обработчике нет маршрута `GET /todos/:id`; он отвечает общим 404
даже для созданной записи. Поэтому требование постановки «существующее поведение для
найденной записи сохранить» не имеет реализованного аналога в данном checkout.
Эта редакция предлагает включить минимальное чтение найденной записи в согласуемый
объём; вопрос к PM приведён отдельно ниже.

## Согласуемый объём и сценарии

1. Клиент запрашивает `GET /todos/:id` с отсутствующим числовым идентификатором.
   Сервер возвращает HTTP 404, `Content-Type: application/json; charset=utf-8`,
   тело ровно `{"error":"not found"}` — существующий формат ошибки маршрутизации.
2. Клиент создаёт TODO через `POST /todos` и читает её по полученному `id`.
   Предлагаемый контракт: HTTP 200, тот же JSON Content-Type, тело — объект
   `{id, title, done}` без обёртки и дополнительных полей. Значения отражают текущее
   состояние, в том числе после завершения TODO.
3. Чтение не меняет список, содержимое TODO или следующий выдаваемый идентификатор.
   Повторный запрос при неизменном состоянии возвращает тот же результат.

Маршрут принимает сегмент из десятичных цифр, сопоставляемый целиком; поиск идёт
по числовому `id`. Query-параметры не влияют на результат. `/todos/stats` сохраняет
свой контракт. Нечисловой сегмент, лишние сегменты и завершающий слеш остаются
неизвестными путями с текущим 404. Новая валидация идентификаторов и статус 400
для них не вводятся. Другие методы не получают новый контракт.

## Критерии приёмки

- Оба сценария чтения выполняют описанный HTTP-контракт; отсутствующая запись
  не вызывает 200, 400 или 500.
- В `test/server.test.ts` добавлен ровно один автоматический кейс: создать запись,
  проверить её чтение с 200 и точным объектом, затем запросить гарантированно
  отсутствующий `id` и проверить 404, JSON Content-Type и точное тело ошибки.
  Обе проверки находятся в одном `it`, чтобы кейс отличал корректный маршрут от
  общего ответа 404. Используется существующий изолированный HTTP-каркас.
- В `README.md` описан `GET /todos/:id` и приведён воспроизводимый пример
  отсутствующей записи: на свежем сервере `curl -i http://127.0.0.1:3000/todos/999`,
  ожидаемые статус 404 и тело `{"error":"not found"}`. Указано условие отсутствия
  записи; пример не предполагает, что 999 отсутствует в любом состоянии.
- Существующие сценарии списка, статистики, создания и завершения TODO сохраняются.

## Границы и исключения

После утверждения предполагаются изменения только в `src/server.ts`,
`src/todos.ts` (если нужен чистый поиск записи), `test/server.test.ts`, `README.md`
и данной спецификации. Поиск в модели должен оставаться чистым, HTTP I/O — в сервере.

В объём не входят изменения платформенного механизма Stop → Retry, самостоятельное
управление остановкой этапа, новые E2E-инструменты, отдельный unit-тест поиска,
рефакторинг роутинга, зависимости, хранение данных, новые CRUD-операции,
изменение ошибок завершения TODO, CI и чужих спецификаций.
Название задачи задаёт контекст платформенной проверки; продуктовая доработка
ограничена TODO API, одной автоматической проверкой и документацией.

## Зависимости и план проверки

Зависимости: утверждение редакции с учётом вопроса к PM, Node.js >=20 и текущие
зависимости проекта. Дополнительные пакеты и сервисы не требуются.

После реализации:

1. Запустить `npm run check` и `npm test`; новый кейс и существующий набор проходят.
2. На собранном сервере вручную проверить пример 404, чтение созданной и завершённой
   записи, повторное чтение и неизменность списка после отсутствующего `id`.
3. Проверить сохранение `/todos/stats`, общий 404 для некорректного пути и отсутствие
   изменений вне согласованных файлов; убедиться, что добавлен ровно один тест.

В фазе спецификации реализация и запуск проверок приложения не выполняются.
Декомпозиция на задачи до утверждения не производится.

## Вопросы к PM

1. Подтвердить включение минимального успешного `GET /todos/:id` с ответом 200
   и объектом TODO: в текущем checkout такого маршрута нет, хотя постановка
   предполагает его существование. Редакция 1 включает этот контракт, чтобы
   проверка 404 подтверждала поиск отсутствующей записи. Если ожидается сохранение
   контракта из другой версии, необходима ссылка на эту версию и уточнение редакции
   до реализации.
