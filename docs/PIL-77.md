# PIL-77 — GET /health

Редакция 1. Статус: объём утверждён 2026-11-28; реализация выполнена в этой же ветке
(`src/server.ts`, `test/server.test.ts`).

## Цель и основания

Предоставить клиенту тестового API простой способ проверить, что сервер отвечает:
`GET /health` возвращает HTTP 200 и JSON `{"status":"ok"}`, не читая и не меняя список дел.

## Согласуемый объём

В существующий HTTP-обработчик добавляется только маршрут `GET /health`.
Ответ: статус 200, `Content-Type: application/json; charset=utf-8`, тело ровно
`{"status":"ok"}` без дополнительных полей. Ответ постоянный, не зависит от количества
или состояния дел. Обработчик маршрута не обращается к состоянию списка и функциям
работы с делами и не изменяет их.

Путь сопоставляется по `pathname`, как существующие маршруты: query-параметры
игнорируются (`GET /health?probe=1` возвращает тот же ответ). `/health/` и `/Health`
не являются этим маршрутом. Методы кроме GET, включая HEAD и POST, сохраняют
существующий ответ 404; для HEAD тело на уровне HTTP не требуется.

Проверки нового поведения добавляются в существующий `test/server.test.ts` с его
текущим HTTP-каркасом и изоляцией состояния. Изменения реализации ограничены
`src/server.ts` и `test/server.test.ts`; эта спецификация хранится в `docs/PIL-77.md`.
Изменение README не требуется. Правила границ файлов PIL-21 относятся к PIL-21;
эта редакция не пересматривает её API и критерии.

## Пользовательские сценарии и критерии приёмки

| Сценарий | Критерий |
| --- | --- |
| Клиент проверяет запущенный API с пустым списком | `GET /health` → 200, указанный JSON Content-Type, тело ровно `{"status":"ok"}` |
| В списке есть открытое и выполненное дело | Ответ `/health` такой же; повторный запрос даёт тот же ответ |
| Клиент вызывает `/health` между операциями с делами | Список и статистика до и после совпадают; следующее добавление получает ожидаемый следующий id |
| Запрос содержит query-параметры | `GET /health?probe=1` имеет тот же статус и тело |
| Использованы POST /health, GET /health/ или GET /Health | 404 с существующим JSON `{"error":"not found"}` |
| Клиент использует прежние маршруты | Поведение создания, завершения, фильтрации и статистики дел, а также обработки ошибок и неизвестных путей сохраняется |
| Изменение готово к передаче | В существующем HTTP-тесте проверено новое поведение; `npm run check` и `npm test` проходят |
| Результат оформлен после утверждения спецификации | Одна ветка и обычный, не draft, PR в main; описание содержит изменения, проверки и точный адрес исходной задачи из раздела оснований |

fetch. Для штатных проверок нужны установленные devDependencies. Новых сервисов и
внешних интеграций маршрут не требует. Для последующего открытия PR необходим доступ
к репозиторию; до утверждения этой редакции реализация и открытие PR не выполняются.

## План проверки

1. В существующем HTTP-тесте проверить точные статус, Content-Type и тело ответа на
   пустом списке; повторить запрос на смешанном состоянии и с query-параметром.
2. Сравнить список и статистику до и после запросов `/health`, затем добавить дело и
   проверить следующий id. Отсутствие чтения состояния подтвердить просмотром ветки
   маршрута: HTTP-наблюдения сами по себе не доказывают отсутствие чтения.
3. Проверить 404 для POST `/health` и несовпадающих путей; остальные регрессии
   покрывает существующий набор HTTP-тестов без изменения его ожиданий.
4. Выполнить штатные `npm run check` и `npm test`. Это план будущей проверки,
   а не заявление о выполнении тестов на фазе спецификации.
5. Проверить diff на соответствие границам файлов и отсутствие новых зависимостей
   и правок CI. При оформлении обычного PR проверить целевую ветку main и точный
   URL PIL-77 в описании.

## Ход реализации

1. `src/server.ts`: маршрут `GET /health` добавлен в существующий HTTP-обработчик и отвечает
   существующим помощником `send`, поэтому статус 200, заголовок
   `application/json; charset=utf-8` и тело ровно `{"status":"ok"}` совпадают с остальными
   маршрутами. Сопоставление пути точное (`url.pathname === '/health'`), query-параметры
   игнорируются, состояние списка дел не читается и не меняется, логика `src/todos.ts`
   не затронута.
2. `test/server.test.ts`: группа `GET /health` в существующем HTTP-каркасе (реальный сервер
   на свободном порту, запросы через `fetch`, закрытие сервера после кейса) — статус и
   content-type, точное тело `{"status":"ok"}`, единственное поле `status` со значением `ok`,
   повторные запросы без изменений списка и сводки и ожидаемый следующий id после них,
   игнорирование query-параметров, прежний 404 `{"error":"not found"}` для `GET /health/`,
   `GET /Health` и `POST /health`.
3. Изменения ограничены `src/server.ts`, `test/server.test.ts` и `docs/PIL-77.md`.
   `README.md` не менялся: по этой спецификации его изменение не требуется.
   Новые зависимости не добавлялись, `package.json`, `package-lock.json` и CI без изменений.
