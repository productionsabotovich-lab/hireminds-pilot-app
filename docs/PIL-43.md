# PIL-43 — E2E · Продолжение сессии Claude Code после уточнения

Редакция 1. Статус: спецификация подготовлена, объём не утверждён; реализация не начата.

## Цель и основания

Задача — сквозная (E2E) проверка того, что агентная сессия продолжается после уточнения
постановки и приводит к ожидаемому материальному результату в тестовом репозитории
TODO API. Материальный результат — один новый документ
`docs/hireminds-session-smoke-20261119.md` с заголовком «Проверка сессии Hireminds»
и строкой «Этот файл используется для сквозной проверки.».

Отличие PIL-43 от остальных задач пилота (например [PIL-21](PIL-21.md)): не добавляется
функциональность API и не меняется поведение существующих маршрутов. Единственное
новое поведение задачи — наличие файла-документа; код приложения остаётся нетронутым
достаточно, чтобы сквозная проверка выполнилась на неизменённом API.

## Согласуемый объём

### 1. Новый файл `docs/hireminds-session-smoke-20261119.md`

- Создаётся ровно один новый файл — `docs/hireminds-session-smoke-20261119.md`,
  в каталоге `docs/`, имя — ровно как указано в постановке, включая дату `20261119`
  в имени.
- Первая строка файла — заголовок первого уровня: `# Проверка сессии Hireminds`
  (один `#`, ровно один пробел, текст заголовка без кавычек).
- После заголовка — пустая строка, затем одна содержательная строка:
  `Этот файл используется для сквозной проверки.`
- Иных разделов, подзаголовков, списков, таблиц, блоков кода, ссылок и дополнительных
  абзацев в файле нет. Документ самодостаточен и сам является проверочным артефактом.
- Кодировка — UTF-8, перевод строки — LF, файл заканчивается переводом строки.
- Файл — статический, генерируемый и поддерживаемый вручную: скриптов, генераторов
  и зависимостей для его создания не добавляется.

### 2. Неизменность API и кода

- `src/todos.ts` и `src/server.ts` **не меняются**: маршруты `GET /todos`,
  `GET /todos/stats`, `POST /todos`, `POST /todos/:id/complete`, коды ответов, тела
  ответов, заголовки и обработка неизвестных путей сохраняются как есть.
- `test/todos.test.ts` и `test/server.test.ts` **не меняются**: новых кейсов не
  добавляется. Артефакт задачи — документ, а не поведение программы; критерий
  «новое поведение покрывается тестом в `test/`» к этой задаче неприменим
  (см. вопрос 2 к PM — если PM потребует автотест, объём расширяется на
  `test/` и фиксируется новой редакцией).
- `package.json`, `package-lock.json`, `tsconfig.json`, `CLAUDE.md`, `README.md`,
  `docs/README.md`, `.github/**` без изменений: новые зависимости не добавляются,
  команды `npm run check` и `npm test` остаются прежними.

### 3. Спецификация (`docs/PIL-43.md`)

- Этот файл — спецификация задачи по конвенции [docs/README.md](README.md)
  («один файл на задачу, имя — ключ задачи в трекере») и включается в PR реализации.
- Дополнительных документов (отчёта, чек-листа, заметок) не создаётся.

### 4. Границы файлов

После утверждения этой редакции допускаются изменения только в:

- `docs/hireminds-session-smoke-20261119.md` (новый файл);
- `docs/PIL-43.md` (эта спецификация).

Других файлов не создаётся и не меняется.

## Исключения и границы

Вне объёма (не делается в этой задаче):

- любые изменения HTTP API: новые маршруты, изменение формата ответов, кодов,
  заголовков, обработки ошибок и неизвестных путей;
- изменения `src/todos.ts`, `src/server.ts`, `test/`, `package.json`,
  `package-lock.json`, `tsconfig.json`, `CLAUDE.md`, `README.md`, `docs/README.md`,
  `.github/**`, CI и инфраструктуры;
- новые зависимости, скрипты, генераторы файла, CI-шаги, хуки и автопроверки
  содержимого документа;
- индексация нового файла в `docs/README.md` или `README.md`;
- переименование, перемещение и удаление существующих файлов `docs/`;
- правки чужих задач и веток (PIL-33, PIL-40, PIL-41, PIL-42, серия PIL-24xxx) —
  не трогаются;
- содержательное наполнение документа сверх заголовка и указанной строки.

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые TypeScript,
  Node.js `>=20` и Vitest; новый файл — обычный текст в `docs/`.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным,
  `npm ci` работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check`
  и `npm test`; обе доступны без сети.
- Особенность окружения (проверено при подготовке спецификации): в текущем окружении
  `NODE_ENV=production` и `npm config omit=dev`, поэтому обычный `npm ci`
  **не ставит** dev-зависимости; для `npm run check` и `npm test` нужен
  `npm ci --include=dev`. На содержимое репозитория это не влияет.
- Базовая проверка на текущем `main` пройдена: `npm run check` — без ошибок,
  `npm test` — 21 тест в двух файлах, все зелёные.

## План проверки

1. `npm ci --include=dev` (в окружении с `omit=dev`) — зависимости установлены.
2. `npm run check` — проверка типов проходит без ошибок.
3. `npm test` — все тесты vitest проходят; новых тестовых файлов нет, существующие
   кейсы не менялись.
4. Проверка артефакта: `head -1 docs/hireminds-session-smoke-20261119.md` → ровно
   `# Проверка сессии Hireminds`; `grep -Fx "Этот файл используется для сквозной проверки." docs/hireminds-session-smoke-20261119.md` → найдена ровно одна строка;
   `grep -cv '^#\|^\s*$\|Этот файл используется для сквозной проверки\.' docs/hireminds-session-smoke-20261119.md` → `0`;
   `file` / проверка окончания файла — UTF-8, LF, завершающий перевод строки.
5. Ручная проверка API на собранном сервере: `npm run build && npm start`, затем
   `GET /todos/stats` (ожидается `{"total":0,"open":0,"done":0}`),

   список), `POST /todos/stats` (404 `{"error":"not found"}`).
6. Проверка границ объёма: `git diff --name-only main...HEAD` показывает только
   `docs/hireminds-session-smoke-20261119.md` и `docs/PIL-43.md`;
   `git diff --stat main...HEAD` не содержит изменений в `src/`, `test/`,
   `package.json`, `package-lock.json`, `tsconfig.json`, `README.md`,
   `docs/README.md`, `.github/**`.
7. CI на HEAD PR выполняет `npm ci`, `npm run check`, `npm test` — все три шага зелёные.

## Вопросы к PM (не блокируют минимальный объём)

1. **Имя файла и конвенция документов.** [docs/README.md](README.md) требует, чтобы
   имя файла документа совпадало с ключом задачи (`PIL-43.md`), а постановка требует
   `docs/hireminds-session-smoke-20261119.md`. Следовать ли постановке буквально?
   Решение по умолчанию: да — создать ровно `docs/hireminds-session-smoke-20261119.md`,
   а `docs/PIL-43.md` оставить как спецификацию по конвенции; два файла не дублируют
   друг друга (артефакт проверки против спецификации).
2. **Автотест на наличие документа.** Нужна ли проверка в `test/` (например
   `test/docs.test.ts`), утверждающая наличие файла и его заголовка?
   Решение по умолчанию: нет — артефакт документационный, нового поведения программы
   нет, а критерий проекта о покрытии тестами распространяется на новое поведение.
3. **Индексация файла.** Нужно ли упоминать новый документ в `docs/README.md` или
   `README.md` (раздел «Структура»)? Решение по умолчанию: нет — оба файла описывают
   правила и структуру, а не перечень конкретных документов.
4. **Дата в имени файла.** Имя зафиксировано постановкой (`20261119`), даже если
   реализация будет позже. Решение по умолчанию: сохранить имя без изменений.
5. **Отчёт о сквозной проверке.** Нужно ли в PR отдельный раздел с фактическим
   выводом команд (включая прогон API)? Решение по умолчанию: да — раздел
   «Как проверено» с реальными выводами, как требует [CLAUDE.md](../CLAUDE.md).
