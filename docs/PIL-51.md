## Согласуемый объём и контракт

Добавляется только операция чтения `GET /todos/:id`. Поиск по числовому `id` выполняется чистой функцией `findTodo(list, id)` в `src/todos.ts` (`Todo | undefined`, вход не мутируется), HTTP-обработка остаётся в `src/server.ts`. Отсутствие результата поиска обрабатывается как 404, без попадания в общий обработчик исключений с ответом 400.

Для найденного дела ответ — HTTP 200 и JSON-объект ровно с полями `id: number`, `title: string`, `done: boolean`, без обёртки. Значения совпадают с текущим состоянием дела в списке. Пример: `{"id":1,"title":"Купить хлеб","done":false}`. Завершённое дело также доступно и возвращает `done: true`.

Для отсутствующего дела ответ — HTTP 404 и ровно `{"error":"not found"}`. Для обоих ответов используется `Content-Type: application/json; charset=utf-8`.

Маршрут принимает один сегмент из ASCII-цифр (`[0-9]+`), как существующий маршрут завершения. Ведущие нули допустимы: `/todos/01` читает дело 1. Сопоставление с числовым ID должно быть точным: небезопасное для JavaScript целое не должно округляться до ID существующего дела и получает 404. ID 0 также даёт 404, поскольку такие дела не создаются. Отрицательные, дробные, знаковые, буквенные сегменты и завершающий слеш не соответствуют маршруту и получают существующий 404. Новая ошибка 400 для идентификатора не вводится.

Query-параметры игнорируются, в том числе `filter`: `/todos/1?filter=done` возвращает дело 1 независимо от его состояния. Другие методы для `/todos/:id` сохраняют ответ неизвестного маршрута 404. Точное соответствие `/todos/stats` сохраняется: этот путь всегда возвращает сводку, а не обрабатывается как ID.

Чтение существующего и отсутствующего дела не меняет состояние: поля дел, состав и порядок списка, `nextId` и статистика сохраняются. Поведение остальных маршрутов, включая ошибки завершения отсутствующего дела, остаётся прежним.

В объём входят автоматические проверки, краткое описание нового маршрута и ответов 200/404 в README, а после утверждения и реализации — один открытый PR в `main` с описанием изменения и проверки. Реализация и проверки выполнены в этой же ветке и включаются в этот PR.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | Создать через POST два дела и прочитать каждое по возвращённому ID | 200, точное совпадение с соответствующим объектом POST; выбор выполняется по ID |
| 2 | Завершить одно дело и прочитать его повторно | 200, тот же ID и title, `done: true` |
| 3 | Прочитать отсутствующий ID в пустом и непустом списках | 404, ровно `{"error":"not found"}`, корректный JSON Content-Type |
| 4 | Прочитать существующее дело с query-параметрами и ведущими нулями | Тот же объект и статус 200 |
| 5 | Запросить ID 0, небезопасное целое, `/todos/abc`, `/todos/-1`, `/todos/1.5`, `/todos/1/` либо POST `/todos/1` | 404 в том же формате; неподходящий ID не возвращает чужое дело |
| 6 | Сравнить список и статистику до и после успешного и неуспешного чтения | Состояние и сводка совпадают; следующий POST продолжает обычную последовательность ID |
| 7 | Прочитать `/todos/stats` в пустом и смешанном списках, также с `?filter=open` | 200, прежний объект `total/open/done`; query не фильтрует сводку |
| 8 | Выполнить прежние сценарии списка, фильтрации, создания и завершения | Статусы и тела ответов сохраняются, существующие тесты проходят |
| 9 | Проверить результат реализации | Новое поведение покрыто тестами; README описывает маршрут; открыт PR в main |

## Исключения и ограничения

Вне объёма: UI, постоянное хранилище, авторизация, новые поля TODO, изменение форматов существующих ответов, новые операции изменения/удаления, кэширование, новые зависимости, переработка роутера, изменение CI и инфраструктуры. Название «E2E новой сборки» не расширяет явно заданный HTTP-сценарий до проверки платформы Hireminds.

Допустимые изменения реализации ограничены `src/todos.ts`, `src/server.ts`, тестами в `test/`, `README.md` и этой спецификацией. Декомпозиция на задачи не выполнялась.

## Зависимости

Node.js >=20, существующие TypeScript и Vitest; внешних сервисов нет. Данные находятся в памяти одного процесса и теряются при перезапуске. Для тестов нужны dev-зависимости из текущего lock-файла. Используется существующий HTTP-каркас с реальным локальным сокетом, встроенным fetch, изолированным состоянием на кейс и закрытием сервера. Зависимости и lock-файл не меняются.

## План проверки

1. Проверить чистый поиск: существующее и отсутствующее дело, актуальное значение `done`, отсутствие мутаций входа.
2. В HTTP-тестах проверить критерии 1–7: реальные запросы к `handle`, точные статусы, JSON-тела и Content-Type; состояние подготавливать через публичный API, ID брать из POST.
3. Выполнить `npm run check`, `npm test` и `npm run build`. Сохранить все существующие проверки статистики и остальных маршрутов.
4. На собранном сервере выполнить сквозной сценарий: POST двух дел → GET по ID → завершение → повторный GET → GET отсутствующего ID → GET `/todos/stats`. Ожидать актуальный TODO, 404 и сводку `{total:2,open:1,done:1}`; сервер остановить после проверки.
5. Проверить границы diff, документацию и открытый PR в main; обязательные проверки CI должны проходить на актуальном HEAD PR.
