# PIL-47 — Проверка готовности TODO API

Редакция 1 от 2026-11-22. Статус: объём согласован (решение D-19, 2026-11-22), реализация выполнена.

## Цель и основания

Предоставить клиенту простой HTTP-запрос для проверки доступности обработчика API
независимо от содержимого списка дел. Задача служит контрольным изменением после
восстановления подключения Hireminds; настройка подключения не входит в изменение приложения.

## Согласуемый объём

После утверждения добавить `GET /health/readiness` в существующий HTTP-обработчик,
покрыть его HTTP-тестом и добавить один пример вызова в README.

Контракт:

- HTTP 200; `Content-Type: application/json; charset=utf-8`.
- Тело ровно `{"ready":true}`: единственное поле `ready`, значение — boolean `true`.
- Ответ постоянный при любом корректном состоянии TODO: пустом, с открытыми
  и выполненными делами. Обработчик не читает и не изменяет состояние списка,
  не вызывает операции TODO и не обращается к внешним сервисам.
- Повторные запросы дают тот же ответ без побочных эффектов.
- Путь сопоставляется точно и с учётом регистра. Query-параметры игнорируются,
  как при сопоставлении существующих маршрутов по `url.pathname`.
- Для других методов на этом пути сохраняется действующий ответ 404;
  для `HEAD` тело отсутствует согласно HTTP-семантике Node.js.
  Неизвестные пути, включая `/health/readiness/`, также сохраняют 404.
- Действующие маршруты, их статусы, форматы ответов, фильтры и обработка ошибок
  сохраняются, включая `GET /todos/stats` из PIL-21.

Допустимые файлы изменения: `src/server.ts`, `test/server.test.ts`, `README.md`
и эта спецификация `docs/PIL-47.md`. Используются существующий JSON-хелпер
и каркас HTTP-тестов. Новые модули и рефакторинг не требуются.

## Пользовательские сценарии и критерии приёмки

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | Клиент проверяет только что запущенный API с пустым списком | `GET /health/readiness` возвращает 200, JSON Content-Type и ровно `{"ready":true}` |
| 2 | Клиент проверяет API после создания дел и завершения одного из них | Тот же статус, Content-Type и тело; содержимое TODO на ответ не влияет |
| 3 | Клиент повторяет проверку при непустом списке | Ответ одинаковый; `GET /todos` до и после проверок возвращает одинаковый список |
| 4 | Клиент передаёт query-параметры, например `?filter=open` | Ответ тот же, параметры не влияют на готовность |
| 5 | Клиент делает `POST /health/readiness` или `GET /health/readiness/` | 404 и действующее JSON-тело `{"error":"not found"}` |
| 6 | Клиент использует существующий TODO API | Прежние сценарии и HTTP-тесты проходят без изменения ожидаемого поведения |
| 7 | Разработчик читает README | В разделе API описан маршрут и приведён один пример вызова с ожидаемым JSON |
| 8 | Проверка состава изменения | Зависимости и файлы за пределами согласуемого объёма не изменены |

Пример, который должен появиться в README:

```sh
curl -s http://127.0.0.1:3000/health/readiness
# {"ready":true}
```

## Исключения и границы

Вне объёма: проверки БД, сети и сторонних сервисов; ответ `ready:false`, HTTP 503
и управление состоянием готовности; отдельный liveness-маршрут; метрики,
мониторинг, оркестратор и CI; авторизация; UI; хранение и восстановление TODO;
изменение модели и функций `src/todos.ts`; настройка подключения Hireminds
и автоматизация E2E платформы. Название задачи не расширяет явную постановку.

## Зависимости

Нужны существующие Node.js >=20, TypeScript и Vitest из [package.json](../package.json).
HTTP-тест использует реальный локальный сервер на свободном порту и встроенный `fetch`
по [существующему каркасу](../test/server.test.ts), с изоляцией состояния и закрытием
сервера после теста. Новых зависимостей, внешних сервисов и изменений lock-файла нет.
Начало реализации зависит от утверждения этой редакции спецификации.

## План проверки после утверждения

1. Добавить HTTP-проверку контракта на пустом списке и после создания смешанного
   списка; сверить точное тело, статус и Content-Type. Сравнить список до и после
   повторных readiness-запросов. Это можно объединить в один сценарный HTTP-тест.
2. В HTTP-проверках подтвердить игнорирование query-параметров и сохранение 404
   для POST и пути с завершающим слешем.
3. Выполнить `npm run check` и `npm test`; существующие тесты TODO и статистики
   должны проходить вместе с новыми проверками readiness.
4. Выполнить `npm run build`, запустить собранный сервер через `npm start`
   и сверить пример README с реальным ответом.
5. Проверить diff: только согласованные файлы, один пример readiness в README,
   без изменений зависимостей, существующих контрактов и инфраструктуры.

## Реализация

Изменены только согласованные файлы: `src/server.ts`, `test/server.test.ts`, `README.md` и эта
спецификация. Зависимости, lock-файл, `src/todos.ts`, существующие маршруты и инфраструктура не тронуты.

- `src/server.ts`: маршрут `GET /health/readiness` в существующем HTTP-обработчике рядом с
  остальными; ответ — 200 и `{"ready":true}` через уже имеющийся JSON-хелпер `send`.
  Состояние списка дел не читается и не изменяется, внешние сервисы не вызываются.
- `test/server.test.ts`: шесть HTTP-проверок в блоке `GET /health/readiness` — контракт на
  пустом и смешанном списке, отсутствие побочных эффектов для списка дел, игнорирование
  query-параметров, сохранение 404 для `POST`, пути с завершающим слешем и другого регистра,
  а также пустое тело для `HEAD`.
- `README.md`: маршрут в таблице API, пояснение независимости от списка дел и один пример вызова.

Проверки: `npm run check` и `npm test` проходят (27 тестов, из них 6 новых); `npm run build`
и запуск собранного сервера подтвердили пример README.
