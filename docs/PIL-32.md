# PIL-32 — Удаление дела по идентификатору

Редакция 1. Статус: спецификация подготовлена к утверждению объёма; реализация не начата.

## Цель и основания

Клиенту HTTP-API нужно удалять одно дело по его идентификатору: `DELETE /todos/:id`.
Постановка требует:

- после удаления существующего дела — HTTP **204** с **пустым телом**;
- для неизвестного числового идентификатора — **404**;
- удаление не меняет другие дела;
- удалённое дело исчезает из списка и из статистики;
- новое поведение покрыто автоматическими проверками, в `README.md` приведён пример;
- остальные маршруты сохраняют текущее поведение.

Задача — первая часть серии проверки полного цикла Hireminds на тестовом репозитории
`hireminds-pilot-app` (E2E 1/3). Реализация других частей серии в эту задачу не входит:
объём ограничен одним маршрутом удаления, остальные пары «метод + путь» сохраняют текущий
ответ 404 (вопрос 5 к PM).

### Текущее поведение (проверено в этом окружении, Node.js v22.23.4)

- `DELETE /todos/1` → **404** `{"error":"not found"}`: в `handle` нет ни одной ветки для
  метода `DELETE`, запрос попадает в общую ветку неизвестного маршрута.
- `DELETE /todos` → **404** `{"error":"not found"}`; `DELETE /todos/abc` → **404**
  `{"error":"not found"}`; `DELETE /todos/1/complete` → **404** `{"error":"not found"}`.
- `POST /todos/999/complete` → **400** `{"error":"todo 999 not found"}`: неизвестное дело в
  существующем POST-маршруте даёт 400 (ошибка из `completeTodo` попадает в общий
  обработчик исключений), а не 404. Это различие существенно: постановка требует от
  `DELETE` именно 404, поэтому «отсутствующее дело» и «неизвестный путь» для `DELETE`
  различаются, а для `POST /todos/:id/complete` — нет.
- `GET /todos` → **200**, JSON-массив дел; `GET /todos/stats` → **200**
  `{"total":N,"open":N,"done":N}`; `POST /todos` → **201** с телом дела.
- Состояние живёт в памяти процесса, `nextId` только растёт (идентификаторы не переиспользуются).

Прототип ответа 204 (проверен в этом окружении): `res.writeHead(204); res.end()` даёт
**204**, **0 байт** тела на уровне сокета и не добавляет ни `Content-Type`, ни
`Content-Length`. Хелпер `send` для этого не подходит: он пишет JSON-тело и заголовок
`content-type`. Проверено также, что `DELETE` с телом запроса отвечает корректно
(тело запроса просто игнорируется), как и существующий `POST /todos/:id/complete`.

## Согласуемый объём

### 1. Чистая функция `deleteTodo` (`src/todos.ts`)

- Экспортируется из `src/todos.ts` рядом с остальными чистыми функциями (`addTodo`,
  `completeTodo`, `listTodos`, `todoStats`), по именованию и стилю существующих функций.
  Логика удаления — в `src/todos.ts` чистой функцией, как требует
  [правило проекта](../CLAUDE.md); I/O остаётся только в `src/server.ts`.
- Сигнатура: `deleteTodo(list: TodoList, id: number): TodoList`. Вход — существующий тип
  `TodoList` (`{ nextId, items }`); новые типы для входа не вводятся.
- Результат — новый `TodoList`:
  - в `items` нет дела с указанным `id`;
  - остальные дела сохранены **как есть**: те же значения, тот же порядок, та же
    идентичность объектов; флаг `done` у оставшихся дел не меняется;
  - `nextId` **не меняется**: удалённое дело не занимает идентификатор, и следующее
    добавленное дело получает `nextId + 1` (идентификаторы не переиспользуются).
- Если дела с таким `id` в списке нет, функция бросает `Error('todo <id> not found')` —
  так же, как `completeTodo`. Проверка существования делается внутри функции, а не в
  вызывающем коде.
- Функция **не мутирует** вход: не меняет `list`, `list.nextId`, массив `list.items`
  (ссылка, длина, порядок), поля и идентичность элементов. Вызов на замороженном входе
  (`Object.freeze`) не бросает исключений.
- Функция детерминирована: повторные вызовы с одним и тем же состоянием дают равные
  результаты.
- Допустимый способ реализации (на выбор разработчика): отбор через `filter`
  (`items.filter((t) => t.id !== id)`) либо через `map`/редьюс; проверка существования
  через `some`. Наблюдаемый результат одинаков.

### 2. Маршрут `DELETE /todos/:id` (`src/server.ts`)

- Обработчик добавляется в существующий `handle` в `src/server.ts`; состояние читается
  из текущей переменной `state`. Новое хранилище, новые модули, отдельный файл-роутер
  и middleware не вводятся; существующие ветки `if` и их порядок не меняются.
- Путь сопоставляется шаблоном `/^\/todos\/(\d+)$/` — по образцу существующего шаблона
  `/^\/todos\/(\d+)\/complete$/`:
  - идентификатор — десятичное целое число; ведущие нули допустимы
    (`DELETE /todos/007` соответствует делу с `id` 7, как и в существующем
    `POST /todos/:id/complete`);
  - нечисловой идентификатор (`/todos/abc`), отрицательный (`/todos/-1`), пустой
    (`/todos/`) и путь с дополнительным сегментом (`/todos/1/complete`) под шаблон **не
    подходят** → общий ответ 404 `{"error":"not found"}` (текущее поведение).
- Ответ при успешном удалении существующего дела:
  - HTTP **204 No Content**;
  - **тело пустое** — 0 байт, переданных в сокет (не `null`, не `{}`, не пустая строка);
  - **заголовков представления нет**: ни `Content-Type`, ни `Content-Length` (проверено
    прототипом). Рекомендуемая реализация — `res.writeHead(204); res.end();`;
    переиспользовать хелпер `send` нельзя, он пишет JSON-тело и `content-type`;
  - тело запроса игнорируется; query-параметры (в том числе `filter`) игнорируются:
    `DELETE /todos/1?filter=open` удаляет дело 1 и отвечает 204.
- Ответ для неизвестного числового идентификатора (в том числе повторное удаление уже
  удалённого дела): HTTP **404**, тело — существующий общий ответ неизвестного маршрута
  `{"error":"not found"}` (вопрос 1 к PM).
- **Порядок проверок обязателен**: обработчик `DELETE` сначала проверяет наличие дела в
  текущем состоянии и, если дела нет, отвечает 404; и только затем вызывает `deleteTodo`
  и отвечает 204. Общий обработчик исключений в `handle` отвечает 400, поэтому
  реализация «вызвать `deleteTodo` и отдать исключение в общий catch» дала бы 400 вместо
  требуемого 404.
- Допустимая альтернатива (тот же наблюдаемый контракт): `deleteTodo` не бросает
  исключение, а возвращает признак удаления (например `{ list, deleted: boolean }`),
  а обработчик по нему выбирает 404 или 204. В этом случае исключение из `deleteTodo`
  не бросается вовсе.
- Все остальные пары «метод + путь» сохраняют текущее поведение **404**
  `{"error":"not found"}`: `DELETE /todos` (без идентификатора), `DELETE /todos/abc`,
  `DELETE /todos/1/complete`, `PUT`/`PATCH`/`POST`/`OPTIONS` на `/todos/:id` и прочие.
  Код `405 Method Not Allowed` и заголовок `Allow` не вводятся.
- Существующее поведение `GET /todos`, `GET /todos?filter=open|done`, `GET /todos/stats`,
  `POST /todos`, `POST /todos/:id/complete` **не меняется**: прежние статусы и прежние тела
  ответов. В частности, `POST /todos/999/complete` по-прежнему даёт 400
  `{"error":"todo 999 not found"}` — приведение этого ответа к 404 в объём задачи не
  входит (вопрос 2 к PM).

### 3. Проверки

Новых тестовых зависимостей нет: используются уже подключённые Vitest, встроенный
`node:http` и глобальный `fetch` Node.js.

#### 3.1. Чистая функция (`test/todos.test.ts`)

Кейсы добавляются в существующий файл `test/todos.test.ts`, рядом с текущей группой
`todos`. Существующие кейсы по смыслу не меняются. Обязательные кейсы:

- **Удаление существующего дела**: дело исчезает из списка, остальные дела сохранены —
  те же значения, тот же порядок, та же идентичность объектов; `nextId` не изменился.
- **Удаление выполненного дела** (`done: true`): дело исчезает так же, как открытое.
- **Удаление последнего дела**: список пуст, `nextId` не изменился.
- **Неизвестный идентификатор**: `deleteTodo(list, 9)` бросает `Error` с сообщением
  `todo 9 not found` (как `completeTodo`).
- **Отсутствие мутаций**: снимок состояния (ссылка на `list`, значение `nextId`, ссылка и
  содержимое массива `items`, порядок элементов, поля и идентичность каждого элемента)
  до и после вызова совпадает; вызов на замороженном входе (`Object.freeze`) не бросает
  исключений.
- **Детерминированность**: два вызова подряд на неизменённом состоянии дают равные
  результаты.

#### 3.2. HTTP-маршрут (`test/server.test.ts`)

Кейсы добавляются в существующий файл `test/server.test.ts` отдельной группой
`describe('DELETE /todos/:id')`. Изоляция состояния уже настроена в этом файле:
перед каждым кейсом выполняется `vi.resetModules()` и модуль `src/server.ts` импортируется
заново, поэтому состояние начинается пустым. Сервер поднимается на свободном порту
(`listen(0, '127.0.0.1')`), HTTP-запросы выполняются глобальным `fetch` Node.js;
дополнительно понадобится хелпер `delete` рядом с существующими `get` и `post`.

Обязательные кейсы:

- **Успешное удаление**: `DELETE /todos/:id` существующего дела → **204**, тело пустое:
  `await res.text()` равно `''`, а на уровне сокета тело равно **0 байт**. Байтовая
  проверка выполняется сырым запросом из `node:http`
  (`request(..., { method: 'DELETE' })`): только она доказывает, что сервер не отправил
  байты тела. Дополнительно проверяется отсутствие заголовка `Content-Length`.
- **Дело исчезло из списка и из статистики**: `GET /todos` до и после удаления — дело
  отсутствует; `GET /todos/stats` — `total` уменьшился на 1, а `open` или `done`
  уменьшился на 1 в зависимости от состояния удалённого дела; инвариант
  `total === open + done` сохраняется. Отдельно проверяется, что удалённое дело
  отсутствует в `GET /todos?filter=open` и в `GET /todos?filter=done` (в списке нужного
  фильтра), а в списке *противоположного* фильтра его тоже нет.
- **Другие дела не изменились**: значения, порядок и флаги `done` оставшихся дел
  совпадают со снимком до удаления.
- **Неизвестный числовой идентификатор**: `DELETE /todos/999` → **404**
  `{"error":"not found"}`.
- **Повторное удаление того же дела**: после успешного удаления повторный
  `DELETE /todos/:id` → **404** `{"error":"not found"}`.
- **Пути вне шаблона**: `DELETE /todos` → 404, `DELETE /todos/abc` → 404,
  `DELETE /todos/1/complete` → 404 — все с телом `{"error":"not found"}`.
- **Query-параметры игнорируются**: `DELETE /todos/1?filter=open` → 204, дело удалено.
- **Тело запроса игнорируется**: `DELETE /todos/:id` с JSON-телом → 204, дело удалено
  (тело не влияет на результат).
- **Регрессия существующих маршрутов**: `GET /todos`, `GET /todos?filter=open`,
  `GET /todos?filter=done`, `GET /todos/stats`, `POST /todos`, `POST /todos/:id/complete`
  отвечают как раньше (прежние статусы и прежние тела ответов).

## Исключения и границы

Вне объёма (не делается в этой задаче):

- удаление всех дел разом: `DELETE /todos`, `DELETE /todos` с телом `{ "ids": [...] }`,
  параметр `?all=true` — текущий ответ 404 сохраняется;
- изменение дела: `PUT /todos/:id`, `PATCH /todos/:id` — текущий ответ 404 сохраняется;
  эти маршруты могут входить в следующие части серии E2E (вопрос 5 к PM);
- чтение одного дела: `GET /todos/:id` — текущий ответ 404 сохраняется;
- мягкое удаление, корзина, восстановление, отметка «удалено», поле `deletedAt` в модели
  `Todo` — удаление окончательное, дело исчезает из состояния;
- возврат удалённого дела в теле ответа (200 с объектом дела) — постановка требует 204
  с пустым телом;
- переиспользование освободившегося идентификатора: `nextId` не уменьшается;

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые TypeScript,
  Node.js `>=20` (`node:http`, глобальный `fetch`) и Vitest; HTTP-клиент из зависимостей
  не нужен.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным,
  `npm ci` работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check` и `npm test`;
  обе доступны без сети.
- Особенность окружения (проверено): в текущем окружении `NODE_ENV=production` и
  `npm config omit=dev`, поэтому обычный `npm ci` **не ставит** dev-зависимости;
  для `npm run check` и `npm test` нужен `npm ci --include=dev`. На содержимое репозитория
  это не влияет.
- Особенность проекта: `tsconfig.json` включает только `src`, поэтому файлы в `test/`
  **не** проверяются командой `npm run check` — типы тестов проверяются вручную или в IDE.
  Сборка `npm run build` тоже затрагивает только `src`.
- В окружении отсутствует `curl`, поэтому ручные проверки выполняются Node-однострочниками
  (см. план проверки); для пользователя эквивалент — `curl -i -X DELETE
  http://127.0.0.1:3000/todos/1`.
- Спецификация (`docs/PIL-32.md`) включается в PR реализации.

## Вопросы к PM (не блокируют минимальный объём)

1. **Тело ответа 404 для неизвестного идентификатора.** Для `DELETE /todos/999` предлагается
   общий ответ неизвестного маршрута `{"error":"not found"}` — так ответ выглядит одинаково
   для «неизвестный путь» и «неизвестное дело». Нужен ли более конкретный текст, например
   `{"error":"todo 999 not found"}`, как у `POST /todos/:id/complete`? Решение по умолчанию:
   **общий `{"error":"not found"}`** — новый формат ошибок не вводится.
2. **Несогласованность 404 и 400 между `DELETE` и `POST /todos/:id/complete`.** Удаление
   неизвестного дела даёт 404 (требование постановки), а завершение неизвестного дела —
   400 `{"error":"todo N not found"}` (текущее поведение). Приводить ли `POST` к 404 в этой же
   задаче? Решение по умолчанию: **нет**, `POST` не трогаем — правка существующего маршрута
   вне объёма.
3. **Заголовки ответа 204.** Рекомендуется отвечать без `Content-Type` и без
   `Content-Length` (проверено прототипом: 204 и 0 байт тела). Нужен ли
   `Content-Type: application/json; charset=utf-8` ради единообразия с остальными
   маршрутами? Решение по умолчанию: **не добавлять** — у ответа без тела заголовок
   представления не имеет смысла.
4. **Повторное удаление.** По умолчанию второй `DELETE` того же id даёт 404 («неизвестный
   числовой идентификатор»). Нужна ли идемпотентность, то есть 204 на повторный запрос?
   Решение по умолчанию: **404**, как следует из текста постановки.
5. **Границы серии E2E 1/3–3/3.** Какие маршруты входят в части 2/3 и 3/3 (например,
   `PUT`/`PATCH /todos/:id`, `DELETE /todos` без идентификатора)? Решение по умолчанию:
   **эта задача реализует только `DELETE /todos/:id`**, все прочие пары «метод + путь»
   остаются с текущим ответом 404, чтобы не забегать вперёд и не пересекаться с
   последующими частями серии.
6. **Идентификаторы после удаления.** По умолчанию удалённый id не переиспользуется
   (`nextId` только растёт). Нужно ли выдавать освободившийся id следующему новому делу?
   Решение по умолчанию: **нет**, поведение как у существующего `addTodo`.
7. **Аудит удаления.** Нужно ли сохранять сведения об удалённом деле (журнал, счётчик
   удалённых, `deletedAt`)? Решение по умолчанию: **нет**, удаление окончательное и
   необратимое, модель `Todo`/`TodoList` не меняется.
