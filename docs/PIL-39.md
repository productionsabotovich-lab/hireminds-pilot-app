# PIL-39 — GET /livez в тестовом API

Редакция 1 от 2026-11-19. Статус: предложена к утверждению объёма.

## Цель и основания

Клиенту тестового API нужен простой HTTP-запрос для проверки, что приложение
отвечает. `GET /livez` возвращает постоянный ответ независимо от списка дел.

## Согласуемый объём

1. Добавить обработку `GET /livez` в существующий HTTP-обработчик
   `src/server.ts`, используя существующий способ отправки JSON.
2. Добавить проверки нового HTTP-поведения в `test/server.test.ts` на
   существующем локальном сервере с автоматически выбранным портом.
3. Добавить строку в таблицу API и короткий пример запроса и ответа в README:
   `curl -s http://127.0.0.1:3000/livez` → `{"alive":true}`.

Допустимые файлы реализации: `src/server.ts`, `test/server.test.ts`, `README.md`.
Спецификация хранится в `docs/PIL-39.md`. Другие файлы, зависимости, модель
списка дел и инфраструктура не требуют изменений.

## Контракт и пользовательские сценарии

| Сценарий | Критерий приёмки |
| --- | --- |
| Клиент проверяет работоспособность запущенного API | `GET /livez` возвращает HTTP 200, `Content-Type: application/json; charset=utf-8`, JSON ровно `{"alive":true}`: одно поле `alive` со значением boolean `true` |
| Клиент повторяет проверку на пустом или заполненном списке | Каждый запрос возвращает тот же статус и JSON; результат не зависит от числа дел и их состояния |
| Проверка выполняется между операциями над делами | Запрос не добавляет, не удаляет и не меняет дела, порядок, идентификаторы или счётчик следующего идентификатора |
| Внешние сервисы недоступны | Маршрут не обращается к внешним сервисам, не проверяет их состояние и не требует новых настроек |
| Клиент передаёт query-параметры, например `/livez?probe=1` | Параметры игнорируются, ответ совпадает с `GET /livez` |
| Клиент обращается к `/livez/` или отправляет метод, отличный от GET, на `/livez` | Сохраняется существующий ответ 404 с JSON `{"error":"not found"}`; автоматическое преобразование HEAD в GET не добавляется |
| Клиент использует существующие маршруты | Статусы, тела ответов, фильтры и ошибки существующих операций остаются прежними |
| Читатель знакомится с README | В таблице API есть маршрут, рядом приведён короткий пример запроса и ответа |

Сопоставление выполняется по точному `pathname` и методу, как у существующих
маршрутов. Порядок байтов и пробелы JSON не являются отдельным контрактом;
важны точная структура и тип значения. Запрос не читает тело и не использует
состояние TODO для формирования ответа.

## Исключения и границы

Вне объёма: readiness-проверки, диагностика БД и других сервисов, дополнительные
поля (версия, время, uptime), альтернативные пути health-check, авторизация,
метрики, UI, настройка инфраструктурных probes и CI, новый E2E-фреймворк,
рефакторинг маршрутизации и изменения существующих API. Название задачи E2E
не требует создания отдельного приложения или стенда: HTTP-контракт
проверяется через существующий серверный тест.

## Зависимости

Достаточны Node.js >=20, встроенный `node:http` и `fetch`, существующие
TypeScript и Vitest из [package.json](../package.json). Новые пакеты,
переменные окружения и внешние сервисы не нужны. Для запуска проверок нужны
установленные dev-зависимости. Используется существующая изоляция состояния
и закрытие сервера в [test/server.test.ts](../test/server.test.ts).

## План проверки после утверждения и реализации

1. HTTP-тест: `GET /livez` на пустом списке — статус 200, JSON Content-Type,
   точное равенство разобранного тела `{ alive: true }` без дополнительных полей.
2. HTTP-тест отсутствия побочных эффектов: создать два дела, завершить одно,
   сохранить список и статистику, дважды запросить `/livez`; ответы одинаковы,
   список и статистика прежние. Следующее созданное дело получает следующий
   последовательный id.
3. Небольшие HTTP-проверки границ: `/livez?probe=1` даёт успешный ответ,
   `/livez/` и `POST /livez` дают прежний JSON 404. Для HEAD проверяется статус
   404 без требования тела, поскольку HTTP подавляет тело HEAD-ответа.
4. Проверка кода маршрута: нет внешних вызовов, чтения/записи состояния,
   чтения тела запроса или новых зависимостей.
5. Выполнить `npm run check` и `npm test`, включая существующие тесты
   операций TODO и статистики. Выполнить `npm run build` и проверить пример
   README на запущенном собранном сервере.
6. Проверить diff: изменения ограничены согласованными файлами; README
   содержит рабочий пример. Сохранить результаты проверок в отчёте реализации.

## Вопросы к PM

Нерешённых продуктовых вопросов нет. Точное сопоставление пути, игнорирование

в соответствии с текущим устройством API.
