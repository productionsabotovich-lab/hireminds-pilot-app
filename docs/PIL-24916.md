## Контракт

`todoStats(list: TodoList)` — чистая экспортируемая функция в `src/todos.ts`.
Вход — существующая модель `TodoList`, а не массив. Результат содержит ровно
три числовых поля `{ total, open, done }`:

- `total` — количество элементов `list.items`;
- `open` — количество элементов с `done === false`;
- `done` — количество элементов с `done === true`.

Для корректного `TodoList` все значения — неотрицательные целые числа,
`total === open + done`. Значение `nextId` не участвует в расчёте.
Вызов не изменяет входной объект, `nextId`, массив `items`, его порядок,
ссылки на элементы и поля элементов. Повторный вызов для неизменённого списка
даёт тот же результат. Валидация некорректных данных вне модели TypeScript
в объём не входит.

`GET /todos/stats` в `src/server.ts` возвращает HTTP 200,
`Content-Type: application/json; charset=utf-8` и результат `todoStats`
для всего текущего состояния процесса, без обёртки и дополнительных полей.
Запрос не изменяет состояние. Параметры запроса, включая `filter`, не влияют
на статистику: фильтрация относится только к существующему `GET /todos`.
Данные по-прежнему хранятся в памяти и обнуляются при перезапуске.
Другие методы для нового пути используют существующий ответ 404.

## Пользовательские сценарии и критерии приёмки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Список пуст | Функция и эндпоинт возвращают ровно `{ "total": 0, "open": 0, "done": 0 }` |
| Есть три дела, одно выполнено | Ровно `{ "total": 3, "open": 2, "done": 1 }` |
| Все два дела выполнены | Ровно `{ "total": 2, "open": 0, "done": 2 }` |
| Добавлено открытое дело | Следующий запрос увеличивает `total` и `open` на 1, `done` остаётся прежним |
| Открытое дело завершено | Следующий запрос сохраняет `total`, уменьшает `open` на 1 и увеличивает `done` на 1 |
| Статистика запрошена повторно | Счётчики и исходный список не меняются |

Дополнительные критерии:

- Тесты в `test/todos.test.ts` покрывают пустой список, смешанные состояния,
  все выполненные дела и отсутствие мутаций входа и его элементов.
- Проверка отсутствия мутаций охватывает весь список, включая `nextId`,
  содержимое и порядок `items`, ссылки на массив и элементы; допустимо
  использовать замороженный вход и сравнение со снимком значений.
- README содержит метод, путь, назначение и пример ответа нового эндпоинта.
- Существующие добавление, завершение и фильтрация дел сохраняют поведение.
- Новые зависимости отсутствуют, изменения ограничены пятью указанными файлами.

## Исключения и зависимости

Функция опирается на существующие типы `Todo` / `TodoList`; HTTP-слой —
на текущее состояние и общий JSON-ответ сервера. Node.js >=20, TypeScript
и Vitest уже определены в [package.json](../package.json).
Пустой список — штатный случай. Дополнительная обработка ошибок, аутентификация,
пагинация и сохранение статистики между перезапусками не требуются.

## План проверки после реализации

1. Выполнить `npm run check` и `npm test`, включая перечисленные проверки
   `todoStats` и существующие регрессионные тесты.
2. На свежем процессе проверить HTTP 200, тип содержимого и точный JSON
   `GET /todos/stats` для пустого списка. Через существующий API добавить
   три дела, завершить одно, проверить смешанные счётчики, затем завершить
   остальные и проверить состояние «все выполнены».
3. Повторить запрос статистики; проверить неизменность списка через
   `GET /todos`. Проверить, что `?filter=open` не меняет общие счётчики,
   а `POST /todos/stats` возвращает существующий 404.
4. Сверить README и состав diff с границами объёма; убедиться в отсутствии
   новых зависимостей и изменений инфраструктуры.

Это план приёмки реализации, а не результаты выполненных проверок.
