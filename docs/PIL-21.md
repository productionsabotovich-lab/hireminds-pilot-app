# PIL-21 — Сводка открытых и выполненных TODO

Редакция 1. Статус: объём утверждён 2026-11-17; реализация выполнена в этой же ветке
(`src/todos.ts`, `src/server.ts`, `test/todos.test.ts`, `test/server.test.ts`, `README.md`).

## Цель и основания

Клиенту HTTP-API нужна сводка по текущему списку дел без изменения данных: сколько дел всего,
сколько ещё открыто, сколько выполнено. Чистая функция считает по переданному состоянию
списка, эндпоинт `GET /todos/stats` отдаёт те же счётчики в JSON.

Отличие PIL-21 от более ранних постановок той же функциональности (PIL-18, PIL-19,
серия PIL-249xx): критерий приёмки прямо требует, чтобы **HTTP-поведение** нового
маршрута было покрыто проверками, а не только чистая логика подсчёта. Поэтому HTTP-уровневый
тест маршрута входит в объём, а не остаётся ручной проверкой.

## Согласуемый объём

### 1. Чистая функция `todoStats` (`src/todos.ts`)

- Экспортируется из `src/todos.ts` рядом с остальными чистыми функциями, по именованию
  и стилю существующих функций (`addTodo`, `completeTodo`, `listTodos`).
- Сигнатура: `todoStats(list: TodoList): TodoStats`, где
  `export type TodoStats = { total: number; open: number; done: number }`.
  Вход — существующий тип `TodoList` (`{ nextId, items }`): так устроены все чистые функции
  модуля, и эндпоинт тогда передаёт `state` напрямую. Новые типы для входа не вводятся.
- Результат — обычный объект **ровно с тремя собственными ключами**: `total`, `open`, `done`.
  Никаких дополнительных полей, вложенности, процентов и метаданных.
- Значения — неотрицательные целые числа:
  - `total` = количество элементов `list.items`;
  - `done` = количество элементов с `done === true`;
  - `open` = количество элементов с `done === false` (эквивалентно `total - done`).
- Инвариант: `total === open + done` для любого корректного входа.
- Счёт идёт по флагу `done` у элементов, а не по истории действий: повторное
  завершение уже выполненного дела не увеличивает `done` второй раз.
- Значение `nextId` в расчёте не участвует.
- Функция **не мутирует** вход: не меняет `list`, `list.nextId`, массив `list.items`
  (ссылка, длина и порядок), поля и идентичность элементов; элементы не добавляются
  и не удаляются.
- Функция детерминирована: повторные вызовы с одним и тем же состоянием дают равные результаты.
- Валидация некорректного объекта вне контракта TypeScript не вводится: функция
  внутренняя, единственный вызывающий код передаёт состояние сервера.

### 2. Эндпоинт `GET /todos/stats` (`src/server.ts`)

- Обработчик добавляется в существующий `handle` в `src/server.ts`; состояние читается
  из текущей переменной `state`. Новое хранилище, новые модули и новая логика хранения
  не вводятся.
- Ответ: HTTP **200**, заголовок `Content-Type: application/json; charset=utf-8`
  (существующий хелпер `send`), тело — результат `todoStats` для текущего состояния
  **без обёртки и дополнительных полей**: `{"total":N,"open":N,"done":N}`.
- Запрос только читает: состояние процесса после запроса не меняется; поведение
  `GET /todos`, `POST /todos`, `POST /todos/:id/complete` не меняется.
- Параметры запроса, включая `filter`, игнорируются: статистика всегда по всему списку.
  Неизвестные query-параметры не приводят к ошибке.
- Путь сопоставляется точно: `/todos/stats` не совпадает с `/todos` и с шаблоном
  `/todos/(\d+)/complete` (совпадение требует цифровой `id`), поэтому коллизий с
  существующими маршрутами нет; существующая логика ответа 404 для неизвестных путей
  сохраняется (включая `/todos/stats/` со слешем).
- Метод, отличный от `GET` (например `POST /todos/stats`), получает существующий
  ответ 404 `{"error":"not found"}` — новое поведение для него не вводится.
- Новая ветка маршрута ставится внутри существующей цепочки `if` до ветки 404;
  отдельный файл-роутер, middleware и рефакторинг `handle` не вводятся.

### 3. Проверки

Проверки закрывают обе части критерия приёмки «чистая логика подсчёта и HTTP-поведение
покрыты проверками». Новых тестовых зависимостей нет.

#### 3.1. Чистая функция (`test/todos.test.ts`)

Кейсы добавляются в существующий файл `test/todos.test.ts`, рядом с текущей группой `todos`
(например, отдельной группой `todoStats`). Существующие кейсы по смыслу не меняются.
Обязательные кейсы:

- **Пустой список**: `todoStats(emptyList())` → ровно `{ total: 0, open: 0, done: 0 }`.
- **Смешанный список**: три дела, одно выполнено → ровно `{ total: 3, open: 2, done: 1 }`.
- **Все выполнены**: два выполненных дела → ровно `{ total: 2, open: 0, done: 2 }`.
- **Отсутствие мутаций**: снимок состояния (ссылка на `list`, значение `nextId`, ссылка и
  содержимое массива `items`, порядок элементов, поля и идентичность каждого элемента)
  до и после вызова совпадает; вызов на замороженном входе (`Object.freeze`) не бросает
  исключений.
- **Детерминированность**: два вызова подряд на неизменённом состоянии дают равные результаты.

Сравнение результата — точное, по всему объекту (`toEqual`): лишние определённые ключи
в результате проверку не проходят, поэтому отдельная проверка набора ключей не обязательна,
но допускается.

#### 3.2. HTTP-маршрут (`test/server.test.ts`, новый файл)

Кейсы HTTP-поведения входят в объём и выполняются автоматически. Отдельный файл
`test/server.test.ts` выбран потому, что `state` — переменная модуля в `src/server.ts`,
и каждый файл тестов в Vitest получает свой экземпляр модуля; при желании тот же приём
(сброс реестра модулей) применяется и внутри существующего файла.

Рекомендуемый и проверенный каркас (прототип собран и прогнан при подготовке спецификации):

- сервер поднимается на реальном сокете: `createServer(handle)` из `node:http`
  (функция `handle` уже экспортируется из `src/server.ts`) и `server.listen(0, '127.0.0.1')`;
  порт `0` — свободный порт, фактический адрес берётся из `server.address()`;
- запросы выполняются глобальным `fetch` Node.js (в проекте `engines.node: >=20`),
  HTTP-клиент из зависимостей не нужен;
- изоляция состояния между кейсами: перед каждым кейсом `vi.resetModules()` и динамический
  импорт `const { handle } = await import('../src/server.js')` — это даёт новый экземпляр
  модуля с пустым `state`, поэтому кейст «пустой список» детерминирован;
- сервер закрывается в `afterEach` (`server.close()`), чтобы не оставались висящие сокеты.

Обязательные HTTP-кейсы:

- **Пустой список**: `GET /todos/stats` → 200, `content-type: application/json; charset=utf-8`,
  тело ровно `{"total":0,"open":0,"done":0}`.
- **Смешанное состояние**: добавить дела через `POST /todos`, завершить одно через
  `POST /todos/:id/complete` → `GET /todos/stats` отдаёт значения текущего состояния,
  например `{"total":2,"open":1,"done":1}`, и выполняется `total === open + done`.
- **Запрос не меняет задачи**: `GET /todos` до и после `GET /todos/stats` отдаёт одинаковый
  список; повторный `GET /todos/stats` даёт тот же результат.
- **Query-параметры игнорируются**: `GET /todos/stats?filter=open` → тот же общий ответ,
  фильтр к статистике не применяется.
- **Не-GET**: `POST /todos/stats` → 404 `{"error":"not found"}` (существующее поведение).
- **Регрессия существующих маршрутов**: `GET /todos`, `GET /todos?filter=open`,
  `GET /todos?filter=done`, `POST /todos`, `POST /todos/:id/complete` отвечают как раньше
  (прежние статусы и прежние тела ответа).

Замечания по окружению (не влияют на объём):

- `tsconfig.json` включает только `src`, поэтому файлы в `test/` **не** проверяются
  командой `npm run check`; типы тестов проверяются только вручную/в IDE.
  Сборка `npm run build` тоже затрагивает только `src`.
- Vitest по умолнию изолирует каждый тестовый файл (свой реестр модулей), поэтому
  `test/server.test.ts` не влияет на `test/todos.test.ts` и наоборот.

## Исключения и границы

Вне объёма (не делается в этой задаче):

- UI, веб-интерфейс, дашборды и визуализация статистики;
- постоянное хранилище: базы данных, файлы, внешние сервисы; статистика живёт в памяти
  процесса так же, как сам список, и сбрасывается при перезапуске (критерий 6);
- статистика по фильтрам, пользователям, категориям, приоритетам, процентам и долям;
- новые поля в модели `Todo`/`TodoList`, миграции модели, валидация некорректного `TodoList`;
- рефакторинг существующих маршрутов, изменение формата ответов `GET /todos`,
  `POST /todos`, `POST /todos/:id/complete`;
- новые зависимости, изменения `package.json`/`package-lock.json`, `tsconfig.json`,
  `.github/**`, CI и инфраструктуры;
- кэширование (`ETag`, `Cache-Control`), пагинация, сортировка, версионирование API,
  авторизация;
- сводка в ответе `GET /todos` (например, полем `stats` или конвертом) — формат
  `GET /todos` не меняется;
- чужие задачи и PR (PIL-18, PIL-19, серия PIL-249xx) не трогаются.

## Зависимости

- Внешних зависимостей и сервисов нет: используются уже подключённые TypeScript,
  Node.js `>=20` и Vitest; HTTP-клиентом в тестах служит встроенный `fetch` Node.js.
- `package.json` и `package-lock.json` не меняются; lock-файл остаётся валидным,
  `npm ci` работает без его обновления.
- Требуются только команды из [package.json](../package.json): `npm run check` и `npm test`;
  обе доступны без сети.
- Особенность окружения (проверено): в текущем окружении `NODE_ENV=production` и
  `npm config omit=dev`, поэтому обычный `npm ci` **не ставит** dev-зависимости;
  для `npm run check` и `npm test` нужен `npm ci --include=dev`. На содержимое
  репозитория это не влияет.
- Спецификация (`docs/PIL-21.md`) включается в PR реализации.

## Вопросы к PM (не блокируют минимальный объём)

1. **Дубликаты задачи.** `PIL-18`, `PIL-19` (открытый PR #15) и серия `PIL-24901…PIL-24917`
   (открытые PR #5–#14) описывают ту же функциональность. Нужно ли объединить их в одну
   задачу и закрыть лишние PR? Решение по умолчанию: PIL-21 реализуется самостоятельно,
   чужие PR и ветки не трогаются.
2. **Различие в критерии приёмки.** PIL-21 требует покрытия HTTP-поведения проверками,
   в PIL-19 такой тест был признан лишним и проверка сделана вручную. Нужно ли
   пересмотреть PR #15 и другие дубли в пользу HTTP-теста? Решение по умолчанию:
   в PIL-21 HTTP-тест обязателен, правки чужих PR — вне объёма.
3. **Фильтр в статистике.** Сейчас `filter` игнорируется, статистика всегда по всему списку.
   Нужна ли поддержка `filter=open|done` (и тогда расширяется ли форма ответа)?
   Решение по умолчанию: не поддерживать.
4. **Разбор и доли.** Нужны ли проценты, доли, группировка по категориям или исполнителям,
   «сводка за период»? Решение по умолчанию: нет, только три целочисленных счётчика.
5. **Кэширование.** Нужен ли `ETag`/`Cache-Control` для `GET /todos/stats`?
   Решение по умолчанию: не добавлять, отдавать как обычный JSON без кэш-заголовков.
6. **Статистика вместе со списком.** Нужно ли вернуть сводку в ответе `GET /todos`
   (например, полем `stats` или конвертом)? Решение по умолчанию: нет, формат `GET /todos`
