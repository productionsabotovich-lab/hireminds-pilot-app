# PIL-64 — Восстановление авторизации до рабочего запроса

Редакция 1. Статус: подготовлена к утверждению объёма. Реализация и декомпозиция не начаты.

## Цель и основания

Изолированный приёмочный прогон: после отказа авторизации раннера владелец восстанавливает доступ и продолжает ту же задачу. Рабочий результат в тестовом TODO API — стабильный заголовок `X-Todo-Api-Version: 1` на успешном `GET /todos` при сохранении статуса и тела.

## Границы объёма

В приложении изменяется только успешный ответ существующего маршрута `GET /todos`: добавляется один HTTP-заголовок с постоянным строковым значением `1`. Поведение покрывается автоматическим HTTP-тестом в существующем наборе Vitest. Предполагаемые файлы реализации — `src/server.ts` и `test/server.test.ts`; настоящая спецификация хранится в `docs/PIL-64.md`.

Заголовок применяется ко всем успешным вариантам этого маршрута: без query, с `filter=all|open|done`, а также с неизвестным значением фильтра или иными query-параметрами. Существующий разбор фильтра сохраняется. Пустой и непустой списки получают одинаковое значение заголовка. Имя заголовка сравнивается без учёта регистра согласно HTTP; значение — строго `1`, без повторных значений.

Статус остаётся `200`, `Content-Type` — `application/json; charset=utf-8`, тело — прежний JSON-массив без обёрток и новых полей. Чтение не меняет состояние, порядок элементов и фильтрацию. На других маршрутах и ошибочных ответах новый заголовок не добавляется.

Приёмочный сценарий авторизации проверяется в платформе Hireminds по истории того же issue/прогона. Он не требует реализации авторизации в TODO API. История в постановке подтверждает сообщение об отказе и явный повтор; сама по себе она не подтверждает успешное завершение всего E2E.

## Пользовательские сценарии и критерии приёмки

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| API-1 | Клиент запрашивает `GET /todos` при пустом состоянии | HTTP 200, прежний Content-Type, тело `[]`, `X-Todo-Api-Version` равен `1` |
| API-2 | В списке два дела, одно выполнено; клиент запрашивает список и `filter=all`, `filter=open`, `filter=done` | Каждый ответ имеет заголовок `1`; статус 200 и точное содержимое прежнего массива для соответствующего фильтра сохранены |
| API-3 | Клиент передаёт неизвестный фильтр или посторонний query-параметр | Прежний успешный ответ всего списка и заголовок `1`; новая валидация не вводится |
| API-4 | Клиент повторяет чтение неизменённого списка | Заголовок стабилен, тела совпадают, состояние не изменяется |
| API-5 | Выполняются запросы статистики, создания, завершения и неизвестного пути | Их существующие статусы и тела сохраняются; заголовок версии не добавляется |
| E2E-1 | Авторизация раннера недействительна до рабочего запроса | Платформа сообщает, что авторизация подключения не пройдена, указывает подключение и понятное действие восстановления/повтора; секреты не выводятся, рабочее изменение не выполняется |
| E2E-2 | Владелец восстанавливает авторизацию и явно повторяет этап | Продолжается PIL-64 с прежней целью и контекстом; рабочий запуск достигает результата API-1–API-5 без создания новой задачи и повторного запроса уже имеющейся постановки |

## Исключения

- Пока авторизация не восстановлена, этап остаётся неуспешным с понятной причиной; успешное выполнение не имитируется.
- Обновление авторизации без явного повтора не обязано автоматически запускать этап: в данном сценарии используется явный повтор.
- Ошибки сети и прочие ошибки раннера не должны трактоваться как подтверждение успешного восстановления; диагностика таких сбоев не расширяет изменение приложения.
- Не вводятся новые коды ошибок, маршруты, схема авторизации API, версия в JSON или версионирование URL.

Вне объёма: изменение платформы Hireminds и её UI, подключений, токенов, retry-механизма; новые E2E-инструменты или инфраструктура; глобальный заголовок для всего API; CORS, кэширование, рефакторинг, изменение бизнес-логики, зависимостей, хранилища и CI. Критерии E2E-1–E2E-2 служат приёмкой существующего платформенного процесса, а не заданием на его разработку в этом репозитории.

## Зависимости

Для API достаточно существующих Node.js >=20, TypeScript, Vitest и HTTP-тестового каркаса; новые зависимости не нужны. HTTP I/O остаётся в `src/server.ts`, чистая логика `src/todos.ts` не меняется. Перед PR обязательны `npm run check` и `npm test`; одна задача — одна ветка — один PR в `main` согласно правилам проекта.

Для платформенной приёмки нужны тестовое подключение раннера, возможность владельца восстановить его авторизацию, явный повтор и доступ к истории запуска. Секреты и их значения в доказательства не включаются. Если история не позволяет проверить отсутствие рабочего запроса до отказа или продолжение того же прогона, соответствующий критерий остаётся неподтверждённым до получения платформенного свидетельства.

## План проверки

1. Расширить существующие HTTP-тесты проверками API-1–API-4 через реальный локальный сервер и встроенный `fetch`; использовать существующие изоляцию состояния и закрытие сервера. Проверять заголовок вместе со статусом и точным телом, чтобы тест обнаруживал изменение контракта.
2. Для API-5 использовать существующие проверки маршрутов, дополнив проверками отсутствия заголовка на статистике, POST и 404. Не создавать отдельный тестовый фреймворк.
3. Выполнить `npm run check` и `npm test`; проверить diff на соответствие границам объёма. В фазе спецификации команды проверки реализации не запускаются.
4. По истории платформы проверить E2E-1: отказ относится к авторизации конкретного подключения до рабочего запроса, сообщение содержит действие восстановления и повтора. Приложить ссылку на событие/лог без секретов.
5. После восстановления и повтора сопоставить issue и идентификаторы запуска/продолжения, подтвердить сохранение контекста и рабочий результат API. Приложить ссылки на продолжение, итоговый PR и проверки. Наличие текущей сессии само по себе не считать доказательством завершения E2E.
