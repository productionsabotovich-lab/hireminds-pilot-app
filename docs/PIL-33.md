# PIL-33 — Версия API списка дел

Редакция 1. Статус: подготовлена к утверждению объёма. Реализация не начата.

## Цель и основания

Клиент HTTP-API может узнать версию API сразу после запуска сервера, без создания дел
и без изменения состояния приложения.

## Согласуемый объём и контракт

1. Добавить в существующий HTTP-обработчик маршрут `GET /version`.
   Ответ: HTTP 200, `Content-Type: application/json; charset=utf-8`, JSON ровно
   `{"version":1}`: единственное поле `version`, числовое значение `1`, без обёртки.
   Это фиксированная версия API, не версия пакета, сборки или приложения.
2. Ответ доступен при пустом списке сразу после запуска и остаётся тем же при любом
   состоянии дел, в том числе после добавления и завершения дел и повторных запросов.
3. Запрос не меняет список, порядок, идентификаторы, названия, признаки выполнения
   и следующий выдаваемый идентификатор. Предварительные записи и внешние сервисы
   не требуются.
4. Путь сопоставляется точно с `/version`; query-параметры игнорируются, как параметры,
   не используемые существующим обработчиком. Например, `/version?filter=open`
   возвращает тот же ответ. `/version/` и `/Version` остаются неизвестными путями.
5. Для других методов на `/version` сохраняется существующий ответ HTTP 404
   с JSON `{"error":"not found"}`. Поддержка HEAD, OPTIONS и ответ 405 не добавляются.
6. Существующие маршруты `GET /todos`, `GET /todos/stats`, `POST /todos`,
   `POST /todos/:id/complete`, их фильтры, ответы и обработка ошибок сохраняются.
7. В существующий набор HTTP-тестов добавить автоматические проверки контракта
   и отсутствия изменений состояния. В README добавить строку маршрута в таблицу API
   и короткий пример `curl -s http://127.0.0.1:3000/version` с ответом `{"version":1}`.

## Пользовательские сценарии

- Клиент обращается к только что запущенному серверу: без создания дел получает
  HTTP 200 и `{"version":1}`; список остаётся пустым.
- Клиент добавляет два дела и завершает одно. До и после повторных запросов версии
  список совпадает целиком, версия равна 1; следующее добавленное дело получает
  следующий последовательный идентификатор.
- Разработчик открывает README и использует готовый пример запроса версии.
- Существующий клиент продолжает получать списки, фильтровать дела, читать статистику,
  создавать и завершать дела с прежними ответами.

## Критерии приёмки и план проверки

| № | Проверка | Ожидаемый результат |
| --- | --- | --- |
| 1 | HTTP-запрос `GET /version` в изолированном сервере до создания дел | 200; JSON Content-Type с UTF-8; тело ровно `{"version":1}` |
| 2 | Прочитать пустой список до и после двух запросов версии, затем создать дело | До и после `[]`; оба ответа версии одинаковы; первое дело получает `id: 1` |
| 3 | Создать два дела, завершить одно, прочитать список до и после двух запросов версии | Версия всегда 1; весь массив дел, включая порядок и поля, совпадает |
| 4 | После сценария 3 добавить ещё одно дело | Создание успешно, `id: 3`; счётчик идентификаторов запросами версии не изменён |
| 5 | `GET /version?filter=open&extra=1` | Тот же успешный ответ версии |
| 6 | `POST /version`, `GET /version/`, `GET /Version` | 404 и `{"error":"not found"}` |
| 7 | Прогнать существующие тесты HTTP и чистых функций | Прежние сценарии списка, фильтров, создания, завершения, статистики и ошибок проходят без изменения ожиданий |
| 8 | Просмотреть README | В таблице есть `GET /version`, пример запроса и точный ответ |

Проверки 1–6 выполняются автоматически в `test/server.test.ts` через существующий
каркас реального HTTP-сервера, встроенный `fetch` и изоляцию состояния между тестами.
Допустимо объединять связанные сценарии в один тест. Отдельная чистая функция и её
тесты для константного ответа не нужны.

После реализации обязательны `npm run check` и `npm test` по правилам проекта.
Дополнительно выполнить `npm run build` и проверить пример README на запущенном
сервере, чтобы подтвердить работу собранного приложения. Проверить diff на соответствие
границам объёма. На фазе спецификации эти проверки реализации не выполняются.

## Исключения и границы объёма

Ожидаемые изменения реализации: `src/server.ts`, `test/server.test.ts`, `README.md`;
документ задачи — `docs/PIL-33.md`.

Вне объёма: UI, хранилище, миграции, изменения модели и чистых функций дел, новые
зависимости, конфигурация сборки и CI, рефакторинг маршрутизатора, авторизация,
кэширование, метаданные сборки, динамическая версия из `package.json`, префиксы
маршрутов `/v1`, изменение существующих ответов и автоматизация платформы Hireminds.
Название E2E не расширяет задачу до проверки полного цикла платформы: обязательная
автоматическая проверка относится к HTTP-маршруту приложения согласно постановке.

Исключения контракта: неверный путь или метод обрабатываются существующим 404;
новая валидация параметров и специальная обработка тела запроса не вводятся.

## Зависимости и ограничения

- Node.js >=20, текущие TypeScript и Vitest; новые библиотеки и сервисы не нужны.
- Используются существующие JSON-ответы сервера и тестовый каркас; I/O остаётся
  в `src/server.ts`, бизнес-логика дел не меняется.
- Для проверки нужны установленные dev-зависимости и возможность открыть локальный
  HTTP-порт в тестах. CI использует Node.js 22 и существующие команды проекта.
- Реализация начинается после утверждения этой редакции спецификации. Декомпозиция,
  реализация, PR и запуск отдельного решения об объёме в эту фазу не входят.
