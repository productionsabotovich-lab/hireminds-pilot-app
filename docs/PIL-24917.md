# PIL-24917 — Add todo statistics

Редакция 1. Статус: спецификация подготовлена к утверждению объёма.

## Цель и основания

Клиенту HTTP-API нужна сводка по списку дел без изменения данных: сколько дел всего,
сколько ещё открыто, сколько выполнено. Функция считает по текущему состоянию списка,
эндпоинт отдаёт тот же счётчик в JSON.

Основания: [постановка PIL-24917](/opt/hireminds/context/issue.md),
[правила проекта](../CLAUDE.md), [описание API](../README.md),

[HTTP-обработчик](../src/server.ts),
[существующие тесты](../test/todos.test.ts),
[команды и зависимости](../package.json).

## Согласуемый объём

### 1. Чистая функция `todoStats` (src/todos.ts)

- Экспортируется из `src/todos.ts` рядом с остальными чистыми функциями; сигнатура
  `todoStats(list: TodoList): { total: number; open: number; done: number }`.
- Результат — обычный объект **ровно с тремя собственными ключами**: `total`, `open`, `done`.
  Никаких других полей, вложенности, процентов и метаданных.
- Значения — неотрицательные целые числа:
  - `total` = количество элементов `list.items`;
  - `done` = количество элементов с `done === true`;
  - `open` = количество элементов с `done === false` (эквивалентно `total - done`).
- Инвариант: `total === open + done` для любого входа.
- Функция **не мутирует** вход: не меняет `list`, `list.nextId`, массив `list.items`
  (ссылка, длина и порядок), поля и идентичность элементов; не добавляет и не удаляет элементы.
- Функция детерминирована: повторные вызовы с одним и тем же состоянием дают равные результаты.
- Вход берётся из существующего типа `TodoList`; отдельная валидация некорректного
  списка не вводится (внутренняя функция, единственный вызывающий код передаёт состояние сервера).

### 2. Эндпоинт `GET /todos/stats` (src/server.ts)

- Обработчик добавляется в существующий `handle` в `src/server.ts`, состояние сервера
  читается из текущей переменной `state`; новое хранилище и новая логика не вводятся.
- Ответ: HTTP **200**, заголовок `Content-Type: application/json; charset=utf-8`
  (существующий хелпер `send`), тело — результат `todoStats` для текущего состояния
  **без обёртки и дополнительных полей**: `{"total":N,"open":N,"done":N}`.
- Запрос только читает: состояние процесса после запроса не меняется, последующие
  ответы `GET /todos`, `POST /todos`, `POST /todos/:id/complete` не меняются.
- Параметры запроса, включая `filter`, игнорируются: статистика всегда по всему списку.
  Неизвестные query-параметры не приводят к ошибке.
- Путь сопоставляется точно: `/todos/stats` не совпадает с `/todos` и с шаблоном
  `/todos/:id/complete` (совпадение требует цифровой `id`), поэтому коллизий с
  существующими маршрутами нет; порядок проверок в обработчике сохраняет текущую логику 404.
- Метод, отличный от `GET` (например `POST /todos/stats`), получает существующий
  ответ 404 `{"error":"not found"}` — новое поведение для него не вводится.

### 3. Тесты (test/todos.test.ts)

Добавляются в существующий файл `test/todos.test.ts`, рядом с текущими кейсами `todos`,
без новых тестовых зависимостей и без отдельных файлов. Обязательные кейсы:

- **Пустой список**: `todoStats(emptyList())` → ровно `{ total: 0, open: 0, done: 0 }`.
- **Смешанный список**: три дела, одно выполнено → ровно `{ total: 3, open: 2, done: 1 }`.
- **Все выполнены**: два выполненных дела → ровно `{ total: 2, open: 0, done: 2 }`.
- **Отсутствие мутаций**: снимок состояния (ссылка на `list`, `nextId`, ссылка и содержимое
  массива `items`, поля и идентичность каждого элемента) до и после вызова совпадает;
  повторный вызов даёт тот же результат.

Дополнительно (не вместо, а сверх обязательных): проверка инварианта `total === open + done`
и того, что результат содержит ровно три ключа. Кейсы HTTP-эндпоинта допускаются,
но не обязательны: отдельного серверного теста в проекте сейчас нет, а добавление
серверных харнессов расширяет объём. Функциональная проверка эндпоинта — в плане проверки ниже.

## Пользовательские сценарии и критерии приёмки

| # | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | Клиент просит статистику пустого списка | Функция и эндпоинт возвращают ровно `{ total: 0, open: 0, done: 0 }` |
| 2 | В списке три дела, одно выполнено | Ровно `{ total: 3, open: 2, done: 1 }` |
| 3 | Все два дела выполнены | Ровно `{ total: 2, open: 0, done: 2 }` |
| 4 | После `POST /todos` | `total` и `open` вырастают на 1, `done` не меняется, `total === open + done` |
| 5 | После `POST /todos/:id/complete` | `open` уменьшается на 1, `done` растёт на 1, `total` сохраняется |
| 6 | Повторное завершение того же дела | Счётчики не меняются (`done` не растёт второй раз) |
| 7 | Вызов `todoStats` на состоянии с делами | Состояние не изменилось: те же `nextId`, тот же массив `items` (ссылка, порядок, длина), те же поля и та же идентичность элементов |
| 8 | Два вызова `todoStats` подряд | Результаты равны |
| 9 | `GET /todos/stats` | Статус 200, `Content-Type: application/json; charset=utf-8`, тело — ровно три ключа `total`, `open`, `done` со значениями текущего состояния |
| 10 | `GET /todos/stats?filter=open` | Ответ не отличается от `GET /todos/stats` (фильтр игнорируется) |
| 11 | `GET /todos/stats` до и после `POST /todos` | Значения счётчиков отражают текущее состояние |
| 12 | `POST /todos/stats` или другой не-`GET` метод | Существующий ответ 404 `{"error":"not found"}` |
| 13 | Существующие операции `GET /todos`, `POST /todos`, `POST /todos/:id/complete` | Поведение не изменилось |
| 14 | Ключи ответа | Ровно `total`, `open`, `done` — ни одного лишнего ключа |

## Исключения и границы

Вне объёма (не делается в этой задаче):

- UI, веб-интерфейс, дашборды и визуализация статистики;
- сохранение данных, базы данных, файловое или внешнее хранилище; статистика живёт
  в памяти процесса так же, как сам список, и сбрасывается при перезапуске;
- статистика по фильтрам, пользователям, категориям, приоритетам, процентам и долям;
- новые поля в модели `Todo`/`TodoList`, миграции модели, валидация некорректного `TodoList`;
- рефакторинг существующих маршрутов, изменение формата ответов `GET /todos`,
  `POST /todos`, `POST /todos/:id/complete`;
- новые зависимости, изменения `package.json`/`package-lock.json`, изменения `.github/**`,
  CI и инфраструктуры;
- серверные тест-харнессы и отдельные файлы тестов;
- пагинация, сортировка, версионирование API, кэш и `ETag`.

## План проверки

1. `npm run check` — проверка типов проходит без ошибок (включая новую сигнатуру `todoStats`).
2. `npm test` — все тесты vitest проходят; новые кейсы (пустой список, смешанный,
   все выполнены, отсутствие мутаций) присутствуют и зелёные; существующие кейсы `todos`
   не меняются по смыслу.
3. Ручная проверка эндпоинта: `npm run build && npm start`, затем
   `GET /todos/stats` (ожидается `{ "total": 0, "open": 0, "done": 0 }`),
   `POST /todos {"title":"a"}`, повторный `GET /todos/stats` (`total` 1, `open` 1),
   `POST /todos/1/complete`, `GET /todos/stats` (`total` 1, `open` 0, `done` 1),
   `GET /todos/stats?filter=open` (тот же ответ), `POST /todos/stats` (404).
4. Проверка, что `GET /todos/stats` не изменил состояние: `GET /todos` до и после
   запроса статистики отдаёт тот же список.
5. Проверка границ объёма: `git diff --name-only` против `main` показывает только
   `src/todos.ts`, `src/server.ts`, `test/todos.test.ts`, `README.md`, `docs/PIL-24917.md`;
   `package.json`, `package-lock.json`, `.github/**` без изменений.
6. CI на текущем HEAD PR выполняет `npm ci`, `npm run check`, `npm test` — все три шага зелёные.

## Вопросы к PM (не блокируют минимальный объём)

1. **Фильтр в статистике.** Сейчас `filter` игнорируется, статистика всегда по всему списку.
   Нужна ли поддержка `filter=open|done` (и тогда расширяется ли форма ответа)?
   Решение по умолчанию: не поддерживать.
2. **Кэширование.** Нужен ли `ETag`/`Cache-Control` для `GET /todos/stats`?
   Решение по умолчанию: не добавлять, отдавать как обычный JSON без кэш-заголовков.
3. **Переиспользование функции.** Нужна ли функция с необязательным аргументом-фильтром
   или отдельные счётчики по пользователям/категориям для будущих задач?
   Решение по умолчанию: оставить минимальную сигнатуру `todoStats(list)`.
4. **Формат чисел.** Подтвердить, что нужны целые числа без дробей и форматирования
   (текущая реализация отдаёт целые). Решение по умолчанию: целые.
